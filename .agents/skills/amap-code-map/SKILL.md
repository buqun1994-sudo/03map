# 高德业务代码地图

## 触发与入口

1. 用户提到“改哪个业务行为或 UI 部位”时使用本 Skill。先读根 AGENTS.md、docs/README.md、docs/code-map/README.md 和 docs/code-map/基线清单.md；输入基线始终是归档的 9.5、125% 全屏 APK，`source/amap-9.5.0.600013/` 是只读源码真值。
2. 读 docs/code-map/主链索引.md 中命中的业务行，只打开列出的文件及局部方法。先判需求属于启动、窗口/手势、顶层 UI、地图层、native 视口/相机、导航协议中的哪条主链；同一现象可能跨层，逐层列出 owner 与验证边界。
3. 索引未命中时，按用户可见元素的文本、资源名/ID、布局、Smali 调用签名、事件处理和 JNI 协议逐层扩展搜索；找到实际消费路径才称为“已定位”。`res/values/ids.xml` 的名字只是候选，不能直接认定控件的绘制者。
4. 历史 `.tmp/` 和旧实验记录只提供已标注的线索，不代替正式基线。第三方 Java 反编译视图不可当作可回编源码；施工入口是 Apktool 的 Smali、Manifest、资源和 assets。修改时从正式快照复制到被忽略的 `apk-work/`，不反向污染快照。

## 业务映射与更新门槛

每次定位高价值业务入口、数据流、资源映射、反证或版本差异时，同一轮更新 docs/code-map/主链索引.md，形成“用户要改什么 → 业务 owner → 第一落点 → 上下游 → 可施工文件/方法 → 最低验证”的可复用记录。具体子控件的 owner 尚未找到时，明确标记“未定位”并写下一跳，不制造虚假的精确路径。

1. 每项至少记录：用户任务信号、业务 owner、精确相对路径和方法签名、上游/下游、已确认行为与证据等级、未证实推断、适用 APK 哈希/版本和验证方式。
2. 例如“150% 的按钮/地址输入”先追 `rv.C()`、`kc.v()` 与 `ui_surface`，再确认具体控件；“车标/道路文字太小”追 `map_surface`、native/资源，不能把 UI 密度当作地图层 setter；“相机偏移”先查 View/Layer/buffer/裁剪原点和 native layout，不直接猜 camera offset。
3. 对静态事实直接定位磁盘源码；对视觉、窗口、相机或 native 生效结论必须有同一 APK 的运行证据。区分“静态确认”“实机确认”“实验参考”“待验证”。
4. 混淆名和资源 ID 同时写物理路径、调用语义和版本；本项目只维护当前 9.5 输入身份，不套用旧版本混淆类或已废弃窗口尺寸。
5. 同一事实只有一个文档 owner。主链索引只记入口与关系，不把 7,269 个类机械罗列成地图；发现索引与源码不一致先纠正根因，再继续施工。
6. 只记录可共享的结构证据，不写 APK 内容、密钥、设备地址、用户轨迹、完整日志或个人绝对路径。

## 收尾

核对新锚点存在且方法签名匹配；执行 `node scripts/check-code-map.mjs`。若改动源码，再按 docs/testing/验证矩阵.md 构建、签名并在设备可用时完成运行级验证。交付时说明新增的“业务 → 文件/方法”映射、证据等级、仍未定位的子控件和下一跳。
