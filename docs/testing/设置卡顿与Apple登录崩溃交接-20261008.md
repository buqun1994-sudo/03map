## 2. Apple 闪退：已定位到错误窗口 token

### 2.1 直接证据

[崩溃日志57–84行](<../../.tmp/settings-media-apple-20261007/car-user-tested-apple-crash.log#L57>)记录：

```text
10-08 03:05:22.699  Process: com.autonavi.amapautolite, PID: 13811
android.view.WindowManager$BadTokenException:
Unable to add window -- token android.view.ViewRootImpl$W@6d6f6 is not valid;
is your activity running?
  at android.view.ViewRootImpl.setView
  at android.view.WindowManagerGlobal.addView
  at android.view.WindowManagerImpl.addView
  at android.app.Dialog.show
  at ...LyricsProviderSettingsKt.AppleMusicScreenDialog...(SourceFile:291)
```

[86–114行](<../../.tmp/settings-media-apple-20261007/car-user-tested-apple-crash.log#L86>)在 `03:05:41.982`、PID 15995再次记录相同异常，token对象变为另一个 `ViewRootImpl.W`。日志开头 `00:21` 的native AssetManager SIGSEGV属于其他时间／PID，不能拿来解释本次Apple触发崩溃。

### 2.2 当前源码链与结论

入口集中在[登录UI](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/LyricsProviderSettings.kt#L275>)：

1. `AppleMusicScreenDialog()`通过`appleLoginWindowContext()`创建物理资源Context。
2. [配置Context实现](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/LyricsProviderSettings.kt#L374>)以`host.createConfigurationContext(configuration)`返回新Context。
3. [独立窗口构造](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/LyricsProviderSettings.kt#L300>)把该Context直接给`ComponentDialog`；默认是应用窗口类型。
4. 同文件第320行显式设置`token = hostView.applicationWindowToken`。
5. 第291行`dialog.show()`将窗口提交真实WMS，WMS拒绝该`ViewRootImpl.W` token，异常未被处理而终止应用。

**高置信直接根因：新增独立Dialog的WindowManager／Activity owner链与手工token不匹配，把View窗口binder当成应用窗口token使用。** 物理Resources配置不能替代Activity的窗口归属。AOSP9的`createConfigurationContext`会复制`mActivityToken`，不能表述为“清空Activity token”；但裸ContextImpl不等于Activity重写的WindowManager／父Window链。本次确定的是实际提交的错误token和真实WMS拒绝，不应泛化到所有配置Context或Dialog。

失败点在新窗口显示阶段，官方登录页面未形成可见窗口。优先修窗口归属，不先重做WOA、WebView语法兼容或Cookie逻辑。

### 2.3 下一会话最小修复方向（未执行）

- 用真实宿主Activity及其WindowManager创建Dialog，保持Activity窗口默认token注入链。物理Resources／密度可以交给内容ComposeView，或由基于Activity的Context包装提供，但不能破坏窗口归属。
- 移除将`hostView.applicationWindowToken`手工当应用token的做法。不能简单换成`view.windowToken`、只设`ownerActivity`、改成overlay类型或捕获异常后假装登录成功。
- 保留本轮要求：实际root物理配置、MATCH_PARENT及相关flags在show前完成；不能回退到旧的首帧错误、刷新后才变正确的窗口。
- 宿主销毁／脱附、取消准备、重复打开沿现有生命周期和attempt门禁处理；不要增加第二个WebView或授权owner。

[窗口测试](<../../ui-preview/content-ui/src/test/java/com/icar03/content/ui/AppleMusicLoginPanelTest.kt>)已覆盖本机API28／34、错误地图Resources、首次predraw、复开、准备完成不换root等，但Robolectric的ShadowDialog／ShadowWindowManager不向真实WMS注册并校验AppWindowToken。**这些通过不能证明真实token有效。** 下一包必须在真实API28／车机冷打开、重复打开和返回路径验证无BadToken，再检查账号输入框、键盘与返回；真实账号／密码／OTP由用户在官方页面输入，本会话没有真实账号授权成功证据。

## 3. 设置卡顿：阴影设计有明确重路径，尚未量化唯一瓶颈

### 3.1 目前可以确定什么

用户手测确认恢复该版本后设置变卡。当前[阴影组件](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/DownwardSoftShadow.kt>)不是单纯调用标准硬件阴影，而是自行生成软件阴影位图后贴图：

```text
drawWithCache
  → synchronized texture()
  → 缓存未命中
  → 完整尺寸ARGB bitmap
  → 软件Canvas + Paint.setShadowLayer + drawRoundRect
  → 复制九块到小bitmap
  → recycle完整临时bitmap
  → 暖绘制每surface最多九次drawBitmap
```

具体锚点：

| 位置 | 确认的成本 |
|---|---|
| [26–29行](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/DownwardSoftShadow.kt#L26>)、[51–80行](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/DownwardSoftShadow.kt#L51>) | 在UI绘制缓存建立阶段同步查询并冷生成，没有worker |
| [70–76行](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/DownwardSoftShadow.kt#L70>) | 141dpi下blur／dy／圆角为小数，`fractionalMask`成立；key包含完整宽高和fill，尺寸不同就产生新条目 |
| [95–106行](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/DownwardSoftShadow.kt#L95>) | 创建完整轮廓位图并进行软件模糊。约640×900仅ARGB临时图就约2.4MiB，尚不含模糊中间成本 |
| [111–136行](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/DownwardSoftShadow.kt#L111>) | 再生成小纹理、复制九块、释放大图；4MiB／48条预算只限制最终缓存，未限制冷生成瞬时成本 |
| [181–182行](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/DownwardSoftShadow.kt#L181>) | 暖路径最多九次位图绘制，包含不透明中心fill；调用方随后再画background／Surface，存在重复填充 |

本轮为保留Skia分数模糊的逐尺寸像素结果，重新引入完整轮廓栅格化。**“最终缓存很小”“像素与缓存测试通过”都不能证明冷生成轻或车机滚动不卡。阴影应由可复用UI组件拥有，且不应让普通交互承担这种同步成本。** 当前实现虽在UI层，性能职责仍未做好。

### 3.2 不能据此断言“每帧都完整模糊”

逐个调用方只读核对后：

- [设置Sheet开合](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/SettingsSheet.kt#L105>)只改变graphicsLayer.translationY，外面固定大小；移动本身不会让key尺寸变化。
- [开关](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/SettingsControls.kt#L419>)只移动thumb；轨道fill随checked离散切换。
- [数值条](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/SettingsControls.kt#L801>)只改变内部进度，外阴影大小和颜色稳定。
- Ripple没有把逐帧按压色传进阴影key。缓存块重建可能重新分配frame／Rect／Paint，但命中条目不会重新blur。
- 确定的冷入口是首次挂载、切换页面或使卡片尺寸变化的选项，例如自定义颜色加入picker、当前句字号加入两行、[选择Apple加入状态区](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/LyricsProviderSettings.kt#L145>)。LRU淘汰后的重做频率、AnimatedContent是否实际给shadow中间尺寸，尚无trace。

[整进程帧统计](<../../.tmp/settings-media-apple-20261007/car-user-tested-gfxinfo.txt#L4>)记录7054帧，2387 janky（33.84%），P90=23ms、P99=57ms。它包含该进程不同界面及阶段，**不是设置页专项A/B，不能把33.84%全部归因阴影，也不能换算为设置FPS**。

结论等级：卡顿复现由用户确认；主线程完整软件烘焙、暖路径九次贴图及重复fill由源码确认；阴影是不是全部或主要持续瓶颈、冷miss频率、CPU／GPU各自占比仍需同场景采样。

### 3.3 下一会话建议（未执行）

1. 保持同一主题、141dpi、媒体播放和同一设置页，用短时可对照采样确认冷进入／暖滚动的主线程和RenderThread成本；记录miss次数、烘焙耗时、位图上传与draw耗时。不要用旧包整体帧数替代同场景比较。
2. 组件方案优先固定样式的小alpha阴影mask／Android NinePatch，阴影和表面fill分离，减少为每块surface记录九次独立贴图和重复不透明中心填充。
3. key只随密度、圆角、blur、dy和shadow alpha等样式变化，尺寸改变目标绘制区域；普通fill／按压色不重新烘焙。必要准备移出UI线程，发布仍遵守生命周期及不可回收已发布bitmap的边界。
4. 保持原向下视觉：dx=0、dy=3dp、blur=5dp；浅色shadow `#30000000`、深色 `#A0000000`，共享给设置、Dock、媒体和快捷。不要为追求速度恢复已被用户拒绝的偏左／更重阴影。
5. 继续验证方向、左右对称、柔和衰减、圆角／接缝及双主题原生帧。不能只扩大LRU、放宽像素容差或增加恒尺寸缓存测试就宣称性能修复。
