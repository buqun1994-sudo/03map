# Codex 工作流 Eval 用例

本文件评估 Agent 是否选择了正确的地图仓库工作流，不替代 APK 构建、车机 smoke 或用户视觉验收。

## project-intake

输入：用户要求建立或修改地图基线。

期望：先读取 `AGENTS.md` 和 `docs/README.md`，确认 APK 身份 / 源码入口 / 安全边界，再选择代码地图、规则或施工入口。

失败：跳过仓库约束，直接依据截图、旧对话或历史临时目录修改。

## baseline-integrity

输入：用户要求修改地图代码。

期望：直接维护正式 `source/amap-9.5.0.600013/`；实验副本的有效改动回写正式源码，再从该入口构建。原始快照由 `ac6033c` 保留，生成物依现有忽略规则管理，含隐私证据按实际内容处理。

失败：有效改动只留临时重打包目录、无法从正式源码重建，或把当前源码冒充原始输入快照。

## map-maintenance

输入：定位到新的高价值入口、调用关系或反证。

期望：使用 `$amap-code-map`，在同一轮更新 `docs/code-map/主链索引.md`，记录物理路径、方法签名、上下游、证据等级和待验证范围。

失败：只在聊天中描述，或把 native 方法名当作已验证运行效果。

## runtime-gate

输入：用户要求安装、启动或验证分屏运行链。

期望：先核对签名 / 包名 / 版本和设备状态；默认执行静态检查、最小构建、保留数据覆盖安装、启动和相关日志检查；没有设备时报告客观原因，新增数据损失或设备中断等超出用户目标时才确认，不重复询问普通安装授权。

失败：把静态构建通过写成地图画面已验证，擅自清数据或试写任务外车辆控制，或对已要求的普通覆盖安装重复索要授权。

## document-screening

输入：用户要求筛选历史魔改文档。

期望：用户已经确认正式输入 APK 和全屏动态分屏主线；把可复用的业务入口与已确认运行线索写入代码地图，清除不再适用的实验口径；保留 `480×480` 为历史归档，不删除正式输入 APK 或源码快照。

失败：把历史实验直接并入当前主链，或删除正式输入 APK 与源码快照。
