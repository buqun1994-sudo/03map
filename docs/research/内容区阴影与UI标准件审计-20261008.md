## 阴影对比结论

设置、Dock、媒体、快捷卡、竖条和来源菜单都已经消费[同一个阴影实现](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/DownwardSoftShadow.kt>)：水平偏移 0、向下 3dp、模糊 5dp，浅色 `0x30000000`、深色 `0xA0000000`。这次有界小 mask 与原生 NinePatch 修复已经覆盖上述区域。

| 区域 | 表面装配与形状 | 当前主题取值 | 对比判断 |
|---|---|---|---|
| 设置页面／组卡 | [页面](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/SettingsSheet.kt>) 12dp、[组卡](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/SettingsControls.kt>) 8dp；阴影后裁剪，再填充 | `SettingsDesign.dark` | 与其它区域共用阴影；页面、组卡、内部原子均有各自表面 |
| 设置数值滑条／色相 | [滑条](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/SettingsControls.kt>)数值条 40dp 高，阴影半径 20dp；色相 8dp | `SettingsDesign.dark` | 当前胶囊半径修正正确，形状和阴影匹配 |
| 快捷卡／竖条 | [按钮](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/QuickControls.kt>)与[竖条](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/QuickControls.kt>)均 12dp，手工串联阴影与裁剪 | Material 背景亮度 `< .2f` | 当前预设主题一致；表面装配及主题判定仍重复 |
| 媒体卡 | [媒体](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/ContentPanel.kt>)外层共享阴影，Surface 12dp，Material shadowElevation 为 0 | Material 背景亮度 `< .2f` | 单一外层阴影；封面没有额外显式阴影 |
| Dock | [Dock](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/ContentPanel.kt>)共享阴影加 12dp background；按钮保留自身按压边界 | `state.dark` | 外框与媒体同一绘制；按钮反馈属于不同产品角色 |
| 来源菜单 | [菜单](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/ContentPanel.kt>)共享阴影加 12dp Surface；选中行 8dp | `state.dark` | 行没有额外阴影；行的波纹裁剪存在独立缺口 |

原生帧中，快捷卡、Dock 与媒体的阴影方向一致。设置组卡本身也一致，但歌词页的数值条、分段、色相、色阶各有投影，因此整页的凸起密度更高。浅色白卡、灰轨道与蓝色填充，以及深色页面／卡片／轨道的对比会改变阴影的感知强度。8dp、12dp、胶囊不同轮廓也会呈现不同边缘形态，不能因此判定渲染器不统一。

[按原始像素拼接的双主题对照图](<../../apk-work/ui-components-audit-20261008.5zsxz9kh/阴影与标准件-双主题原生对照.png>)保留 1:1 裁剪。内容页使用 API34、640×1080 mdpi 的预览 fixture；设置使用实际 SettingsSheet 的 API28 mdpi 原生参考帧，裁去页面空白。fixture 不等于当前车机的功能排列，参考帧也不是本轮重新读取的 Figma 或车机截图。原图、SHA-256、裁剪坐标与两次验证报告已保存在[本机证据清单](<../../apk-work/ui-components-audit-20261008.5zsxz9kh/evidence-manifest.json>)。

阴影缓存按几何而非填充颜色或主题生成小 mask，普通大尺寸仅改变目标区域；密度、有效圆角及极小尺寸会形成新键。缓存 owner 上限为 4MiB／48 项。当前[原生阴影测试](<../../ui-preview/content-ui/src/test/java/com/icar03/content/ui/DownwardSoftShadowTest.kt#L249>)确认多次平移、颜色与主题变化复用纹理；1920×1080、141dpi 对应的 mask 小于 64KiB，warm 路径使用一次原生 NinePatch draw。该数值是阴影 mask 的有界分配，不是进程总内存或帧时间。

历史成本也支持这次修复有效。[上一实现的只读快照](<../../apk-work/ui-components-audit-20261008.5zsxz9kh/old-shadow-49ae783.kt#L68>)来自提交 `49ae783`：141dpi 下模糊、偏移或圆角为分数，旧路径会先按目标整尺寸生成 reference Bitmap，模糊完成后才压成小纹理；此前 4MiB 缓存预算只约束压缩后保留的纹理，未约束这次冷分配。

| 141dpi 的示例目标 | 旧冷生成 reference | 当前直接生成的小 mask |
|---|---|---|
| 1920×1080、12dp 圆角 | 1954×1114×4 = 8,707,024 字节，约 8.3MiB | 83×83×4 = 27,556 字节，约 26.9KiB |
| 600×120、12dp 圆角 | 634×154×4 = 390,544 字节 | 83×83×4 = 27,556 字节；与上行复用相同几何键 |
| 574×78、8dp 圆角 | 608×112×4 = 272,384 字节 | 77×77×4 = 23,716 字节 |

以上按已读源码、ARGB_8888 与 `density = 141/160` 计算，属于静态分配估算，不含分配器或 native bookkeeping，也不是进程峰值实测。当前[冷生成公式](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/DownwardSoftShadow.kt>)直接使用固定角／边跨度，消除了分数密度大目标的整尺寸模糊；填充和主题也不再造成新 mask。整数密度或本来很小的控件未必有相同幅度收益，不能外推为所有场景的帧率提升。

## 优先级与发现

优先级表示建议施工顺序。下表区分已确认的源码行为、原生回归证据和设计建议；本机通过不消除静态发现，也不证明车辆帧率。

| 编号 | 优先级 | 发现 | 证据与影响 |
|---|---|---|---|
| A01 | P1 | 快捷竖条未采最终抬手坐标，Dock 已采 | 静态出口已确认；最终 UP 跨档时可能提交不同值 |
| A02 | P1 | 填充动画在 composition 读取，与只在 draw 更新的合同不符 | 更新阶段静态确认；既有标签稳定测试通过，耗时尚未测量 |
| A03 | P1 | 滑条刻度音 Provider 范围不足；新增系统音量提交漏出静音分类 | 正式宿主静态确认；同类滑条反馈不同，拖动提交会走按钮 CLICK |
| A04 | P2 | 来源行的圆角底色没有裁剪 Ripple | 静态装配确认；按压边界可能超出 8dp 行圆角，具体像素待验 |
| A05 | P2 | 统一阴影以后，表面几何、裁剪、填充和主题取值仍手工装配 | 当前默认值匹配；后续变体修改容易分叉 |
| A06 | P2 | Dock 分档共享画法，未共享调档语义 | 快捷条可 `setProgress`，Dock 只提供按钮点击／状态 |
| A07 | P2 | 内外表面的阴影强弱缺少明确角色 | 原生帧观察及设计建议；内部投影不是已确认的规则违规 |
| A08 | P3 | 未消费的颜色别名、仅为兼容保留的 fill 参数增加维护噪声 | 静态 API 清理候选，不影响当前运行 |
| A09 | P3 | 设置规则与实际开关热区、文字行框合同有漂移 | 文档和源码／测试相互冲突，容易引导下一轮错误返工 |

### A01：最终坐标应属于通用数值交互合同

[共享竖向手势](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/QuickControls.kt>)在正常 UP 时直接 `onCommit()`；连续条和分档条提交的都是之前 `onDrag` 保存的 draft。[Dock 手势](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/DockQuickControls.kt>)先用最终 `change.position` 更新草稿，再提交。

例如最后 MOVE 在 3 档、最终 UP 已进入 2 档，快捷条仍可能提交 3，Dock 提交 2。连续数值也可能有同类偏差。正式路径由[业务适配](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/ContentPanel.kt>)到[Binding](<../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/ContentBinding.kt>)及[Store](<../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentStore.java#L1064>)透传明确目标，后续没有补采指针坐标。

建议正常 UP 先采最终坐标，再一次提交；取消、失焦、几何失效仍不写入。[既有手势测试](<../../ui-preview/content-ui/src/test/java/com/icar03/content/ui/QuickControlsNativeTest.kt#L107>)主要 `moveTo` 后 `up`；Dock 用例虽然说明最终坐标不同，仍在 UP 前 `moveTo`，不足以证明覆盖独立 UP 坐标。最小新增验证应直接改变最后 UP 的坐标并跨档，同时覆盖取消路径。

### A02：纯填充动画应只使绘制失效

[VerticalControlSurface](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/QuickControls.kt>)在组合阶段读取 `animatedFill.value` 到 `fillValue`，随后 `drawWithCache` 捕获该值。非拖动状态的 220ms 动画会逐帧进入该组合 scope，并更新 cache block；稳定分隔线／避让几何也存在重复装配路径。源代码“animated state is read only in draw”的注释与实际读取位置不符。

建议保留动画 State，在 `onDrawBehind` 内读取值，几何仍由 `drawWithCache` 按尺寸、刻度和标签 bounds 缓存。共享阴影 mask 仍能复用，这项发现不意味着每帧重新执行模糊。

本轮重跑[现有动画测试](<../../ui-preview/content-ui/src/test/java/com/icar03/content/ui/QuickControlsNativeTest.kt#L607>)，API28／34、双主题四项通过。测试证明标签内的 icon slot 组合／测量计数稳定，未计数 VerticalControlSurface 自身的组合或 draw cache 构建，因而不能证明整个 surface 只更新 draw。后续验证应直接观察该 scope 或缓存构建次数；车辆帧时间仍须单独测量。

### A03：声音属于操作类型，不能依赖业务事件漏项

[事件分发的静音分类](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/ContentPanel.kt>)包含 `BrightnessChanged` 和 `VolumeChanged`，遗漏 `SystemVolumeChanged`。同一个[ContinuousVerticalControl 业务适配](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/ContentPanel.kt>)中，通话／导航／语音音量提交后者；正式 Mapper 注册全部 SystemQuickControl。正常拖动完成会落入 `else -> true`，在事件出口播放按钮 CLICK。这与[AGENTS 的有效点击／拖动音效合同](<../../AGENTS.md#L56>)不符。

另一条独立缺口是[刻度音 Provider](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/ContentPanel.kt>)只包 SettingsSheet。快捷竖条位于其外，[正式绑定宿主](<../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/BoundContentPanel.kt>)也未在外层提供它，因此快捷竖条调用刻度音时得到[默认空回调](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/ContentClickSound.kt>)，设置却能得到实际播放器。

建议由面板根统一提供一个有生命周期的刻度音 owner，标准数值控件拥有分桶去重及操作反馈类型；普通点击继续沿现有单次 ContentClickSound。最小回归用正式 ContentPanel 的实际 Provider 位置验证新增音量类型：刻度变化有一次 tick，拖动提交没有按钮 CLICK，取消及禁用保持静音。现有注入记录器的测试不能单独验证生产 Provider 位置。

### A04：圆角背景与反馈边界应成套装配

[来源行](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/ContentPanel.kt>)用 8dp RoundedCornerShape 绘制选中背景，随后使用 Material Ripple，没有相应 `clip`。圆角 background 只改变底色形状；菜单外层 12dp Surface 只能裁菜单整体，无法裁每一行的四角。

建议该行消费公共圆角 PressSurface，将裁剪与背景、Ripple 的边界成套配置。Material Ripple 可以保留；媒体矩形 opacity＋scale、Dock 局部选中也继续保留既有 profile。当前对照图均未按压，本轮没有据此宣称 Ripple 外溢像素已复现。

### A05：公共表面需要唯一几何及主题输入

快捷、竖条、Dock、媒体、来源、设置分别手工拼 `shadow → clip／Surface → fill`；有的默认阴影圆角为 12dp，有的显式传入半径。主题也分显式 resolved mode 与背景 luminance 推断。目前预设值匹配，但新的配色或形状变体容易漏改一侧。

[SettingsDesign](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/SettingsDesign.kt>)同时将半径和由半径初始化的 shape 放入 data class。后续 `copy(cardCornerRadius = …)` 会沿用旧 `cardShape`，不会重新计算，因此存在阴影与裁剪的潜在分叉。当前[数值胶囊与色相轨道](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/SettingsControls.kt>)已经匹配，是正确例子。

建议一个轻量 SurfaceSpec 从唯一几何派生绘制、裁剪与填充，主题消费同一已解析高德 mode。现有 settings card 8dp、page／content card 12dp、数值胶囊、媒体按压边界继续作为具名变体。SettingsDesign 仍拥有设置专属间距、文字角色和蓝／绿功能色；公共标准件不需要一个包含所有业务的万能组件。

### A06：数值控件还需要共享语义入口

[快捷分档条](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/QuickControls.kt>)提供 progress range、power click 和 `setProgress`，受 gate 约束。[Dock slot](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/ContentPanel.kt>)只有 selected／stateDescription 加按钮点击；[Dock 浮层](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/DockQuickControls.kt>)复用 VerticalControlSurface 绘制，未补范围及调档语义。语义操作只能切换开关，无法直接选手动档。

建议通用数值语义适配器消费相同的范围、提交事件及可交互 gate，Dock 入口与快捷条共用。Dock 上滑呼出的触屏行为继续由 Dock 手势 owner 管理。

### A07：统一阴影强度的使用角色

现在外层组卡和内部数值条／分段／色阶等消费同一强度，歌词设置页因此比 Dock／媒体区拥有更多浮起层。原生帧能支持这个视觉观察；它不能证明内部原子阴影违规。[代码地图](<../code-map/主链索引.md>)明确登记既有原子阴影共享 renderer，[设置规则](<../product/设置页UI规则.md#L43>)的“不重复叠加容器阴影”还需要与实际角色一致解释。

建议定义少量投影角色：外层浮层、内容卡、内部轨道。保留外层主阴影，对内部轨道选择更轻或无阴影的明确 variant；不同角色仍共用小 mask renderer。具体强度属于后续视觉决策，需要用同屏原生帧比较后确定，不在本轮审计中默默更改。

### A08／A09：维护接口与文档漂移

[ContentThemeColors](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/ContentTheme.kt>)保留多个 selected／pressed 别名，而现有实际消费者刻意统一 `selectedSurface`。[既有主题测试](<../../ui-preview/content-ui/src/test/java/com/icar03/content/ui/ContentPanelRenderTest.kt#L803>)明确证明独立别名不决定当前选中面。建议删除或显式派生未消费的别名，保留产品要求的共享选中角色和 OEM 原声明功能色。[阴影的兼容 fill 参数](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/DownwardSoftShadow.kt>)当前固定返回 0，缓存不消费实际 fill／dark，可以作为小范围 API 清理候选。它是有意保留的源码兼容适配层，删除该参数没有已确认的当前性能收益。

[设置规则](<../product/设置页UI规则.md#L26>)仍写整行 toggleable，而[SettingsSwitchRow](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/SettingsControls.kt>)和现有测试明确让文字被动，仅开关扩展热区拥有点击及语义。这是文档漂移，不能据旧文字把整行改成另一个交互。规则还写行框“不 trim”，[实际文字样式](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/SettingsDesign.kt>)使用 Trim.Both 与固定行框；应同步准确解释字号／行高如何进入布局，避免重复修正已经固定的几何。

## 标准件的最小分层建议

已有通用 Continuous／SteppedVerticalControl、Dock 业务适配和 SteppedControlScale 应继续承担职责。建议补齐表面与操作合同，业务事实仍沿 Store → Snapshot／Mapper／Binding → UI；标准件只消费 value、range、enabled 和回调。

|---|---|---|
