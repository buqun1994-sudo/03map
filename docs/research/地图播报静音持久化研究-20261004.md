# 地图播报静音持久化研究（2026-10-04）

> **职责：** 记录高德 9.5 右上角播报菜单的静音保存／恢复链、设置页的区别、修复落点和验证边界。业务入口汇总在[主链索引](<../code-map/主链索引.md>)。本轮为研究，没有修改应用源码、构建或安装新 APK。

## 1. 问题与结论

用户报告：右上角可选“智能、详细、简洁、极简、静音”；选择静音后当次没有播报，车辆再次上电后浮窗不再保持静音。设置页的“导航播报”“巡航播报”均为关闭。

**最有证据支持的恢复失配位置：浮窗静音改变运行时普通静音，已追踪的实际点击链没有把用户选择写回 `mute` 配置；重新初始化则从配置或系统同步源重建状态。** 播报风格有独立的 `PlayStyle` 配置写回。五个可见选项不是同一份五值枚举。

另有明确的条件覆盖路径：导航组件初始化时，若 `StartNaviCancelMute=1` 且当前静音，会执行 `SetMute(false, observer4)`。本轮没有读到车机该配置的实际值，不能把它直接认定为这辆车每次上电时的唯一原因。

修复方向应是补齐**用户普通静音偏好的及时保存与启动恢复**，并让**导航初始化尊重这份偏好**。所查 observer 和 GAI 路径尚未穷尽，磁盘后端／当前配置值／实际上电顺序仍未闭合；不能把“已定位链未保存”扩大成“全应用绝不保存”或“已实机证明每次上电强制取消静音”。

| 结论 | 证据等级 | 限定 |
|---|---|---|
| 五个选项由四种播报风格和独立普通静音组成 | 静态确认 | 已定位 native 点击入口和消费者，不只依赖文字资源 |
| 实际浮窗静音 adaptor 只调用 `SetMute`，没有配置写回 | 静态确认 | 已核查点击链、音量 setter、两个 UI observer 与 `SaveData`；未穷尽全部 native observer／GAI 回调 |
| 音量初始化从配置或系统同步源重建普通静音，对象初值为 false | 静态确认 | 当前车机 `mute`、同步参数、磁盘值未取得 |
| `StartNaviCancelMute=1` 可在导航组件初始化取消普通静音 | 静态确认 | 配置读取成功、值为 1、当前静音三项条件；不是无条件应用启动行为 |
| 清除临时静音不会清除已开启的普通静音 | 静态确认 | native `SetTempMute` 在普通静音开启时直接返回 |
| 用户所述两个“关闭”项的确切控件／字段 | 待验证 | 设置页有风格单选、自动巡航开关、内容复选等多层控件；本轮未取得稳定的该页画面 |
| 真实再次上电时哪个恢复／覆盖路径触发 | 待验证 | 本轮未重启车辆／车机、强停地图或改变播报偏好来复现 |

## 3. 代码链

### 3.1 右上角风格与静音

[地图 UI 库](<../../source/amap-9.5.0.600013/lib/arm64-v8a/libautonavi.so>)部分符号被剥离。下列 UI 方法由实际日志字符串交叉引用、函数边界和调用指令确认；objdump 显示的最近导出符号（例如 `getUserInfoVersion`）不是这些方法的业务名。

| `hmi::CDetailVolumeComponent` 方法 | VA | 实际消费 |
|---|---|---|
| `OnClickSmartTts(CGView*)` | `0xa081a0` | `0xa08458` 写 `PlayStyle=3` |
| `OnClickDetailTts(CGView*)` | `0xa0a1f0` | `0xa0a3d4` 写 `PlayStyle=1` |
| `OnClickSimpleTts(CGView*)` | `0xa09cc0` | `0xa09e9c` 写 `PlayStyle=0` |
| `OnClickVerySimpleTts(CGView*)` | `0xa09788` | `0xa0996c` 写 `PlayStyle=2` |
| `OnClickMuteTts(CGView*)` | `0xa09460` | `0xa09548` 调用 `VolumeBarOnClickedOff`，没有写 `PlayStyle=4` |

前四者调用 `Config::SetInt32("PlayStyle", value, SetterType1)`。键的前八个 UTF16 字符 `PlayStyl` 在 `0x2f8906`，构造指令补 `e`；不是凭方法名推断数值。最终磁盘提交和 SetterType 的完整后端语义未在本轮闭合。

静音调用闭环：

```text
OnClickMuteTts                         0xa09460
  → VolumeBarOnClickedOff              0xa0b000
  → this+0x208 的 vtable+0x10           0xa0b32c
  → CGSceneVolumeBarAdaptor 静音回调    0xa0cd4c
  → GetVolumeNotifyHandle              0xa0cd5c
  → SetMute(newMute, observer0)         0xa0cd68
```

`VolumeBarOnClickedOff` 在 `0xa0b320` 算出 `newMute=!currentMute`。最后一个虚调用由 RTTI／vtable 核对：创建入口 `0xa077a0`，`0xa077f4` 设置 vptr `0xe03c38`，`0xa079d0` 把 adaptor 放入组件 `this+0x208`；重定位 `0xe03c48` 指向 `0xa0cd4c`。RTTI 名 `N3hmi23CGSceneVolumeBarAdaptorE` 在 `0x373470`。该回调完整范围 `0xa0cd4c–0xa0cd7c` 仅获取 handle、设置运行时静音、返回成功，没有 `Config::SetBool` 或文件写入。

[音量业务库](<../../source/amap-9.5.0.600013/lib/arm64-v8a/libhsl.so>)的状态与恢复边界：

| 方法 | VA | 已确认行为 |
|---|---|---|
| `UtilVolumeNotify` 构造 | `0xcd6c50` | 普通静音 `this+0x131`、临时静音 `this+0x132` 初值均为 false |
| `UtilVolumeNotify::Init()` | `0xce0654` | 调用 `InitSoundLevel()` |
| `UtilVolumeNotify::InitSoundLevel()` | `0xcdd974` | 先读 `isAudioStreamCustomSync`；false 时在 `0xcddc34` 调用 `GetBool("mute", this+0x131, strategy0)`；true 时改走 `GAI_SysVolumReq` 系统同步源 |
| `UtilVolumeNotify::IsMute() const` | `0xcd84cc` | 读取普通静音 `this+0x131` |
| `UtilVolumeNotify::SetMute(bool, EVolumeObserverType_)` | `0xcd84d4` | `0xcd85b4` 写普通静音内存，通知 GAI、observer 和状态；本体没有配置 setter |
| `UtilVolumeNotify::SaveData(bool)` | `0xce12a8` | 完整范围到 `0xce13f4`，只做日志等操作并返回 true，没有保存指令 |
| `UtilVolumeNotify::SetTempMute(bool)` | `0xcd86b8` | `0xcd8734` 先读普通静音，为 true 时直接返回，只有 false 时才更新临时静音 |

普通静音读键内容在 `0x1c9448`；同步键在 `0x2c2f44`。冷初始化不是从旧对象继续，也不是无条件清零，而是从配置或系统同步源重建。

不能把“有 observer”当作已保存。在[地图 UI 库](<../../source/amap-9.5.0.600013/lib/arm64-v8a/libautonavi.so>)中，`CVolumeNotifyModel::OnVolumeChange` 的完整范围 `0xbb2394–0xbb26e4` 确有 `SetBool`，但 `0xbb2544` 写的是 `isShowResetToast=false`，不是 `mute`；键在 `0x30170c`。另读取 `isShowMuteToast`，属于提示 UI。所追踪的两个 UI observer 没有补上用户静音保存；全部 native observer／GAI 的外部效果仍保留调查边界。

### 3.2 导航初始化主动取消普通静音

[地图 UI 库](<../../source/amap-9.5.0.600013/lib/arm64-v8a/libautonavi.so>)的 `hmi::CNaviComponentBase::InitCancelMute()` 位于 `0xc0f6d0`：

1. `0xc0f73c` 读取整数配置 `StartNaviCancelMute`，UTF16 键在 `0x2f4d88`。
2. 读取成功且值为 1，才继续取得当前静音状态。
3. 当前静音为 true，才在 `0xc0f794` 调用 `SetMute(false, observer4)`。
4. 唯一找到的直接调用点 `0xc0ea04` 属于 `CNaviComponentBase::Init()`（起点 `0xc0e904`），并有 `this+0x1999` 的一次性门禁。

这条路径应在恢复导航／创建导航组件时观察，不能写成“所有启动都无条件清静音”。当前车机是否启用该参数，未取得运行值。

另一条配置应用候选在[音量业务库](<../../source/amap-9.5.0.600013/lib/arm64-v8a/libhsl.so>)的 `0x8f5af8`：查询 `ConfigKeyMute` 编号 609 后调用 `SetMute(value==1, observer6)`。实际 owner 与启动顺序未闭合，只作为定位初始化／覆盖的下一跳。

### 3.4 设置页与插件

[本体帮助](<../../source/amap-9.5.0.600013/assets/res/HmiRes/broadcast_day.txt>)第 2 行明确有“设置→声音播报→导航播报→简洁播报”。实际消费在[原生设置库](<../../source/amap-9.5.0.600013/lib/arm64-v8a/libCommon.so>)：

- `CGSettingBroadcastStyleBizView::onCheckedChanged` `0xa60e00` → `saveConfig(int)` `0xa60e70` → `0xa60ed8` 调用 `SetInt32("PlayStyle", value, SetterType1)`；键在 `0x6ed37a`。
- `getCheckedRadioId()` `0xa60ff4` 同键 `GetInt32`。
- 四档智能版 `CGSettingBroadcastStyleIntelligentBizView::onCheckedChanged` `0xa61aa8` → `CGSettingRadio4BasedBizView::saveConfig` `0xa61758`，同样写 `PlayStyle`。

这里只确认配置写回／读回，未把 `saveConfig` 或 `SetInt32` 方法名当作掉电持久化实测。

[本体 UI 资产库](<../../source/amap-9.5.0.600013/lib/arm64-v8a/libcmb_Common.so>)实际控件串 `0xa53569`（重复 `0xac2a20`）同时含导航风格单选 `cbr_navi_broadcast`、自动巡航开关 `cbs_auto_cruise_broadcast`、巡航内容复选 `cbc_cruise_broadcast_first/second/third`。仅凭标题和“关闭”不能认定它们等于全局 `mute`。`cruise_mute`／`OpenAutoEnterCruise`／`Camera`／`traffic` 的 native 字段字符串只是后续候选，尚未与用户所述两项关闭逐一闭环。

正式[插件初始化](<../../source/amap-9.5.0.600013/smali/com/autonavi/amapauto/chenmo_float/ApplicationInitialization.smali>)只注册生命周期和窗口广播，未发现 `ttsSettings`／`GuideRoad`／`CruiseRoad` 自定义模块。已有交通灯插件调用[ttsService](<../../source/amap-9.5.0.600013/smali/floatapp/tts/ttsService.smali>)的 `e()`，封装 `protocolId=80082`，通过本包 `JsonProtocolService` 和 `nativeRecvJsonAsync` 进入统一引擎；native `GOTHERProtocolAlToHmi::TTStextforAutoAlToHmi` `0xc359c4` → `VRGuideImpl::PlaySoundRespRcvCb` `0x9fd114` → `UtilVolumeNotify::PlayTextById(mode1)`。尚未验证这个 mode 的全部静音条件，不能宣称插件绕过全局静音，也没有证据把它作为浮窗状态丢失的原因。

## 4. 最小修复方案（待施工）

建议保留现有菜单与播报引擎，在普通静音 owner 上修复：

1. **保存用户选择。** 右上选择静音／解除静音时立即提交持久偏好；风格 `PlayStyle` 与普通静音分开保存，保留最后一个非静音风格。不依赖退出、断电前回调或空的 `SaveData()`。最接近用户意图的落点是实际 `CGSceneVolumeBarAdaptor` 静音回调；如选 Java bridge，要先解决状态回调的来源区分。
2. **启动恢复同一份偏好。** 配置和系统同步初始化完成后、允许第一条地图语音前恢复普通静音；图标／选中态和引擎共用状态。先核实现有 `Config("mute")` 的存储层／提交方式并优先复用；需要 Java 适配时只保留一个 owner。若 `isAudioStreamCustomSync=true`，要处理系统同步回流，不能只补本地配置读取。
3. **导航初始化尊重偏好。** 读取 `StartNaviCancelMute` 实际配置；若现场确认其覆盖用户静音，关闭适用配置或在已保存用户静音时跳过自动取消。来电等仍走现有临时通道，用户主动改选有播报应立即生效并保存。
4. **核对设置页语义。** 实际对照两个关闭控件再明确内容／场景与全局静音的关系，避免把自动巡航、风格单选或内容复选误合成全局开关。全局静音对地图播报的优先级应一致。

本轮没有修改原生库。后续 native 施工须以固定 SHA 和函数边界建立可重建、可核验方式；Java 接入也须在正式源码证明就绪与意图契约。只改图标、每次 `onResume` 强制静音或把所有 `SetMute` 调用自动保存，都不能正确表达用户偏好：它们会混入初始化、协议命令和条件覆盖。

## 5. 验收与剩余证据

施工时补最少状态证据，区分“未保存”与“保存后覆盖”：用户动作、持久偏好、配置／系统同步初始化完成、普通静音回读、导航初始化、状态回调和请求来源。只记录状态与原因，不记录位置／路线／账号。

| 场景 | 必须结果 |
|---|---|
| 选择静音后直接结束进程，再冷启动 | 首条地图语音前普通静音为 true；菜单保持静音；不依赖正常退出 |
| 真实下电后再次上电 | 与上一项一致，并检查初始化／外部协议是否随后写 false |
| 前后台、Activity 重建、地图收放 | 静音不丢失，偏好不被初始化回调重写 |
| 启动／恢复导航 | 自动取消路径不能覆盖已保存用户静音 |
| 静音后改选四种有声风格 | 当次恢复相应播报，下一次冷启动保留新的非静音选择 |
| 来电或外部导航触发临时静音并恢复 | 普通用户偏好保持，临时状态不保存成长久偏好 |

## 6. 用户开始修复后的后端闭合（2026-10-04）

前文第4／5节保留原研究轮次的待施工与未构建事实。用户随后要求开始修复，实际源码、签名包、回归和设备边界由[修复验证记录](<../testing/地图静音持久化修复验证记录-20261004.md>)维护，不把前轮未修改结论套到当前实现。

`Config::SetBool`在[libhsl](<../../source/amap-9.5.0.600013/lib/arm64-v8a/libhsl.so>)的VA `0x6008dc`，只是包装。`this+0x2a0`来自[libturbo](<../../source/amap-9.5.0.600013/lib/arm64-v8a/libturbo.so>)的`Loader::getFuncConfig`，后端RTTI为`turbo::TurboConfig`，vptr `0x39b20`；SetBool slot+0x90指向 `0x320b8`。若功能map `this+0x250`或路径map `this+0xf0`含同名键，立即返回false；否则要求用户KeyStorage `this+0x390`已启用（flag `this+0x3f8`），写字符串1／0到用户map `this+0x400`。无额外用户键白名单，键由存储深复制；SetterType1不绕过保护层。原`mute`是否在当前加密OEM配置中被保护仍未读出，因此实现采用一个明确用户键作为唯一显式意图，原合并mute仅保留默认用途。

`GetUserConfigBool` body `0x60028c`／PLT `0xd2f290`，backend slot+0x170 → `0x32fe8`，只读用户map。必须同时检查found和outbool，缺键out也为false。合并`GetBool`优先级为功能→用户→默认UI→路径，包装还可有临时override；合并读取不能证明来自用户层。

SetBool仅接受RAM变更并通知dirty，不能代替文件提交。`Config::SaveData(bool)` `0x60e768` → `SaveByBinary()` `0x6081e8` → backend slot+0x150／`0x32da4` → 用户存储 `0x1783c`：serialize、AES、openFile4Write(temp) `0x17ed8`、writeData `0x18078`、flush `0x18084`、可选sync `0x18114`、close、renameFile(final) `0x180a8`。写出长度正确且rename成功才返回true并清dirty；首rename失败有删除旧final后再次rename的原后端路径。本函数没有用传入bool控制sync，其内部flag未现场读取，未逐项检查flush／sync／close返回，也未见rename后目录fsync。返回true不是任意瞬断下抗掉电实测。

正确String16构造使用既有`Encoding::CharToString16` body `0x776474`／PLT `0xd2bcb0`：x0=NUL UTF8键，x8=&8字节结果对象；工厂分配并深复制UTF16 buffer，使用结束由原delete[] PLT `0xd2b040`释放一次。不用临时UTF16 header伪造长期key。SetBool的ABI是x0=Config*、x1=&String16、w2=bool、w3=1；GetUserConfigBool的x2为bool输出地址；保存返回均检查低位。

已额外确认后续系统同步：`OnVolumeInfo()` `0xcd89fc`的 `0xcd8ba4`调用 `SetMute(currentVolume==0,observer2)`，`0xcd8bb4`调用同值SetTempMute。因此仅初始化末恢复一次仍会被非零媒体音量清除。`InitSoundLevel`当前库直接BL调用仅找到 `Init()`的 `0xce0854`指向PLT `0xd3b2d0`；其它库／虚调用及首次播报时序仍需实际候选验证。正式修复只标记菜单意图，不把所有原SetMute调用保存。
