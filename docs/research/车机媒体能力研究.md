# iCAR 03 车机媒体能力研究

> **职责：** 唯一车机能力证据台账，也是正式车控适配器的当前研究输入。本文记录原始观察、源码入口、运行结果和权限边界；产品文档定义用户可见范围，架构文档定义 Port / Adapter 边界，二者只引用这里的结论，不复制属性编号、Binder 事务或完整日志。
>
> 本文包含媒体会话、媒体来源、标准控制、车机媒体键、充电、档位、温度、天气、座椅、除霜、车门锁和方向盘加热研究。方向盘加热的本轮四态只读现场对照、自动状态与厂商数值转换见第 18 节；前雨刮六态HAL对照、普通第三方直接读取、读写不同编码及三档五秒控制／恢复自动的用户确认见第 19 节。车门锁及第 17 节的普通第三方 APK Binder 结果是当前固件已验证的车控适配输入，不是仅供历史参考；正式地图 APK 仍需逐项完成 Adapter、状态回流和 UI 闭环。后续研究记录日期、用户目标、实际动作、状态回读、恢复结果和适用范围。具体个人风险与已有授权见 [安全与密钥边界](../security/安全与密钥边界.md)；文中 P / 零速和逐操作确认保留当时探针事实，不作为后续限制。后雨刮609同一value2两次发送的开启／停止闭环、后窗洗涤610的触发与自动复位、失败候选及正式地图未接入边界见第22节。

## 1. 研究范围

研究日期：2026-09-24；车辆充电数据补充研究：2026-09-25；档位、温度与天气补充研究：2026-09-26；充电枪插入未充电与预约充电等待补充研究：2026-09-27；宠物模式温度和档位映射核对：2026-09-27；座椅通风状态与设置链、主驾座椅按摩、主驾座椅加热三档、前后风挡加热（除霜）以及车门锁获取与设置研究：2026-09-27；普通第三方 APK 对温度、电量、剩余里程、充电状态和三项座椅控制的 Binder 实机研究：2026-09-28。

目标是验证第三方应用在当前 iCAR 03 车机上是否能够：

1. 读取并展示当前媒体的标题、歌手、专辑、播放状态和进度。
2. 主动切换蓝牙音乐、U 盘音乐、本地音乐、爱趣听和网易云音乐。
3. 控制当前媒体暂停、恢复播放和下一首。

本轮通过临时诊断 APK 进行应用进程内验证。通知监听授权由 ADB 完成，按本任务约定不把授权本身作为阻断条件；设备地址、完整日志、截图和 APK 均保留在仓库外临时目录，没有进入仓库。

### 1.1 车控研究目标与路线选择原则

本项目的车控研究目标是：在当前 iCAR 03 车机上，使用**普通第三方 APK**，在用户允许的 ADB 安装、启动、权限授予、组件调用和日志取证条件下，实际读取或设置车辆目标状态。研究对象是“能否达到车控目的”，不是“能否通过某一条预设 API”。

1. 普通第三方 APK 指非系统 UID、非车机原厂签名、通过 ADB 安装运行的独立应用；不能因为它不是系统应用，就预先判定车控不可行。
2. 按用户研究目标比较标准 `CarPropertyManager`、车机导出的厂商服务 / Binder、显式组件、广播或其它可由 APK 直接调用的车机接口；只要最终形成“请求 → 车辆状态变化 → 状态回读”的闭环，接口路线不设限。
3. ADB 权限边界是研究条件，不是正式产品运行依赖：可以用 ADB 安装、启动、授予平台允许授予的权限、调用导出组件和采集日志；当前正式适配路线是设备内服务 / Binder；其它技术路线按目标、兼容证据和具体风险评估，不按名称禁止研究。
4. 某条链路失败只能记录为该链路的权限或兼容性边界，不能直接升级为“普通第三方 APK 无法车控”的总判断；应继续检查其它已存在且可授权的车机入口。
5. 成功标准必须包含实际状态回流和可逆恢复；仅有“调用返回成功”、静态源码存在或属性目录可见，不足以写成车控已实现。

## 2. 结论摘要

| 能力 | 蓝牙音乐 | 爱趣听 | 网易云音乐（当前 03 上的 03T APK 移植版） | U 盘 / 本地音乐 |
| --- | --- | --- | --- | --- |
| 第三方应用读取并展示 | 可以 | 可以 | **当前标准 MediaSession 路径不可可靠读取** | 当前无可播放内容，未形成有效媒体会话 |
| 第三方应用直接暂停 / 恢复 | 可以 | 可以 | 当前不可证实为可控，实测未生效 | 无内容，无法验证 |
| 第三方应用直接下一首 | 可以 | 可以 | 当前不可证实为可控，实测未生效 | 无内容，无法验证 |
| 第三方应用主动切换来源 | 可以 | 可以 | 可以 | 服务调用可达；无曲目时画面不切换 |

结论不是“网易云功能不存在”：当前系统的 `CloudMusicService` 能在车机系统层生成播放状态和歌曲元数据，也能被多媒体中心切入；问题是这条会话在 iCAR 03 当前移植组合中没有按标准可控 MediaSession 对第三方应用公开。

### 2.2 首轮内容区施工的接入边界（2026-09-27）

1. 充电相关、`HVAC_IN_OUT_TEMP`、座椅通风、座椅加热和座椅按摩已经完成车机侧研究，当前形成的是正式适配器的字段 / 编码锚点；正式 `com.autonavi.amapautolite` 的属性可见性、权限、持续订阅和写入闭环仍未完成。

5. 后续接入真实能力时，只替换车辆 / 媒体适配器和命令端口；`ContentStore` 的快照 owner 与 `ContentRenderer` 的渲染链不改。

## 3. 读取媒体信息

### 3.1 已验证可用的应用链

第三方应用在获得通知监听使用权后，可以通过：

1. `MediaSessionManager.getActiveSessions(ComponentName)` 枚举系统公开会话。
2. `MediaController.getMetadata()` 获取标题、歌手、专辑和时长。
3. `MediaController.getPlaybackState()` 获取播放 / 暂停、位置、速度和支持操作位。
4. 应用自己的 Activity 将上述字段展示在界面中。

实测结果：

- 蓝牙会话为 `com.android.bluetooth/A2dpMediaBrowserService`，可展示《姑娘在远方》、歌手 `Li`、专辑和播放状态。
- 爱趣听会话为 `com.tencent.wecarflow/MusicService`，可展示当前歌曲、歌手、播放状态、位置和队列大小。
- 探针界面已在车机上实际显示蓝牙歌曲标题、歌手、专辑、时长、播放状态、进度和操作位；不是只根据 `dumpsys` 文本推断。

### 3.2 当前网易云的特殊情况

切入网易云后，系统 `dumpsys media_session` 可以看到：

- 会话：`com.tencent.wecarflow/CloudMusicService`。
- `active=false`。
- `state=PLAYING`，并且有歌曲标题、歌手和歌词型描述文本。
- `actions=0`。

但第三方探针通过公开 `getActiveSessions` 获取到的只是 `com.tencent.wecarflow` 的无元数据 / 无播放状态候选，无法稳定拿到 `CloudMusicService` 那条带歌曲数据的会话。探针还检查了现有媒体通知，没有发现可用于构造该会话的标准 `EXTRA_MEDIA_SESSION` Token。

因此要区分两层事实：

- **系统层可见：** 网易云会话确实产生了状态和元数据。
- **第三方应用标准 API 可见：** 当前 03 上不可靠，不能直接按蓝牙 / 爱趣听的方式承诺。

这与“03 上的网易云是从 03T 多媒体中心 APK 提取后覆盖安装”的背景一致，优先判断为移植后的会话生命周期或能力声明不完整；这是当前组合的兼容性问题，不应泛化为标准 iCAR 03T 或其他网易云版本的结论。

### 3.3 蓝牙零位快照、实际事件与只读 Binder 候选（2026-10-02）

本轮同机同时运行的03歌词可以滚动，而地图首候选不能。普通进程的标准 `com.android.bluetooth` 会话持续报告 `state=3, position=0, speed=0`，仅 `updated` 更新不能当作位置推进；这也不能推导固件没有其它进度入口。系统实际广播注册/历史投递显示，两应用都收到 `PLAY_STATUS` / `TRACK_EVENT` 等当前固件事件。地图原先额外要求来源Binder回读明确为蓝牙，在来源服务未绑定时拒绝了已合法选定的蓝牙会话事件；同时仅TRACK读取Android语义的 `profile.extra.PLAYBACK`。正式 `ContentMediaAdapter` 已对齐03歌词实际decoder和已选来源规则，保留来源/token/录音/曲长/生命周期隔离。修正包实际位置连续推进，歌词当前句与同时运行03歌词对应，切歌封面与正文更新；证据和包身份见[本轮验证记录](../testing/Lyrimuse国内歌词车机适配验证记录-20261002.md)。这些AVRCP名称属于已验证固件实现，不是Android9公开SDK通用契约。

普通UID绑定可导出的服务、注册只读Binder回调同样适用于媒体，无须将第17节的车辆属性号或车控事务套到音乐上。已核验原厂 `IPlayControlsInterface` 的事务1/2注册/注销、事务6读取来源；`IPlayInfoCallBack` 的事务3明确读取两个long并调用 `onCurrentPlayMediaProcess(currentProcess, totalProcess)`，原厂包装器直接转发，`PlayMediaInfo` 本身没有进度字段。当前地图来源callback只消费1/2/4、尚未消费3，因此这里是后续只读进度候选。必须在当前服务可绑定后独立确认两个值的单位、暂停、切歌重置、回调频率及同来源/录音关系，才能作为真实位置发布；本次不把静态接口存在写为现场可用。已验证广播已解决当前蓝牙滚动，本轮未新增控制事务或为了补齐候选另行占用车机。

## 5. 直接媒体控制

### 5.1 蓝牙音乐

第三方探针对 `com.android.bluetooth/A2dpMediaBrowserService` 的 `MediaController.TransportControls` 逐项执行：

1. `pause()`：会话状态从 `PLAYING` 变为 `PAUSED`。
2. `play()`：会话状态恢复为 `PLAYING`。
3. `skipToNext()`：歌曲从《空城》切换到《姑娘在远方》，元数据发生真实变化。

结论：蓝牙暂停、恢复、下一首均可行。

### 5.2 爱趣听

第三方探针对 `com.tencent.wecarflow/MusicService` 逐项执行：

1. `pause()`：状态变为 `PAUSED`，位置冻结在当前曲目。
2. `play()`：状态恢复为 `PLAYING`。
3. `skipToNext()`：歌曲从《哪凉快哪去 (Live)》切换到《夜曲》，元数据发生真实变化。

结论：爱趣听暂停、恢复、下一首均可行。该会话在播放时报告 `active=true`、`flags=7` 和非零操作位，与可控结果一致。

### 5.3 当前网易云移植版

对 `CloudMusicService` 做了两类直接控制尝试：

- `TransportControls.pause()` / `play()` / `skipToNext()`。
- 绑定到第三方可见的无状态候选会话后调用 `dispatchMediaButtonEvent`。

实测均没有让 `CloudMusicService` 从 `PLAYING` 变为 `PAUSED`，也没有让歌曲切换；发送前后 `actions=0`，播放位置继续递增。这不是全局媒体键不可靠造成的假阴性，而是当前移植会话本身未向第三方暴露可执行控制能力。

因此当前 iCAR 03 组合下不能承诺第三方通过标准 `MediaController` 控制网易云。若产品必须控制网易云，需要另行确认 03T 原车 APK / 服务版本的会话实现，或由车机侧修复其 `CloudMusicService` 的 active 状态、操作位和回调链；不能仅凭“切源成功”推断“可暂停 / 下一首”。

### 5.4 方向盘 / 系统媒体键路径

本轮额外把网易云切到当前来源后，记录了系统媒体键路径，而不是调用第三方控制器：

1. 切源后 `dumpsys media_session` 显示 `Media button session is com.tencent.wecarflow/CloudMusicService`，但该会话仍为 `active=false`、`actions=0`、`state=PLAYING`。
2. 发送一次系统级 `KEYCODE_MEDIA_NEXT`（`adb shell input keyevent 87`）后，`CloudMusicService` 的歌曲从《至少还有你》切换为《IS IT LOVE》，元数据和播放位置都发生了真实变化。
3. 同一会话的 `mediaButtonReceiver` 指向 `com.tencent.wecarflow/.media.service.MediaButtonIntentReceiver`；包组件解析表也声明了该 Receiver 接收 `android.intent.action.MEDIA_BUTTON`。
4. 车机日志同时出现 `CloudMusicService: updatePlaybackState:playState=PLAY`、`isSkipToNext=1` 和网易云内部来源 `source=10`。外部多媒体中心切源参数 `audio_source=9` 与内部媒体来源编号不是同一套编号。

这解释了“第三方标准控制失败，但方向盘下一首有效”的表面矛盾：

- `TransportControls.skipToNext()` 依赖目标会话发布的 `PlaybackState.actions` 和控制回调；当前网易云发布 `actions=0`，所以第三方控制器调用没有效果。
- 方向盘按键很可能经车机输入 / 媒体键分发链路进入 `MediaButtonIntentReceiver` 或车机内部媒体分发，再由 `CloudMusicService` 执行下一首；这条路径不以 `actions=0` 作为阻断条件。
- 本轮的 `adb shell input keyevent 87` 是对系统媒体键接收链的可重复触发，不等同于已经抓到方向盘的物理 CAN 信号；但它与用户确认的方向盘“下一首”结果一致。当前没有把“系统媒体键可切下一首”外推为“系统媒体键暂停也已通过”，暂停仍需单独取证。

所以，`active=false` 只说明该会话在标准活动会话排序中的发布状态异常，不等于车机内部完全没有播放控制路径；`actions=0` 也只否定当前标准 `TransportControls` 能力，不能否定方向盘 / 系统媒体键路径。

## 7. 与既有研究的关系

既有 `03desktop` 研究已经验证普通应用直接发送全局媒体键不能可靠控制当前会话。本轮把这个结论细分为两条路径：

- 普通第三方应用的会话级 `dispatchMediaButtonEvent` 和全局媒体键不能作为通用方案；当前网易云的标准会话控制仍失败。
- 车机系统级媒体键 / 方向盘输入可以通过 `MediaButtonIntentReceiver` 进入当前来源；当前已对网易云的“下一首”取得真实元数据变化证据。
- 在通知监听使用权已由 ADB 配置的前提下，标准 `MediaController.TransportControls` 对蓝牙和爱趣听可用。
- 是否可控取决于目标媒体服务是否正确发布活动会话、操作位和回调，权限不是唯一决定因素。

## 8. 后续集成建议

1. 媒体信息读取层优先采用 `NotificationListenerService` + `MediaSessionManager`，并把会话包名、元数据、播放状态和操作位作为可观测字段。
2. 媒体控制层按会话能力位判断：只有存在有效 `PlaybackState` 且对应操作位时才显示可控按钮；不要把全局媒体键当作可靠回退。
3. 来源切换单独封装为当前固件适配器，使用 `MediaCenterPlayService` 的显式 Intent；切换后必须重新枚举会话，不能复用旧控制器。
4. 网易云要把能力拆成两层：标准 `MediaController` 的暂停 / 下一首当前不可用；车机系统媒体键的“下一首”已取得证据，但不能把它等同为普通第三方 API，也不能据此宣称暂停已可用。
5. 如果后续产品确实允许接入车机系统媒体键，应把它单独定义为车型 / 固件适配器，并记录输入事件前后歌曲元数据变化；不能让 `active=false` 或 `actions=0` 单字段直接覆盖这条系统级能力判断。

1. **厂商快充 / 慢充枚举：** 车机配置了 `INFO_EV_CONNECTOR_TYPE`（`0x11410107`），但本次快照没有该属性的缓存事件；`VENDOR_BMS_CHARGE_STS=3` 仍只能作为厂商状态码记录，不能把它单独解释成类型枚举。
2. **剩余时间单位：** 早先的 `519` 和特殊值 `2047` 尚未有厂商定义；本次充电会话中原始值从 `62` 变为 `61`，并且 SOC 持续上升，强烈符合“剩余分钟数”的表现，但仍保留 `2047` 为特殊值 / 无效值处理边界。
3. **直接充电功率字段：** `EV_BATTERY_INSTANTANEOUS_CHARGE_RATE`（`0x1160030c`）本次仍没有缓存事件；`VCU_INST_POWER_CONSUM`、`VCU_TOTAL_POWER_DISPLAY` 和 `VCU_INST_POWER_DISPLAY` 仍不能作为直接充电功率字段。车机已经提供足够的高压电压和电流，可由 `P≈U×I/1000` 实时计算有效充电功率。
4. **应用层权限：** 本轮证据证明车机内部 Vehicle HAL / `CarPropertyService` 能产出这些属性，不等同于普通第三方 APK 已经可以通过 `CarPropertyManager` 直接读取；应用层权限和订阅闭环未测。
5. **预约状态枚举：** 用户明确处于“预约充电等待”时，`VENDOR_BATTERY_BOOKCHG_STATE=1` 与 `VENDOR_BMS_CHARGE_STS=6` 同时出现；当前没有厂商枚举表，也没有切换到其它预约状态的对照，暂只能称为本车型本次运行锚点。
6. **无预约的插枪未充电状态码：** 2026-09-27 的第一组“插枪但没充电”快照中，连接字段有 `1`，但 `VENDOR_BMS_CHARGE_STS` 和 `VENDOR_BATTERY_BOOKCHG_STATE` 均未形成缓存事件；事件缺失不能解释为数值 `0`，还需要一次从无预约状态到插枪状态的事件级复核。

另有 `VENDOR_BATTERY_VOLT`（`0x2160031f`）读到约 `14.1`。它与高压 BMS 电压字段分离，按数量级应视为低压辅助电源相关数据；不能把它当作动力电池电压或充电桩电压。

### 10.4 充电状态对照与结论

以下样本统一使用连接字段、BMS 充电状态、预约状态、SOC 和高压电流交叉判断，不把单个能量流或单次缺失事件当作完整状态码。

### 10.4.1 第二次充电会话的快速判定

车辆再次充电期间已抓到连续四次只读快照：

| 采样 | SOC | 高压电压 | 高压电流 | 电压 × 电流估算功率 | 剩余时间原始值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 首次快照 | `59.3%` | `393 V` | `183.2 A` | 约 `72.0 kW` | `62` |
| 连续采样 1 | `63.89%` | `394 V` | `184.8 A` | 约 `72.8 kW` | `61` |
| 连续采样 2 | `64.05%` | `394 V` | `184.0 A` | 约 `72.5 kW` | `61` |
| 连续采样 3 | `64.21%` | `394 V` | `185.2 A` | 约 `73.0 kW` | `61` |
| 连续采样 4 | `64.38%` | `394 V` | `183.9 A` | 约 `72.5 kW` | `61` |

同时读到 `VENDOR_CHARGE_PORT_CONNECTED=2`、`VENDOR_BMS_CHARGE_STS=3`、`VCU_ENERGY_FLOW_SHOW=8`，且 `EV_BATTERY_LEVEL` 从 `59.3%` 持续升至 `64.38%`。因此，本次实际充电会话可以确定为**高功率直流快充**：车机侧没有直接公开可命名为“快充”的类型枚举，但约 `72–73 kW` 的高压充电电气量已经足以与此前约 `5.85 kW` 的低功率充电样本区分。`VENDOR_CHARGE_PORT_CONNECTED=2` 是本次会话的连接状态原始值，不在没有厂商枚举表的情况下单独宣称其数值含义。

本次样本还证明了两点：`VENDOR_BMS_CHGREMAIN_TIME` 的 `62→61` 与充电进度同步，产品侧可以暂按“分钟”显示并将 `2047` 视为未知 / 特殊值；直接功率字段虽然没有事件，但用同一时刻的高压电压 × 高压电流即可得到约 `72–73 kW` 的实时有效功率。

### 10.4.2 两类“已插枪但未充电”状态对照

2026-09-27 先在用户明确的“插入充电枪但没充电”状态下抓取 `18:27:05`、`18:27:11`、`18:27:16` 三份快照；随后用户将车辆切换为“预约充电等待”，再抓取 `18:30:18`、`18:30:25`、`18:30:31` 三份快照。两组均为只读 `dumpsys car_service`，没有调用设置接口。

| 车辆状态 | 充电口连接 | BMS 充电状态 | 预约状态 | SOC | 高压电流 | 能量流显示 | 运行级结论 |
| --- | ---: | --- | --- | --- | --- | ---: | --- |
| 插枪未充电（无预约状态事件） | `1` | 未出现缓存事件 | 未出现缓存事件 | `97.13–97.14`，无上升 | `-2.0 → -1.8 A` | `9` | 已确认物理连接且当前没有实际充电功率；不能把缺失事件写成 `BMS_CHARGE_STS=0` |
| 预约充电等待 | `1` | `6` | `1` | `97.09`，三次稳定 | `-1.8 … -2.0 A` | `9` | 用户明确的预约等待状态；连接存在，但 BMS 未进入实际充电 |

两组样本共同说明：`VENDOR_CHARGE_PORT_CONNECTED=1` 只能回答“枪已插入”，不能回答“正在充电”；`VCU_ENERGY_FLOW_SHOW=9` 在两组中都出现，也不能单独承担“实际充电 / 预约等待”的区分。当前最稳定的状态判定证据是：

1. **实际充电：** 既有充电会话中 `VENDOR_BMS_CHARGE_STS=3`，同时 SOC 连续上升、高压电流为正，且 `BMSCharge.isCharging()` 的系统实现只将状态 `3` 视为正在充电。
2. **预约等待：** 本次用户明确状态中 `VENDOR_CHARGE_PORT_CONNECTED=1`、`VENDOR_BATTERY_BOOKCHG_STATE=1`、`VENDOR_BMS_CHARGE_STS=6`，SOC 不上升且高压电流接近零 / 略为负值。
3. **插枪未充电但尚未确认预约：** 当前只能表达为“连接存在 + 未观察到实际充电 + 预约字段没有有效缓存事件”；在正式应用适配器中应保持 `UNKNOWN` 或“未验证”，禁止把没有回调等价成 `0`。

因此，产品侧的归一化状态至少需要区分 `UNPLUGGED`、`PLUGGED_IDLE`、`SCHEDULED_WAITING`、`CHARGING` 和 `UNKNOWN`。其中 `SCHEDULED_WAITING` 的当前车型运行锚点是 `BOOKCHG_STATE=1 + BMS_CHARGE_STS=6`；`PLUGGED_IDLE` 的显式 `BMS_CHARGE_STS=0` 尚未取得，不得提前固化为厂商枚举结论。

### 10.5 现阶段结论与应用边界

截至 2026-09-27，系统层样本已经能够把“已插枪且实际充电”和“已插枪但预约等待”分开；“已插枪但未充电且没有预约”的物理现象也已取得，但它的 BMS 显式状态码仍未取得。产品可以读取电量、电压、电流、连接 / 充电状态、预约等待候选状态、剩余时间原始值，并由电压 × 电流计算实时功率；剩余时间按分钟显示属于当前样本的强推断，`2047` 必须作为特殊值处理。

正式施工前仍需完成两项闭环：一是让正式 `com.autonavi.amapautolite` 验证 `CarPropertyManager` 对连接、BMS 状态和预约状态的权限、读取、订阅及失效回调；二是在用户下次恢复“无预约、已插枪未充电”后，抓取从拔枪到插枪的事件序列，确认 `BMS_CHARGE_STS` 是否产生明确的 `0`。原始车机转储和完整设备标识仅保留在仓库外临时目录，没有写入仓库。

### 10.6 车内温度边界

本节旧结论已由 2026-09-27 的宠物模式核对进一步修正：系统应用源码和运行证据已经确认 `HVAC_IN_OUT_TEMP` 区域 `1` 是实际车内温度，区域 `2` 仍未定语义。普通第三方 APK 的原厂 Binder 直接读取已于 2026-09-28 完成（第 17 节）；正式 9.5 APK 的读取、稳定订阅和断链表现仍未验证。不得用车外或区域 `2` 温度替代；原始语义记录见第 11 节。

### 11.4 天气信息

天气不走 Vehicle HAL。正式高德 9.5 源码已定位到一条内部天气链：

```text
AndroidWidgetRequest.onWeatherInfo(int, String)
    → WidgetWeatherInformation
        a = 温度整数转成的字符串
        c = 天气状况字符串
    → pm0.a(Context, WidgetWeatherInformation)
        → pm0.b 静态缓存
        → 显式广播 com.autonavi.amapauto.AUTO_WIDGET_UPDATE_WEATHER_INFO
           extra = WEATHER_INFO_KEY
           target package = rv.L()
    → qm0 天气更新处理
    → AutoWidgetProvider / AutoWidgetProviderTwoXThree 消费并展示
```

物理入口如下：

1. `source/amap-9.5.0.600013/smali/com/autonavi/amapauto/widget/jni/AndroidWidgetRequest.smali` 的 `onWeatherInfo(ILjava/lang/String;)V` 接收温度整数和天气状况字符串，并构造 `WidgetWeatherInformation`。
2. `source/amap-9.5.0.600013/smali/com/autonavi/amapauto/widget/weather/WidgetWeatherInformation.smali` 的 `a`、`b`、`c` 分别是温度字符串、整数字段和天气状况字符串；当前 JNI 回调只写入 `a` 和 `c`，`b` 没有在该回调中写入。

### 12.3 已定位的系统层获取链

系统 SystemUI 的座椅通风按钮已经给出可复用的物理主链：

```text
SeatVentilationBtn.apply()
    → HvacManager.HvacState.leftSeatState / leftSeatLevel
    → HvacManager.updateHvacSeatState()
    → MBVirtualCarManager.getValue(0x212, area=0, canDataType=0x28)
    → VirtualCarPropertyManager 整数读取
    → 厂商 VirtualCarProperty 服务 / Vehicle HAL
    → HVAC_MAINSEAT_HEAT_VENTILATION (0x15400515)
```

对应静态入口为：

1. `SeatVentilationBtn.smali` 的 `apply()V`、`executeClick()V` 和 `onHvacStateChanged(...)`；按钮不自己保存车辆真值，而是从 `HvacManager.HvacState` 回流更新。

正式 9.5 APK 后续若走标准 `CarPropertyManager`，应以 `getPropertyConfig(0x15400515)` 返回的有效区域为准，再做整数读取和变化订阅；当前运行事件的区域是 `0x0`。在正式 APK 的车控权限、读取结果、持续回调和无效状态全部闭环前，不能把这条标准路径写成已接入。

### 16.4 与标准 `CarPropertyManager` 路径的关系

### 17.4 第三方 APP 直接读写的施工契约

这条链路的调用者是**应用自身进程**，不是先由 ADB 或系统进程读取，再把结果传给应用。独立探针是普通 UID、本地调试签名、Manifest 无 `android.car.*` 车控权限；当前 Android 9 车机上，它直接显式绑定原厂导出服务。ADB 只用于安装、启动和观察日志，不是产品运行时的数据通道。以下是当前车型 / 固件已实测的调用契约，不保证跨车型或升级后的接口不变。

1. 在第三方 APP 中用 `Intent.setComponent(new ComponentName("com.chery.virtualcarservice", "com.chery.virtualcarservice.virtualcar.VirtualCarService"))` 显式指定服务，调用 `context.bindService(intent, connection, Context.BIND_AUTO_CREATE)`；`bindService` 的返回值只表示绑定请求是否被接受。等待 `ServiceConnection.onServiceConnected` 得到 `IBinder`，核对 `binder.getInterfaceDescriptor()` **严格等于** `com.chery.canmanager.interfaces.IVirturalCarProperty`（原厂拼写为 `Virtural`，不可改成 `Virtual`），再从后台线程读写。连接失败 / 断连时将数据标为不可用并重新绑定，组件生命周期结束时 `unbindService`。
2. 对 `IBinder.transact(code, request, reply, 0)`，请求 `Parcel` 先 `writeInterfaceToken(descriptor)`，再依次写 **虚拟车控函数号** `writeInt(functionId)`、`writeInt(area)`；写入事务还须紧接着 `writeInt(value)`。检查 `transact` 布尔结果，再调用 `reply.readException()`，读取事务按类型使用 `reply.readInt()` 或 `reply.readFloat()`；始终回收两份 `Parcel`。不要把 HAL 属性 ID 当作这里的函数号，也不要用整数读事务解析浮点值。

| 动作 | `transact` 事务号 | `Parcel` 参数（描述符之后） | `reply.readException()` 后 |
| --- | --- | --- | --- |
| 读取整数 `getData(II)I` | `7` | `functionId`, `area` | `readInt()` |
| 读取浮点 `getDataFloat(II)F` | `13` | `functionId`, `area` | `readFloat()` |
| 写入整数 `sendData(III)V` | `5` | `functionId`, `area`, `value` | 无值；**不代表车控生效** |

下面的 Java 封包与独立探针实际运行的 `getData`、`getDataFloat`、`sendData` 一致；`binder` 必须来自上述服务连接，而不是 `CarPropertyManager`：

```java
private static final String DESCRIPTOR =
        "com.chery.canmanager.interfaces.IVirturalCarProperty";

static int getData(IBinder binder, int functionId, int area) throws RemoteException {
    Parcel request = Parcel.obtain();
    Parcel reply = Parcel.obtain();
    try {
        request.writeInterfaceToken(DESCRIPTOR);
        request.writeInt(functionId);
        request.writeInt(area);
        if (!binder.transact(7, request, reply, 0)) {
            throw new RemoteException("getData transaction unavailable");
        }
        reply.readException();
        return reply.readInt();
    } finally {
        reply.recycle();
        request.recycle();
    }
}

static float getDataFloat(IBinder binder, int functionId, int area)
        throws RemoteException {
    Parcel request = Parcel.obtain();
    Parcel reply = Parcel.obtain();
    try {
        request.writeInterfaceToken(DESCRIPTOR);
        request.writeInt(functionId);
        request.writeInt(area);
        if (!binder.transact(13, request, reply, 0)) {
            throw new RemoteException("getDataFloat transaction unavailable");
        }
        reply.readException();
        return reply.readFloat();
    } finally {
        reply.recycle();
        request.recycle();
    }
}

static void sendData(IBinder binder, int functionId, int area, int value)
        throws RemoteException {
    Parcel request = Parcel.obtain();
    Parcel reply = Parcel.obtain();
    try {
        request.writeInterfaceToken(DESCRIPTOR);
        request.writeInt(functionId);
        request.writeInt(area);
        request.writeInt(value);
        if (!binder.transact(5, request, reply, 0)) {
            throw new RemoteException("sendData transaction unavailable");
        }
        reply.readException();
    } finally {
        reply.recycle();
        request.recycle();
    }
}
```

| --- | --- | --- |
| 实际车内温度 | `getDataFloat(binder, 0x110, 1)` | 已在普通第三方 APP 读到 `25.0 → 26.0°C`；不要读空调设定温度或 `area=0` 代替 |

可据上述少量对得上的样本**直接开始正式 APP 开发**，不必先穷举所有充电组合、座椅档位或实现订阅；先做绑定成功后的主动读取和有效 / 未知状态，再按应用需要补轮询或订阅。写控制时核对实际目标、读取真实回流并记录恢复结果；已有目标不重复确认，新增风险按当前风险口径处理。不能在 APP 启动时自动写座椅，也不能用 `sendData` 无异常作为成功 UI。若正式 APP 没读到值，优先逐项核对组件、描述符、绑定回调、函数号、区域、事务号、数据类型和服务断连；**不应先推翻已由普通第三方 APK 验证的数值映射**。
