# iCAR 03 车机媒体能力研究

> 本文件是迁入 `03地图` 的唯一车控媒体研究文档。迁移范围只包括媒体会话发现、媒体来源切换、标准媒体控制、车机媒体键路径和对应取证结论；不迁移 `03lyrics` 的歌词主链、诊断 APK、测试、Skill 或源码。

## 1. 研究范围

研究日期：2026-09-24。

目标是验证第三方应用在当前 iCAR 03 车机上是否能够：

1. 读取并展示当前媒体的标题、歌手、专辑、播放状态和进度。
2. 主动切换蓝牙音乐、U 盘音乐、本地音乐、爱趣听和网易云音乐。
3. 控制当前媒体暂停、恢复播放和下一首。

本轮通过临时诊断 APK 进行应用进程内验证。通知监听授权由 ADB 完成，按本任务约定不把授权本身作为阻断条件；设备地址、完整日志、截图和 APK 均保留在仓库外临时目录，没有进入仓库。

## 2. 结论摘要

| 能力 | 蓝牙音乐 | 爱趣听 | 网易云音乐（当前 03 上的 03T APK 移植版） | U 盘 / 本地音乐 |
| --- | --- | --- | --- | --- |
| 第三方应用读取并展示 | 可以 | 可以 | **当前标准 MediaSession 路径不可可靠读取** | 当前无可播放内容，未形成有效媒体会话 |
| 第三方应用直接暂停 / 恢复 | 可以 | 可以 | 当前不可证实为可控，实测未生效 | 无内容，无法验证 |
| 第三方应用直接下一首 | 可以 | 可以 | 当前不可证实为可控，实测未生效 | 无内容，无法验证 |
| 第三方应用主动切换来源 | 可以 | 可以 | 可以 | 服务调用可达；无曲目时画面不切换 |

结论不是“网易云功能不存在”：当前系统的 `CloudMusicService` 能在车机系统层生成播放状态和歌曲元数据，也能被多媒体中心切入；问题是这条会话在 iCAR 03 当前移植组合中没有按标准可控 MediaSession 对第三方应用公开。

## 3. 读取媒体信息

### 3.1 已验证可用的应用链

第三方应用在获得通知监听使用权后，可以通过：

1. `MediaSessionManager.getActiveSessions(ComponentName)` 枚举系统公开会话。
2. `MediaController.getMetadata()` 获取标题、歌手、专辑和时长。
3. `MediaController.getPlaybackState()` 获取播放 / 暂停、位置、速度和支持操作位。
4. 应用自己的 Activity 将上述字段展示在界面中。

实测结果：

- 蓝牙会话为 `com.android.bluetooth/A2dpMediaBrowserService`，可展示《姑娘在远方》、歌手 `Li`、专辑和播放状态。
- 爱趣听会话为 `com.tencent.wecarflow/MusicService`，可展示当前歌曲、歌手、播放状态、位置和队列大小。
- 探针界面已在车机上实际显示蓝牙歌曲标题、歌手、专辑、时长、播放状态、进度和操作位；不是只根据 `dumpsys` 文本推断。

### 3.2 当前网易云的特殊情况

切入网易云后，系统 `dumpsys media_session` 可以看到：

- 会话：`com.tencent.wecarflow/CloudMusicService`。
- `active=false`。
- `state=PLAYING`，并且有歌曲标题、歌手和歌词型描述文本。
- `actions=0`。

但第三方探针通过公开 `getActiveSessions` 获取到的只是 `com.tencent.wecarflow` 的无元数据 / 无播放状态候选，无法稳定拿到 `CloudMusicService` 那条带歌曲数据的会话。探针还检查了现有媒体通知，没有发现可用于构造该会话的标准 `EXTRA_MEDIA_SESSION` Token。

因此要区分两层事实：

- **系统层可见：** 网易云会话确实产生了状态和元数据。
- **第三方应用标准 API 可见：** 当前 03 上不可靠，不能直接按蓝牙 / 爱趣听的方式承诺。

这与“03 上的网易云是从 03T 多媒体中心 APK 提取后覆盖安装”的背景一致，优先判断为移植后的会话生命周期或能力声明不完整；这是当前组合的兼容性问题，不应泛化为标准 iCAR 03T 或其他网易云版本的结论。

## 4. 主动切换媒体来源

车机导出了多媒体中心切源组件：

- 组件：`com.tencent.wecarflow/com.mengbo.service.MediaCenterPlayService`
- Action：`com.mengbo.multimedia.local.switch.mediasource`
- Extra：`audio_source`

第三方进程通过显式 `startService` 调用该入口，当前固件实测映射如下：

| `audio_source` | 来源 | 实测结果 |
| ---: | --- | --- |
| `1` | U 盘音乐 | 服务调用成功；当前没有可播放 U 盘曲目，仍保留原来源 |
| `2` | 蓝牙音乐 | 成功切入蓝牙 |
| `3` | 本地音乐 | 服务调用成功；当前没有可播放本地曲目，仍保留原来源 |
| `4` | 爱趣听 | 成功切入爱趣听并出现 `MusicService` 播放会话 |
| `9` | 网易云音乐 | 成功切入网易云并出现 `CloudMusicService` 播放会话 |

所以“主动切源”在当前车机上可行；U 盘和本地音乐的剩余不确定性来自测试介质没有有效曲目，不是切源服务不可达。该入口属于当前车机实现的导出服务，不是 Android 通用媒体 API，后续集成必须隔离成固件适配器并保留失败观测。

## 5. 直接媒体控制

### 5.1 蓝牙音乐

第三方探针对 `com.android.bluetooth/A2dpMediaBrowserService` 的 `MediaController.TransportControls` 逐项执行：

1. `pause()`：会话状态从 `PLAYING` 变为 `PAUSED`。
2. `play()`：会话状态恢复为 `PLAYING`。
3. `skipToNext()`：歌曲从《空城》切换到《姑娘在远方》，元数据发生真实变化。

结论：蓝牙暂停、恢复、下一首均可行。

### 5.2 爱趣听

第三方探针对 `com.tencent.wecarflow/MusicService` 逐项执行：

1. `pause()`：状态变为 `PAUSED`，位置冻结在当前曲目。
2. `play()`：状态恢复为 `PLAYING`。
3. `skipToNext()`：歌曲从《哪凉快哪去 (Live)》切换到《夜曲》，元数据发生真实变化。

结论：爱趣听暂停、恢复、下一首均可行。该会话在播放时报告 `active=true`、`flags=7` 和非零操作位，与可控结果一致。

### 5.3 当前网易云移植版

对 `CloudMusicService` 做了两类直接控制尝试：

- `TransportControls.pause()` / `play()` / `skipToNext()`。
- 绑定到第三方可见的无状态候选会话后调用 `dispatchMediaButtonEvent`。

实测均没有让 `CloudMusicService` 从 `PLAYING` 变为 `PAUSED`，也没有让歌曲切换；发送前后 `actions=0`，播放位置继续递增。这不是全局媒体键不可靠造成的假阴性，而是当前移植会话本身未向第三方暴露可执行控制能力。

因此当前 iCAR 03 组合下不能承诺第三方通过标准 `MediaController` 控制网易云。若产品必须控制网易云，需要另行确认 03T 原车 APK / 服务版本的会话实现，或由车机侧修复其 `CloudMusicService` 的 active 状态、操作位和回调链；不能仅凭“切源成功”推断“可暂停 / 下一首”。

### 5.4 方向盘 / 系统媒体键路径

本轮额外把网易云切到当前来源后，记录了系统媒体键路径，而不是调用第三方控制器：

1. 切源后 `dumpsys media_session` 显示 `Media button session is com.tencent.wecarflow/CloudMusicService`，但该会话仍为 `active=false`、`actions=0`、`state=PLAYING`。
2. 发送一次系统级 `KEYCODE_MEDIA_NEXT`（`adb shell input keyevent 87`）后，`CloudMusicService` 的歌曲从《至少还有你》切换为《IS IT LOVE》，元数据和播放位置都发生了真实变化。
3. 同一会话的 `mediaButtonReceiver` 指向 `com.tencent.wecarflow/.media.service.MediaButtonIntentReceiver`；包组件解析表也声明了该 Receiver 接收 `android.intent.action.MEDIA_BUTTON`。
4. 车机日志同时出现 `CloudMusicService: updatePlaybackState:playState=PLAY`、`isSkipToNext=1` 和网易云内部来源 `source=10`。外部多媒体中心切源参数 `audio_source=9` 与内部媒体来源编号不是同一套编号。

这解释了“第三方标准控制失败，但方向盘下一首有效”的表面矛盾：

- `TransportControls.skipToNext()` 依赖目标会话发布的 `PlaybackState.actions` 和控制回调；当前网易云发布 `actions=0`，所以第三方控制器调用没有效果。
- 方向盘按键很可能经车机输入 / 媒体键分发链路进入 `MediaButtonIntentReceiver` 或车机内部媒体分发，再由 `CloudMusicService` 执行下一首；这条路径不以 `actions=0` 作为阻断条件。
- 本轮的 `adb shell input keyevent 87` 是对系统媒体键接收链的可重复触发，不等同于已经抓到方向盘的物理 CAN 信号；但它与用户确认的方向盘“下一首”结果一致。当前没有把“系统媒体键可切下一首”外推为“系统媒体键暂停也已通过”，暂停仍需单独取证。

所以，`active=false` 只说明该会话在标准活动会话排序中的发布状态异常，不等于车机内部完全没有播放控制路径；`actions=0` 也只否定当前标准 `TransportControls` 能力，不能否定方向盘 / 系统媒体键路径。

## 6. 系统层 APK 身份与移植判断

本车通过 ADB 读取到的相关 APK 和组件如下：

| 作用 | 包名 | APK 身份 | 当前证据 |
| --- | --- | --- | --- |
| 多媒体中心、网易云会话、媒体键接收 | `com.tencent.wecarflow` | 当前更新包位于 `/data/app/.../base.apk`，`versionName=3.2.1.174`；原系统基线位于 `/system/app/MB_WeCarFlow/MB_WeCarFlow.apk`，`versionName=3.2.0.174` | 同一包内存在 `CloudMusicService`、`MediaCenterPlayService`、`MediaButtonIntentReceiver`，以及 U 盘 / 本地 / 爱趣听公开媒体服务；当前包标记为 `UPDATED_SYSTEM_APP` |
| 系统音频焦点与路由 | `com.mengbo.media` | `/system/priv-app/MB_MLAudioService/MB_MLAudioService.apk`，`versionName=1.0.18.2` | UID 1000、persistent/privileged；导出 `com.mengbo.media.IAudio`，拥有 `MODIFY_AUDIO_ROUTING`、`MANAGE_AUDIO_POLICY`、车载音量等系统能力 |
| 多媒体卡片 / 控制服务 | `com.mengbo.medium` | `/system/app/MB_Medium/MB_Medium.apk`，`versionName=1.1.0.54` | 导出 `CardInfoService`、`CardControlService`；本轮没有证据证明它是网易云标准会话缺少 `active/actions` 的直接原因 |

当前判断：**暂时没有理由为了修复网易云标准会话，先从 03T 移植另一只系统 APK。** 当前 03 已经有 `MB_MLAudioService`，并且在现有 APK 组合下，系统媒体键已经能让网易云切下一首；这说明音频路由和车机媒体键主链至少没有整体缺失。

如果要继续做 03 与 03T 的并列验证，优先级应是：

1. 先逐版本比较 `com.tencent.wecarflow` 的 03T 原包、03 当前更新包和 `/system/app/MB_WeCarFlow` 基线，重点看 `CloudMusicService` 的 `setActive`、`setPlaybackState`、`setMetadata` 和媒体键接收链。
2. 再比较 `com.mengbo.media` 的版本、签名和系统配置，确认它是否只负责音频焦点 / 路由，不能把它当作网易云会话实现的替代品。
3. 只有日志明确指向 `CardControlService` 或蓝牙服务差异时，才继续比较 `MB_Medium.apk` 或 `MB_BTService.apk`；不做无证据的整包覆盖。

## 7. 与既有研究的关系

既有 `03desktop` 研究已经验证普通应用直接发送全局媒体键不能可靠控制当前会话。本轮把这个结论细分为两条路径：

- 普通第三方应用的会话级 `dispatchMediaButtonEvent` 和全局媒体键不能作为通用方案；当前网易云的标准会话控制仍失败。
- 车机系统级媒体键 / 方向盘输入可以通过 `MediaButtonIntentReceiver` 进入当前来源；当前已对网易云的“下一首”取得真实元数据变化证据。
- 在通知监听使用权已由 ADB 配置的前提下，标准 `MediaController.TransportControls` 对蓝牙和爱趣听可用。
- 是否可控取决于目标媒体服务是否正确发布活动会话、操作位和回调，权限不是唯一决定因素。

## 8. 后续集成建议

1. 媒体信息读取层优先采用 `NotificationListenerService` + `MediaSessionManager`，并把会话包名、元数据、播放状态和操作位作为可观测字段。
2. 媒体控制层按会话能力位判断：只有存在有效 `PlaybackState` 且对应操作位时才显示可控按钮；不要把全局媒体键当作可靠回退。
3. 来源切换单独封装为当前固件适配器，使用 `MediaCenterPlayService` 的显式 Intent；切换后必须重新枚举会话，不能复用旧控制器。
4. 网易云要把能力拆成两层：标准 `MediaController` 的暂停 / 下一首当前不可用；车机系统媒体键的“下一首”已取得证据，但不能把它等同为普通第三方 API，也不能据此宣称暂停已可用。
5. 如果后续产品确实允许接入车机系统媒体键，应把它单独定义为车型 / 固件适配器，并记录输入事件前后歌曲元数据变化；不能让 `active=false` 或 `actions=0` 单字段直接覆盖这条系统级能力判断。

## 9. 证据等级与边界

- **运行级应用证据：** 临时诊断 APK 的真实 Activity 展示、`TransportControls` 调用日志及调用前后 `dumpsys media_session` 对比。
- **运行级 ADB 证据：** 多媒体中心显式服务调用、来源切换后的会话和车机截图。
- **系统组件证据：** `com.tencent.wecarflow` 的更新包 / 系统基线包身份、`MediaCenterPlayService` 和 `MediaButtonIntentReceiver` 声明，以及 `com.mengbo.media` / `com.mengbo.medium` 的系统 APK 身份。
- **媒体键运行证据：** 切到 `audio_source=9` 后，`KEYCODE_MEDIA_NEXT` 使 `CloudMusicService` 从《至少还有你》切到《IS IT LOVE》；本轮未把物理方向盘事件本身抓成独立输入样本。
- **未完成项：** 当前没有可播放的 U 盘和本地音乐介质，因此没有对这两个来源完成“切入后有曲目 + 暂停 / 下一首”的闭环；网易云原车 03T APK 与当前 03 覆盖安装版本也未做双包并列实验；系统媒体键暂停仍未完成独立闭环。
