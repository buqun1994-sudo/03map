# 歌词卡顿与失焦空白诊断（2026-10-05）

## 结论与证据等级

本次发现两条应分别处理的链路。**持续空白存在可复核的呈现门禁缺陷：主屏地图仍可见、Activity仍RESUMED时，窗口焦点停在虚拟屏应用；歌词把失焦等同不可见，停止正文文档准备。新录音或页面重新挂载后没有已准入文档，只呈现空Box，直到门禁恢复。** 这是与现场相符的源码因果链；焦点单变量的本机验证结果记录在后文。

**卡顿有主线程慢广播的直接证据：** 同一地图进程的蓝牙接收器在14:12—14:13多次耗时50—93ms。该路径与页面交互共享主线程，可以延迟切页与动画。恢复期的8秒trace也记录到慢广播。尚未取得最初卡顿时的方法采样，不能把所有时间归给某一个Java方法、GC或此前已治理的重复Binder读取。

14:29:56将既有地图任务置前后，实际窗口焦点回到地图，14:30截图已恢复歌词与背景运动。进程、Activity实例和任务均未重建；但该操作伴随一次pause/resume，而且恢复时自然切到了下一录音，**不能冒称同录音、仅焦点变化的实机单变量实验**。本轮分析没有修改运行源码、重新打包／安装、清理数据或发送车控。

## 持续空白的具体owner

[现场构建前指纹](<../../apk-work/9.5.0.600013/source-build.bK1f74/source-before.json>)用于逐文件核对候选输入。歌词过渡、Wallpaper视窗、Panel、Binding、Mapper、Store在该候选中与施工前的Git源码一致；当前工作树含其它对话的未提交设置改动。失焦门禁仍一致，但后来已提交的平衡断行／默认宽度渲染变化未进入现场候选，不能拿当前整树或旧包验收替代本次输入。

1. [LyricsBodyTransition.rememberLyricVisibility()](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/LyricsBodyTransition.kt#L107-L124>)返回 `started && focused && LocalIconVisible`；`focused`取自`View.hasWindowFocus()`和窗口焦点通知，没有把“仍在主屏可见”与“拥有输入焦点”分开。
2. [LyricsBodyTransition()](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/LyricsBodyTransition.kt#L57-L65>)在visible=false时直接更新displayedKey，清held，opacity置1；新录音的文档owner随后按新key建立。
3. [WallpaperLyrics()](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/WallpaperLyrics.kt#L112-L143>)令`workEnabled = visible && !freezeMotion`，false时不调用`prepareLyricDocument()`；新key的candidate/admitted为空时返回没有正文的Box。已有文档可以暂留，但换歌或重新挂载没有可保留文档时会持续空白。
4. [ContentPanel()](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/ContentPanel.kt#L123-L142>)另外把pager当前页投影为`LocalIconVisible`；这是实际页门禁，不能因虚拟屏输入焦点而阻止仍可见歌词页的首份文档。
5. [MediaAmbientBackground()](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/MediaAmbientBackground.kt#L73-L85>)使用焦点停止连续motion；初次／替换烘焙仍沿active运行。失焦可解释背景停止运动，**不能单凭失焦推导背景纹理被清除**。
6. [ContentComposeHost](<../../source/amap-9.5.0.600013/content-compose/host/com/icar03/content/host/ContentComposeHost.kt#L43-L70>)通过局部Lifecycle绑定Recomposer；Binding根据STARTED启停。当前不是由后台Activity销毁地图进程后丢歌词的证据。

[已有转场测试](<../../ui-preview/content-ui/src/test/java/com/icar03/content/ui/LyricsBodyTransitionTest.kt#L182-L207>)验证失焦后恢复及不补播；[文档worker测试](<../../ui-preview/content-ui/src/test/java/com/icar03/content/ui/WallpaperLayoutWorkerTest.kt>)验证hidden取消。它们没有把“车机主屏持续可见但虚拟屏长期拿焦点”作为应继续呈现的产品条件，因此历史通过不排除本次门禁缺陷。

## 卡顿的消费主链与数值边界

[ContentMediaAdapter.acceptAvrcpEvent()](<../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentMediaAdapter.java#L507-L573>)在主线程接受事件；即使只是位置，仍`queueSnapshotLocked()`并在外层锁退出后`drainDeliveries()`，经唯一[Store.acceptMediaSnapshot()](<../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentStore.java#L391-L464>)更新录音／时间线、对齐语义、发布Binding，并把快照交给LyricsPort。外层锁已经解除不等于这些下游CPU工作已离开主线程。

只读复核[ContentLyricsTimeline](<../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/lyrics/ContentLyricsTimeline.kt#L20-L63>)、[ContentLyricsEngine](<../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/lyrics/ContentLyricsEngine.kt>)及03lyrics的既有媒体／录音契约确认：稳定同录音纯进度不会重解析或主动清空READY正文，也通常复用既有CanonicalSemanticIndex；但仍同步执行全态copy、元数据归一、录音／proof比较、时间锚准入、语义resolve和timer撤回／重排，Engine.update也在Store lock内再次检查元数据。Adapter的snapshot equality包含AVRCP sequence，所以每个有效progress事件仍可成为完整快照交付；播放中同值position而接收时间前进也可能产生新anchor并发布，这是静态churn候选，没有现场anchor revision日志，不宣称唯一CPU热点。外部来源／音频／封面Binder读取由worker调度，不能重新套用此前主线程高频getter问题。

[14:16:05现场日志](<../../.tmp/lyrics-freeze-investigation-20261005-141605/logcat-initial.txt#L21160>)中地图已接受179506—180005ms、state=3；同窗蓝牙发布duration=210465ms。因此真实播放仍在曲中，不能用“已唱到结尾”解释整曲空白。不过[Mapper.atEnd](<../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/ContentUiMapper.kt#L172-L199>)消费的是地图Store的语义sample；未直接取得内部atEnd／changingTrack，仍保留旧值／代际误判作为未证候选。

恢复期执行8秒 `atrace`，分类包括sched／freq／idle／gfx／view／wm／am／binder_driver／dalvik；完整各CPU交集为 `3141.501732—3149.501733`，约8.000001秒。[分析入口](<../../.tmp/lyrics-freeze-investigation-20261005-141605/analyze_trace.py>)由已有同车解析器调整PID及输入文件得到，[结果](<../../.tmp/lyrics-freeze-investigation-20261005-141605/trace-analysis.json>)记录：

- 主线程51次`broadcastReceiveReg`，inclusive总560.423ms，p50=8.847ms、p95=27.974ms、max=55.774ms。
- 主线程实际sched running约519.897ms；62次doFrame，inclusive总30.863ms、最大5.340ms。这不是最初卡住时的同窗样本，且doFrame数量不等于歌词屏幕呈现帧率。
- 两次后台并发GC的inclusive总232.049ms；初始日志中的GC大部分暂停为几十至数百微秒、短命对象11—14MiB。并发总时长不等于主线程完全暂停，不能把100ms GC日志直接当100ms UI停顿。
- 原生地图库仍在渲染。当前未采Java方法热点；`debuggerd -b`要求root，而设备无`su`，因此没有方法栈证据，也没有更改设备权限／调试状态。

[此前蓝牙短回跳](<蓝牙逐字歌词短回跳诊断-20261005.md>)是进度重锚问题；它可以使字符填充轻微回拉，但不能单独解释快捷页也卡和整曲正文长期消失。两次诊断分开保留。

## 修复方向与剩余项

本轮 `node scripts/check-project-docs.mjs`、`node scripts/check-skills.mjs`、`node scripts/check-code-map.mjs` 和 `git diff --check` 均退出0。运行代码未修改，仅执行上面的一个候选UI诊断用例；这些结果不代表全工程回归或车机性能验收。

优先在既有歌词呈现owner中区分页面／生命周期可见性与输入焦点：仍可见的当前歌词页应能准备首份文档、显示静态正文并消费正常媒体时间；真正离页、停止、销毁才取消不可见工作。输入失焦若用于节能，不能使新曲无限停留在无文档空Box；避免引入另一套歌词Store、媒体时间线或由ADB常驻抢焦点。

主线程慢广播另作定向治理：按元数据／录音事实版本复用已归一身份，位置事件保留真实顺序和seek／pause语义；先采同包方法热点，再决定把哪些纯计算移到worker，不用合流丢弃真实媒体事件或照搬此前旧Binder结论。

本轮目标为分析及证据保留。正式修复、签名候选、同包多显示／切页／换歌与性能回归尚未执行；现场当前已恢复歌词，不等于门禁缺陷已经修复。故障最初时刻的完整方法栈、虚拟屏焦点变化与卡顿触发顺序，以及两个现象是否具有共同初始触发仍待进一步证据。
