# 车机热点与家庭出口统一链路研究（2026-10-07）

## 1. 研究范围与结论

本记录审查了畅流 7.1 APK 的本机静态分析、`lander96/cartunnel-apk` 当前公开源码，以及 iCAR03 上已经取得的 VPN、SoftAP 和手机代理实测证据。目标是为“一个车机端客户端 + 一个家庭端客户端”确定可行链路、两端职责、首次配置方式和不可绕过的系统边界。

本记录不设计畅流或 Cartunnel 的兼容客户端，不复用它们的账号、配置格式或 UI。它们只作为已经验证过的网络结构和生命周期逻辑参考。畅流分析本身没有安装运行 APK、连接车辆或请求其服务器，因此其结论属于静态分析；Cartunnel 的公开 `main` 源码不等同于当前车机已安装 APK；车机路由和代理结论以本机实测为准。

**结论：** 家庭出口端、统一车机 VPN、车机热点和热点侧 HTTP/HTTPS 代理可以组成一条可用且可维护的链路。最合理的车机集成点是把热点代理接入车机端客户端自己的本机 Xray SOCKS/HTTP 入站，而不是启动第二个 VPN 或试图把 SoftAP 下游流量强行改入 `tun0`。

在“两端应用”约束下，可以做到车机侧自动恢复、家庭出口端自动提供出口，以及手机首次完成必要配置后的大部分无感使用。普通 Android APK 无法同时保证手机不设置代理、不安装辅助程序、所有应用和所有 TCP/UDP/QUIC/DNS/IPv6 流量都透明经过家庭出口端；这是系统网络边界，不是继续模仿畅流即可消除的问题。

## 3. 可借鉴的成熟逻辑

### 3.1 畅流与 Cartunnel 的共同主链

两者都采用下列职责分层：

```text
Android VpnService 建立 TUN
        ↓
HEV 负责 TUN 与本机代理之间的转发
        ↓
Xray 本机代理接收 TCP/UDP
        ↓
VMess/WebSocket 或后续自有隧道传到远端
        ↓
远端服务作为互联网出口
```

应用自身被排除在 VPN 之外，是为了让它连接远端节点时使用原有底层网络，避免 VPN 自循环。这不是热点手机流量已经进入 VPN 的证据。

### 3.2 应吸收的生命周期逻辑

车机端客户端应吸收畅流和 Cartunnel 已有的状态管理思想：

- VPN、远端核心、热点和热点代理由一个状态机协调；
- 启动顺序固定为“远端核心就绪 → VPN/HEV 就绪 → 出口健康检查 → 热点 → 热点代理”；
- 网络变化、车机唤醒和开机恢复使用有界重试；
- 同一个动作使用 single-flight 门禁，避免重复启动和重复停止；
- 失败时保留可恢复状态和脱敏诊断；
- VPN 或远端出口不可用时默认停止热点代理，避免用户以为流量仍走家庭出口端；
- 节点、密钥和状态持久化与运行态分离。

畅流的 HTTP `10809` 入站对本方案尤其有参考价值。当前 Cartunnel 公开源码只创建了本机 SOCKS `127.0.0.1:10808`，车机端客户端应增加本机 HTTP 入站，或者由热点代理桥接到本机 SOCKS/HTTP 入站，再由 Xray 转发到家庭出口端。

### 3.3 不应照搬的部分

以下内容不属于车机端客户端的设计目标：

- 畅流账号、套餐余额、订阅接口和第三方节点列表；
- 畅流或 Cartunnel 的 profile JSON、VMess URI 和包间通信；
- 依赖固定内置节点的回退逻辑；
- 将 `www.baidu.com` Host 当成加密或授权机制；
- 让车机扫描家庭出口端二维码；
- 用第二个 `VpnService` 接管热点流量。

### 3.4 固定电脑端不是必要条件

“电脑端”只是当前常见的家庭端客户端运行载体，不应成为产品架构的固定前提。统一方案应定义一个无界面或可选管理界面的**家庭端客户端（内部称家庭出口端 Agent）**，由它负责隧道服务、公网入口、设备授权和家庭宽带出口；电脑、NAS 和路由器只是这个客户端的不同部署目标。

| 部署目标 | 优势 | 主要限制 | 产品定位 |
|---|---|---|---|
| NAS | 长期开机、存储可靠、通常支持 Docker/容器、便于备份和日志管理 | 仍可能处于 CGNAT 后；不同品牌的容器和网络权限不同 | **第一默认部署目标** |
| OpenWrt/Linux 路由器 | 位于家庭网络边界，天然负责 WAN/LAN、防火墙、端口转发和 DDNS；无需依赖电脑开机 | CPU/内存/闪存有限；原厂固件可能不能安装自有服务；升级固件有网络中断风险 | **网络位置最优，作为第二部署目标** |
| 电脑 | 开发调试方便，计算资源充足，首次验证成本最低 | 可能睡眠、关机、换网络或被防火墙拦截；不适合作为必须常驻的唯一设备 | **开发、诊断和备用部署目标** |

因此，最佳产品形态不是“电脑客户端 + 车机客户端”，而是“家庭端客户端 + 车机端客户端”。电脑端可以保留管理界面，但数据面服务仍属于家庭端客户端，允许它作为 NAS 容器、路由器插件或电脑后台服务运行。

出口端提供两种连接模式：

- **直连模式：** 出口端监听公网端口。路由器部署时由自身完成端口转发；NAS 或电脑部署时由上级路由器转发到对应主机。必须有可达的公网 IPv4/IPv6，或运营商允许入站连接。
- **中继模式：** 出口端主动向 VPS 建立长期出站连接，车机连接 VPS 后由中继转发到出口端。该模式不依赖家庭入站端口，适合 CGNAT、动态地址和普通 NAS/电脑网络。

直连与中继属于 Agent 的部署模式，不应改变车机端的配置模型和状态机。无论 Agent 运行在哪里，车机端看到的都应是同一个“家庭出口设备”。路由器上的控制接口只允许内网管理，不应把路由器管理权限或未认证代理暴露到公网。


### 4.1 家庭出口端

家庭端客户端（家庭出口端 Agent）承担出口和设备管理职责：

1. 在 NAS、路由器或电脑上运行统一隧道服务，使家庭宽带成为车机的互联网出口。
2. 在有公网 IPv4 且路由器支持端口转发时提供直连模式。
3. 在 CGNAT、动态公网地址或入站受限时，主动连接 VPS 中继。
4. 生成车机端导入配置，包括服务地址、端口、设备标识、认证密钥和传输参数。
5. 管理设备授权、密钥轮换、设备撤销、连接状态和基本流量统计。
6. 只开放统一隧道服务端口；任意内网端口映射属于独立功能，不能默认与互联网出口混在一起。
7. 对公网入口做认证、连接数限制、失败限速、防火墙检查和配置备份。

现有 Cartunnel 的 `deploy/server/deploy.sh` 证明了 VMess/WebSocket/Xray 服务端的基本部署方式，但它面向 Ubuntu/Docker，不能直接视为最终出口端实现。出口端 Agent 需要重新设计服务进程、安装方式、端口检测、重启恢复和中继管理。

### 4.2 车机端

车机端客户端承担连接、热点和热点代理职责：

1. 通过文件、ADB、U 盘、局域网文件共享或人工填写导入家庭出口端配置。
2. 统一管理 VPN 授权、隧道核心、HEV、TUN、健康检查和自动重连。
3. 第一次通过系统热点设置保存 SSID 和密码，之后负责开启、关闭和恢复热点。
4. 检查 `wlan1` 是否真正进入 `TetheredState`，读取每次启动后的实际网关地址。
5. 在当前 SoftAP 网络侧提供 HTTP/HTTPS CONNECT 代理入口。
6. 将热点代理请求交给车机端客户端内部的本机 Xray SOCKS/HTTP 入站，再通过家庭端客户端访问互联网。
7. 只允许当前 SoftAP 子网连接代理，不把代理暴露到车机其他网卡。
8. VPN、远端出口或热点代理未就绪时，默认停止接受新代理连接，并在界面显示真实状态。
9. 在屏幕上显示 Wi-Fi 二维码和当前代理信息；该二维码由手机扫描，车机不扫描出口端二维码。
10. 记录脱敏的连接状态、最近错误、当前网关和代理连接计数，不记录业务内容、密码或隧道密钥明文。

车机端客户端不应再启动一个独立 VPN。热点代理应复用车机端客户端内部的远端核心；这既避开了 VPN UID 排除问题，也避免两个 VPN 相互替换。

## 5. 客户端实施结构

本节描述可以进入技术设计的模块边界，不代表代码已经实现。产品始终只有两个客户端：车机端客户端和家庭端客户端；NAS、路由器和电脑只是家庭端客户端的运行载体，VPS 只在中继模式下提供基础设施。

### 5.1 两端共用的连接合同

两个客户端之间需要有一份自有的设备连接合同，不兼容畅流或 Cartunnel 的客户端配置。合同至少包含：

- 设备唯一标识；
- 每台车独立的认证密钥或证书；
- 家庭端地址、端口和直连/中继模式；
- 传输协议版本和能力集；
- 配置版本、有效期、撤销状态；
- 车机端需要的热点代理策略；
- 最后一次成功连接和失败原因的脱敏状态。

连接数据面和管理控制面分开：

```text
车机端客户端数据面
  VPN/TUN 或热点代理
        ↓
  车机端本地隧道核心
        ↓ 认证加密连接
家庭端客户端数据面
        ↓
  家庭宽带出口
```

```text
家庭端客户端控制面
  设备注册、撤销、配置生成、健康状态

车机端客户端控制面
  导入配置、授权、热点设置、状态和诊断
```

家庭端控制面默认只允许家庭局域网访问；公网只暴露认证后的隧道数据入口。不能把家庭端做成没有认证的 SOCKS、HTTP 或任意端口转发服务。

### 5.2 车机端客户端模块

车机端客户端至少拆成以下模块：

| 模块 | 责任 |
|---|---|
| 配置与安全存储 | 导入家庭端配置，使用 Android Keystore 保存设备密钥和热点相关敏感字段，校验配置版本和撤销状态 |
| 会话协调器 | 串行处理启动、停止、重连、网络变化、唤醒恢复和用户停止，阻止重复动作 |
| 隧道核心适配器 | 启停本地隧道核心、HEV 和远端连接，向上层提供就绪、失败、流量和延迟状态 |
| 唯一 VPN owner | 由一个 `VpnService` 建立 TUN，管理 VPN 授权、路由、DNS、MTU 和自身 UID 排除；不启动第二个 VPN |
| SoftAP 控制器 | 启停系统热点，等待稳定的 `TetheredState`，读取当前 SSID、接口和实际网关 |
| 网关观察器 | 监听 `wlan1` 地址和热点重启，更新当前代理地址；不假设网关永久固定 |
| 热点代理桥 | 只在当前 SoftAP 子网监听 HTTP/HTTPS CONNECT，把请求交给车机端内部 HTTP/SOCKS 入站；VPN/家庭端未就绪时停止接受新请求 |
| 自动恢复器 | 处理开机、唤醒、网络切换和车机服务重建，使用有界退避和恢复冷却时间 |
| 状态与诊断 | 显示当前阶段、家庭端、VPN、热点、代理和最近失败原因；日志脱敏，不记录业务内容 |

车机端启动状态应收敛为：

```text
未配置
  → 已配置
  → 等待 VPN 授权
  → 启动家庭端连接
  → 隧道就绪
  → 出口健康
  → 启动热点
  → 网关稳定
  → 热点代理就绪
  → 已运行
```

任意阶段失败时进入可恢复错误或降级状态。家庭端连接、VPN 或出口健康检查失败时，热点代理必须关闭或拒绝新连接；不能让界面显示“已联网”而实际流量回落到 `usb0`。

车机应用本地车机流量和热点代理流量共用远端隧道核心，但入口不同：

```text
车机本地应用 → TUN → HEV/隧道核心
手机热点流量 → wlan1 → 热点代理桥 → 本地 HTTP/SOCKS → 隧道核心
```

第二条路径是第一版解决热点共享的关键。它不要求 Android 把 `wlan1` 的原始转发包送进 `tun0`，也不调用第二个 `VpnService`。

### 5.3 家庭端客户端模块

家庭端客户端的核心逻辑与运行平台分离，至少包含：

| 模块 | 责任 |
|---|---|
| 设备注册表 | 保存每台车的设备标识、密钥/证书、启用状态、撤销状态和最后连接时间 |
| 配置生成器 | 生成车机端导入包，按设备生成凭据，不复用畅流或 Cartunnel profile |
| 隧道监听器 | 直连模式监听公网入口，完成认证、加密握手和会话建立 |
| 中继连接器 | 中继模式主动连接 VPS，维护出站长连接和重连；中继只转发已认证会话 |
| 会话管理器 | 限制设备并发数、连接时长、空闲连接和带宽，处理撤销即时生效 |
| 家庭出口适配器 | 将已认证隧道流量通过 NAS、路由器或电脑的默认家庭网络发送到互联网 |
| 控制接口 | 在家庭局域网提供设备添加、撤销、配置导出、模式选择和健康状态，不暴露到公网 |
| 持久化与诊断 | 保存加密配置、版本迁移、备份、轮换记录和脱敏运行日志 |

直连和中继只替换 `隧道监听器/中继连接器` 的连接方式，设备注册、认证、会话和配置合同保持一致。家庭端不提供匿名代理，也不把“端口映射任意内网服务”作为默认能力。

### 5.4 三种部署封装

三种部署方式应共享家庭端客户端核心，只更换启动、存储、网络和管理适配器：

- **NAS 软件：** 优先提供 Docker/容器和可持久化数据目录，设置健康检查、自动重启、配置备份和明确的端口映射。NAS 仍需要上级路由器端口转发，或使用中继模式。
- **路由器插件：** 面向 OpenWrt/Linux，提供对应架构的后台进程、`procd`/系统服务启动、UCI 或等价配置、日志轮转和最小防火墙规则。只有支持自定义软件包、容器或插件的路由器才属于支持范围；封闭原厂固件不能默认安装。
- **电脑服务：** 提供 Windows/macOS/Linux 后台服务，桌面界面只负责管理和诊断，数据面服务可以在无用户登录时运行。电脑睡眠、关机和防火墙状态必须在界面中明确显示。

这三种封装不应各自维护一套协议或业务逻辑。应由同一个家庭端客户端核心生成同样的设备配置、接受同样的车机连接，并返回同样的状态模型。

### 5.5 配置和配对实现

配置流程由家庭端客户端发起：

1. 家庭端客户端创建一台车的设备记录和独立凭据。
2. 家庭端客户端生成配置文件或受保护的导入包。
3. 用户通过 U 盘、ADB、文件共享或人工输入把配置交给车机端客户端。
4. 车机端客户端校验版本、地址、凭据和有效期后，加密保存。
5. 车机端客户端完成一次 VPN 授权，随后可以自动恢复。

车机端没有摄像头，因此不设计车机扫描家庭端二维码。车机屏幕上的 Wi-Fi 二维码只用于手机加入车机热点，与两个客户端之间的配置导入无关。

### 5.6 第一版实施边界

第一版客户端应先完成以下闭环：

- 家庭端直连和中继二选一的稳定连接；
- 车机端配置导入和安全保存；
- 一个 VPN owner 的车机本地 IPv4 隧道；
- 车机自动开热点、发现当前网关；
- 当前 SoftAP 子网的 HTTP/HTTPS CONNECT 代理；
- 家庭端认证、撤销、重连和 fail-closed；
- NAS、路由器、电脑三种部署封装中的至少一种可重复安装方式。

以下能力不应假装包含在第一版：

- SoftAP 原始转发包透明进入 `tun0`；
- 手机所有应用的 TCP/UDP/QUIC/DNS/IPv6 全流量；
- 标准 Wi-Fi 二维码自动写入 HTTP 代理；
- 不依赖公网入口或中继的 CGNAT 直连；
- 未认证的任意端口映射；
- 对畅流或 Cartunnel 客户端的配置兼容。


## 6. 两端操作流程

### 6.1 家庭端客户端操作

1. 安装或启动家庭端客户端（内部服务称家庭出口端 Agent）；电脑部署时打开管理界面，NAS/路由器部署时使用其管理入口。
2. 选择直连或中继模式。
3. 生成并启动家庭出口服务。
4. 配置路由器端口转发或等待中继连接建立。
5. 新增一台车，生成该车专用配置。
6. 通过 U 盘、ADB、文件共享或用户选择的传输方式把配置交给车机。
7. 在家庭出口端查看车机是否上线、出口是否健康，必要时撤销或轮换该车密钥。

### 6.2 车机端操作

1. 打开车机端客户端，导入家庭出口端配置。
2. 完成一次系统 VPN 授权。
3. 第一次进入系统热点设置，保存 SSID 和密码。
4. 返回车机端客户端，开启自动连接和自动共享。
5. 车机端客户端依次恢复 VPN、远端出口、热点和热点代理。
6. 车机屏幕显示 Wi-Fi 二维码、当前热点网关和代理状态。
7. 后续开机、唤醒或网络变化时由车机端客户端自动恢复，不再重复导入配置。

家庭出口端到车机端的配置导入，与车机端向手机展示 Wi-Fi 二维码是两个独立动作。不能把“出口端生成配置”和“手机加入车机热点”设计成车机扫码流程。

## 7. 硬阻碍与边界

| 问题 | 结论 |
|---|---|
| SoftAP 手机流量自动进入 `tun0` | 当前普通 APK 做不到。实测系统规则是 `wlan1 → usb0`，需要系统级 tethering/策略路由能力才能改变。 |
| 只扫描一次 Wi-Fi 二维码，同时自动设置代理 | 标准 Wi-Fi 二维码没有 HTTP 代理字段，不能作为两端应用的可靠承诺。 |
| 热点重启后代理地址永久不变 | 当前不能保证。已观察到 `wlan1` 网关地址会变化；普通应用不能稳定固定 SoftAP 网关。 |
| CGNAT 下家庭出口端直接接受公网连接 | 做不到，必须使用 VPS 或其他公网中继。 |
| 所有手机 App、UDP、QUIC、DNS、IPv6 自动走家庭出口端 | 两端普通 APK 方案做不到，需要手机侧 VPN 或车机系统级透明转发能力。 |
| 直接把 `www.baidu.com` Host 当作安全措施 | 不成立。当前 VMess/WebSocket 配置的外层 TLS 为空，Host 只是传输兼容字段；车机端客户端应由设备密钥和正式加密传输负责认证与保密。 |
| 通过第二个车机 VPN 解决热点转发 | 不可取。Android 用户 VPN 会替换现有 VPN，车机端客户端必须只保留一个 VPN owner。 |

## 8. 当前产品决策

1. 产品形态固定为“一个车机端客户端 + 一个家庭端客户端（可部署于 NAS、路由器或电脑）”，不做畅流或 Cartunnel 兼容层。
2. 家庭出口端负责公网入口、家庭宽带出口、设备授权和配置生成。
3. 车机端负责 VPN、热点、热点网关发现和热点侧代理。
4. 家庭出口端到车机使用配置文件、ADB、U 盘、文件共享或人工输入；不设计车机扫描出口端二维码。
5. 车机到手机使用车机屏幕上的 Wi-Fi 二维码；这不是家庭出口端配置流程。
6. 热点共享的第一阶段目标是 HTTP/HTTPS 代理链路，不宣称所有应用的透明全流量共享。
7. 默认采用 fail-closed：远端出口不可用时停止新代理连接，并按产品需要停止热点。
8. 若将来要求所有手机流量无感经过家庭出口端，必须单独引入手机侧 VPN 或车机系统级权限，不能把它写成普通 APK 阶段目标。
9. 若需要更强公网安全性，应在统一协议中加入 TLS/mTLS 或同等强度的设备认证；不能把白名单 Host 或固定路径写成安全保证。

## 9. 后续验证顺序

后续真正施工前，验证顺序应保持为：

1. 家庭出口端在直连模式下验证隧道服务、出口和重启恢复。
2. 家庭出口端在 CGNAT/中继模式下验证反向连接和连接撤销。
3. 车机端验证配置导入、VPN 恢复和远端健康检查。
4. 车机端验证热点启动、`wlan1` 网关变化和代理桥生命周期。
5. 在多个热点重启周期中验证代理地址变化对实际使用的影响。
6. 再决定是否需要固定网关的系统能力或额外的客户端发现机制。

在上述验证完成前，不能把“开机后手机完全无感上网”写成已实现功能。
