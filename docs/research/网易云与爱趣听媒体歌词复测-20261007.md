# 网易云与爱趣听媒体歌词复测记录

> 复测日期：2026-10-07。目标设备为 iCAR 03 `S56_HQX`、Android SDK 28、`1920×1080`、density `141`。车机通过当次发现的 ADB serial 连接；原始 dumpsys、logcat 和网络响应保存在被忽略的 [`.tmp/netease-research-20261007/`](../../.tmp/netease-research-20261007/) 目录，本文只记录可复核的脱敏结论。
>
> 本文是[车机媒体能力研究](车机媒体能力研究.md)的本轮补充，重点复核网易云、爱趣听和用户随后要求的蓝牙动态歌词。蓝牙专项在用户确认“单行歌词不满足需求”后结束，不扩展产品方案。

## 结论先行

| 目标 | 当前结论 | 能力等级 |
| --- | --- | --- |
| 网易云媒体信息 | 能读到系统 `CloudMusicService` 的标题、歌手、时长、播放状态和 `description` 内嵌逐行 LRC；普通活动排序会漏掉这条 `active=false` 会话，需沿 03lyrics 的公开 Browser／未声明服务发现与仲裁链读取 | 读取已取得系统级现场证据，正式地图 UI 仍需运行级接入验收 |
| 网易云标准控制 | `PlaybackState.actions=0`，普通 `MediaController.TransportControls` 不能形成暂停、恢复、下一首闭环 | 标准第三方控制不可用 |
| 网易云车机媒体键 | ADB shell 的媒体暂停、恢复、下一首均有前后状态证据；下一首改变了实际歌曲元数据 | 车机系统路径可用；不等同普通 APK 获得全局媒体键注入权限 |
| 爱趣听媒体信息与控制 | `MusicService` 标准会话可读；暂停后位置冻结，恢复后继续，下一首改变标题和歌手 | 读取、暂停、恢复、下一首均已现场确认 |
| 爱趣听歌词 | 当前 `MusicService` 的 `description` 为 `null`，没有通过公开 MediaSession 交付内嵌歌词；外部 QQ 匹配可以取得完整逐行 LRC | 当前样本逐行同步完整；无翻译、无逐字时间 |
| 网易云歌词质量 | 内嵌会话提供逐行 LRC；网络接口样本另提供逐行翻译，但 `klyric` 为空 | 逐行同步可用；逐字缺失；翻译取决于网络源，非会话内置 |
| 蓝牙动态歌词 | A2DP 标题随播放变成当前歌词行，歌手字段携带“原歌名 - 歌手”；只有当前行，没有完整正文、逐字时间或翻译 | 不满足地图歌词需求，专项结束 |

## 03lyrics 参考链与本轮适用边界

本轮先对照了 03lyrics 当前正式源码和测试：

- [`PublicMediaBrowserSessionRegistry`](../../../03lyrics/app/src/main/kotlin/com/ninepointnine/desktoplyrics/PublicMediaBrowserSessionRegistry.kt) 在 `MediaSessionManager.getActiveSessions(listenerComponent)` 之外，还枚举声明的公开 Browser 服务，并对符合条件的活动包补充未声明服务。
- [`MediaSessionSelectionPolicy`](../../../03lyrics/app/src/main/kotlin/com/ninepointnine/desktoplyrics/MediaSessionSelectionPolicy.kt) 按播放、缓冲、活动性和来源证据选择会话；不能只按包名或旧会话复用。
- [`MediaSessionMetadataPolicy`](../../../03lyrics/app/src/main/kotlin/com/ninepointnine/desktoplyrics/MediaSessionMetadataPolicy.kt) 从 description、display description、album 等字段归一标题、歌手、专辑、时长和媒体 ID；只有至少两行时间戳的同步 LRC 才会进入 `embeddedLyrics`。
- [`LyricsPlaybackStore`](../../../03lyrics/app/src/main/kotlin/com/ninepointnine/desktoplyrics/LyricsPlaybackStore.kt) 的测试证明：有效内嵌 LRC 优先于网络查询，网络请求数为零；无效内嵌文本才回退普通解析。
- [`PublicLyricsSources`](../../../03lyrics/app/src/main/kotlin/com/ninepointnine/desktoplyrics/PublicLyricsSources.kt) 的 NetEase 源解析 `lrc` 和 `tlyric`，QQ 源解析 `lyric` 和 `trans`。当前实现的 `LyricsKind` 只有逐行 `SYNCHRONIZED`，没有 `klyric` 逐字时间轴的消费路径；相关约束也由 [`PublicLyricsSourcesTest`](../../../03lyrics/app/src/test/kotlin/com/ninepointnine/desktoplyrics/PublicLyricsSourcesTest.kt) 覆盖。

因此，“能读到会话字段”“能读到逐行歌词”“有逐字时间轴”“有翻译”必须分别验收，不能因为同一条 MediaSession 存在就把四项能力合并成高质量歌词。

## 网易云现场复测

### 会话、元数据与控制

切换入口仍是：

```text
com.tencent.wecarflow/com.mengbo.service.MediaCenterPlayService
action: com.mengbo.multimedia.local.switch.mediasource
audio_source: 9
```

切入后的 `CloudMusicService` 原始会话显示：

- `state=3`（播放中），位置和速度字段更新；
- `active=false`；
- `actions=0`；
- `metadata:size=9`；
- description 以 `[00:00.000]` 开始，包含完整的逐行 LRC 正文。

本轮控制前后的证据文件为 [`netease-01-before-controls.txt`](../../.tmp/netease-research-20261007/netease-01-before-controls.txt)、[`netease-02-after-pause-key.txt`](../../.tmp/netease-research-20261007/netease-02-after-pause-key.txt)、[`netease-03-after-play-key.txt`](../../.tmp/netease-research-20261007/netease-03-after-play-key.txt) 和 [`netease-04-after-next-key.txt`](../../.tmp/netease-research-20261007/netease-04-after-next-key.txt)。结果如下：

| 操作 | 现场结果 |
| --- | --- |
| `KEYCODE_MEDIA_PAUSE`（127） | `state=3 → state=2`，位置从约 `549ms` 样本推进到暂停位置后停止 |
| `KEYCODE_MEDIA_PLAY`（126） | `state=2 → state=3`，位置继续推进 |
| `KEYCODE_MEDIA_NEXT`（87） | 标题从《Knock You Down》变为《Crazy Things》，位置重置，仍为播放 |

这些是 ADB shell 发送系统媒体键后的设备回读，不是普通 APK 的 `TransportControls` 成功日志。`actions=0` 仍足以判定标准第三方会话控制不可用；当前可行的是车机系统媒体键／原厂媒体分发路径。正式地图若要复用该路径，需要明确系统权限或车机导出适配器，不应把 shell 证据直接写成普通应用权限。

### 内嵌与网络歌词质量

当前现场 `CloudMusicService` 的 description 内嵌样本是逐行 LRC：有行级时间戳，没有看到 `<字级时间>` 标记，也没有翻译轴。03lyrics 的 `firstEmbeddedLyrics` 会把这种至少两行时间戳文本认定为有效内嵌同步歌词，`LyricsPlaybackStore` 会直接发布它。

随后对当前 NetEase 歌曲的公开歌词接口保存了 [`netease-cloud-lyrics.json`](../../.tmp/netease-research-20261007/netease-cloud-lyrics.json)。本次样本统计如下：

| 字段 | 结果 |
| --- | --- |
| `lrc.lyric` | 30 条带时间戳行，覆盖整首 `Crazy Things` 的 1:53.417 末尾 |
| `klyric.lyric` | 空；没有逐字时间标记 |
| `tlyric.lyric` | 30 行左右的翻译轴，29 行带时间戳；第一首英文制作信息行没有对应中文歌词 |
| 结论 | 网络源可以补出逐行翻译，但当前会话内嵌正文没有把这条翻译一起交付；逐字数据本样本不存在 |

所以网易云当前能达到“逐行同步正文”，网络源在部分歌曲上还能达到“逐行翻译”；不能写成“逐字歌词完整”，也不能把网络翻译回填为车机 MediaSession 已提供的字段。

## 爱趣听现场复测

### 会话、元数据与控制

切换入口使用 `audio_source=4`。当前公开会话为 `com.tencent.wecarflow/MusicService`，现场操作证据保存在 [`aq-02-before-controls.txt`](../../.tmp/netease-research-20261007/aq-02-before-controls.txt) 至 [`aq-06-after-next-key.txt`](../../.tmp/netease-research-20261007/aq-06-after-next-key.txt)：

- 复测前：标题《玫瑰》、歌手贰佰，`state=3`，位置约 `111901ms`，`actions=4023`；
- 发送暂停键后：`state=2`，位置约 `112832ms`；
- 等待两秒：仍为 `state=2`、位置仍约 `112832ms`；
- 发送播放键后：`state=3`，位置继续到约 `113888ms`；
- 发送下一首后：标题变为《国王与乞丐 (Live)》、歌手华晨宇，位置回到 `0`，仍为播放。

这构成了爱趣听暂停、位置冻结、恢复和下一首元数据变化的完整闭环。会话 metadata 的 description 为空，因此这次 MediaSession 本身没有交付内嵌歌词。

车机日志还观察到爱趣听自身的 `lyricChange` 内部消息，例如当前行 `V12的发动机`、`开进去 开进去`，并同时带有 `current`、`lineNumber` 和 `lyric`。这是原厂内部卡片／语音链路的逐行回调线索，不能直接当作普通第三方已经有订阅入口；本轮没有把该内部回调接入地图。

### 外部歌词质量

当前爱趣听歌曲《你一定要幸福 / 简弘亦》通过 QQ 搜索匹配到 `songmid=002xdDqK3GkHVO`，响应保存在 [`aq-qq-search.json`](../../.tmp/netease-research-20261007/aq-qq-search.json) 和 [`aq-qq-lyrics.json`](../../.tmp/netease-research-20261007/aq-qq-lyrics.json)。统计结果：

| 字段 | 结果 |
| --- | --- |
| `lyric` | 45 条带时间戳行，正文从 `00:00.00` 到 `04:09.74`；包含完整主歌词行 |
| `trans` | 空 |
| 逐字时间 | 没有 `<...>` 字级标记 |
| 结论 | 当前样本可以得到完整逐行同步正文，但无翻译、无逐字时间 |

这证明“爱趣听当前歌曲能配到高质量逐行歌词”是可行的网络回退结论；它不证明爱趣听 `MusicService` 已经把歌词嵌入公开 MediaSession，也不证明所有爱趣听歌曲都有同样的 QQ 匹配和翻译覆盖率。

## 蓝牙专项结果（按用户要求结束）

用户手机开启“蓝牙设备歌词”后，使用 `audio_source=2` 切入蓝牙；车机日志明确记录 `sourcetype=BT, source=6`。A2DP 会话的字段随着播放表现为：

```text
Title=自你离开以后, Artist=西海情歌 - 刀郎, Album=刀郎Ⅲ
Title=回不到我们的从前, Artist=西海情歌 - 刀郎, Album=刀郎Ⅲ
```

两次标题分别在约 `57s` 和 `155s` 的播放阶段出现，标题内容与《西海情歌》的公开逐行歌词时间轴相符。也就是说蓝牙协议把“当前歌词行”塞进了标题，歌名和歌手被拼在歌手字段中；A2DP metadata 没有完整歌词正文、翻译字段或逐字时间轴。系统媒体键当时仍指向陈旧的 `MusicService` 会话，未形成对 A2DP 播放／暂停／下一首的独立控制闭环。

这满足了“蓝牙能传当前行”的判断，但不满足地图需要的完整歌词时间线。该专项按用户确认结束，不再为单行字段设计解析或缓存策略。

## 包标识与封面元数据

这里的“bundle ID”按 Android 语境对应包名。爱趣听和当前移植的网易云并不是两个独立 Android 包，二者都运行在：

```text
packageName: com.tencent.wecarflow
```

来源要用 MediaSession 组件区分：

| 来源 | MediaSession 组件 | 车机来源域 |
| --- | --- | --- |
| 爱趣听 | `com.tencent.wecarflow/MusicService` | 外部切源 `audio_source=4`；日志内部 `mSource=13` |
| 网易云 | `com.tencent.wecarflow/CloudMusicService` | 外部切源 `audio_source=9`；PlayableMedia卡片 `source=10`，当前IMB播放器真实读回 `getMediaDataSoure()=14` |

因此只保存一个 package/bundle ID 不足以区分平台；正式录音身份至少要同时保存包名、会话组件／token、标题、歌手、专辑和时长。

爱趣听公开 `MusicService` 的 metadata 已通过临时只读探针枚举确认，证据为 [`aq-media-metadata-probe.txt`](../../.tmp/netease-research-20261007/aq-media-metadata-probe.txt)：

```text
android.media.metadata.ART_URI
https://y.gtimg.cn/music/photo_new/T002R300x300M000002pgY7c3LgAqu_1.jpg
MediaDescription.iconUri = 同一 URL
```

同一条会话还发布了 `DISPLAY_TITLE`、`DISPLAY_SUBTITLE`、`ALBUM`、`DURATION` 和 `MEDIA_ID`；本样本没有直接传 Bitmap，传的是可下载的 URI。车机内部 `PlayableMedia` 日志也记录了爱趣听的 `itemImageUrl`，与公开会话的封面 URI 形成对应。

网易云的当前 `dumpsys media_session` 摘要只打印 `metadata:size=9` 和 description，不展开每个 metadata key；但本轮重新切入网易云的运行日志已经直接记录了 `CloudMusicService` 来源 `source=10` 的媒体封面。当前歌曲《Take Me Away / Keyshia Cole》的字段为：

```text
PlayableMedia.itemImageUrl=
http://p1.music.126.net/xYwTL0QJfeBsyNkEGHZwJA==/6663040465261101.jpg?imageView=1&thumbnail=100z100&type=webp&quality=80
```

原始位置见 [`netease-cover-current-logcat.txt`](../../.tmp/netease-research-20261007/netease-cover-current-logcat.txt)，`CardInfoManager` 在第 315 行收到该 URL；同一轮 `CloudMusicService` 随后在第 1436、1439 行调用 `setMetadata`。这就是网易云切歌时车机媒体卡使用的封面链接。地图正式读取时应优先接收公开 MediaSession 的标准封面字段 `ALBUM_ART`、`ART`、`DISPLAY_ICON` 及 `ALBUM_ART_URI`、`ART_URI`、`DISPLAY_ICON_URI` 和 `MediaDescription.iconUri`；本车网易云已证明对应媒体记录里存在可直接使用的图片 URL。

当前正式地图的 [`ContentMediaAdapter`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentMediaAdapter.java) 已经按这组键读取 Bitmap 和 URI：Bitmap 优先借用公开 metadata，URI 交给封面下载／缓存链；因此封面获取在代码能力上已经具备，网易云公开 `CloudMusicService` 的具体 `ART_URI` 键仍应在正式地图运行级日志中补一次字段验收。

## 正式接入时的来源域纠正（同日补充）

地图新包冷启动实读`IMBMediaCenterInterface.getMediaDataSoure()`返回14；当前车机安装包的`Constants.MediaSource.MSRC_WYY=0xe`、`MSRC_AQT=0xd`。`MediaCenterPlayImpl.getMediaDataSoure()`直接返回`PlayManager.getCurrentMediaSource()`，`MbMusicCardUtils.mapMediaCenterSource2MbMusicCardSource()`则明确把播放器14映射为卡片10。上文PlayableMedia的`source=10`是卡片域，不可拿来确认播放器来源；外部切源`audio_source=9`也是第三个不同的域。地图此前用10准入网易云导致真实14被拒，此为正式UI漏读的具体根因。

当前原厂`CloudMusicService.updateMetadata()`明确将图片URL写入标准`android.media.metadata.ALBUM_ART_URI`；`onGetRoot()`返回公开ROOT_ID，没有caller白名单。源码证据已取得，正式地图新候选的字段日志、原生图及内嵌歌词仍需同包现场验证，不能用该静态证据代验。

## 适合正式接入的结论

1. 网易云可以接入“公开会话元数据 + 标准封面 URI／Bitmap + 内嵌逐行 LRC 优先 + NetEase 网络源补翻译”的读取链；要保留 `actions=0` 的控制禁用状态，并把车机媒体键控制作为独立车型适配能力。
2. 爱趣听可以直接接入标准 `MusicService` 的元数据和控制；歌词走外部源时应绑定标题、歌手、时长和录音身份，不能把空 description 当作歌词来源。原厂 `lyricChange` 只有在找到可绑定的导出订阅协议后才能进入正式主链。
3. 当前本轮样本没有任何一个来源提供可确认的逐字歌词时间轴：网易云网络响应的 `klyric` 为空，QQ `lyric` 只有行级时间，蓝牙只传当前行。正文和翻译必须分轴建模，不能用翻译或单行动态标题伪造逐字数据。
4. 读取、歌词解析、翻译增强和媒体控制保持独立能力位；产品 UI 应分别展示“媒体可读”“逐行歌词可用”“翻译可用”“逐字不可用”和“标准控制不可用”，避免一个字段覆盖其它结论。
