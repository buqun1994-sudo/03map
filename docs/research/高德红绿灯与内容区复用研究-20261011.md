# 高德红绿灯数据与内容区复用研究

研究日期：2026-10-11。范围为当前正式高德 `9.5.0.600013` 源码／原生库的静态读取与公开接口核对。本研究记录原生 DTO 证据与内容区接入合同，不把文档内容本身当作代码、构建或车机运行证据。当前巡航可见主链采用地图 native 显示 DTO 文件桥；`CameraLightInfoWrapper` 保留为高德历史 HMI／语音链和内容区诊断来源，不再作为可见灯组的权威输入。

## 1. 结论与边界

**同一高德 APK 内的内容区可以复用已有红绿灯数据，当前可见巡航灯组应复用地图 native 显示 DTO，而不是从语音或 HMI 共享 wrapper 推导。** 原生资源、DTO 字段和文件桥协议已完成静态闭合；正式源码接入、定向测试、APK 构建和车机运行结果仍由专项验证记录维护，本研究不提前宣称通过。

| 要求 | 当前结论 | 证据等级 |
|---|---|---|
| 内容区另画灯色、方向和秒数 | 地图显示 DTO 经 `cruise-map.S` 写入 v2 文件，再由 `ContentCruiseMapBridge` 接入 `ContentStore`；内容区只消费归一化快照 | 原生静态确认；实现与验证待专项记录 |
| 与高德使用相同数据来源 | 复用同进程地图 native 显示 DTO，继续由高德负责定位、路线与上游获取；不另建网络请求链 | 原生静态确认；服务覆盖待实车 |
| 导航外显示多个方向 | DTO vector 提供多项四整数记录；`lightCount` 与 `showType` 共同决定主／次灯资格 | 原生静态确认；触发条件待实车 |
| 每个路口均有倒计时 | 不成立；主灯 status 8 无秒，主灯 status 6 还受 `sdType` 控制，次灯也可能只有灯色 | 原生静态确认；覆盖待实车 |
| 当前 DTO 的方向／灯态枚举 | 方向 `1=左、2=右、8=直`；status `2/3=红、4/5/6=绿、8=黄`；未知值丢弃 | 原生资源与 DTO 静态确认；运行值待实车 |
| 当前 DTO 的主／次灯资格 | `showType=3` 为主灯；`showType=2` 为次灯且只接受 `8` 方向；`lightCount=1` 接受 2/3，`lightCount>=2` 仅接受 3 | 原生资源与 native 分支静态确认 |
| 路线交通灯数量等同实时灯态 | 不成立；公开服务另见第4节 | 静态／官方文档核对 |
| 灯距、路口 ID／名称与路线关联 | 本轮 DTO 与两种 Java 灯模型均没有可直接消费的距离或路口 ID；关联导航状态需另查 | 静态确认字段缺失；关联待定位 |

正式输入 APK SHA-256 为 `dfb763c9b9ab42d6096e6c988578937bfbaaa73436db22f99efe37503d54f3f5`，原始快照为 `ac6033c`，详见[基线清单](<../code-map/基线清单.md>)。本轮直接读取持续演进的[正式源码](<../../source/amap-9.5.0.600013/>)，不把历史悬浮布局作为当前施工入口。

## 3. 巡航灯组：地图 native DTO 主链与历史 wrapper 诊断链

当前可见内容区使用地图显示 DTO 文件桥，链路为：

```text
libGbl CruiseTrafficSignalLightDisplayInfoToJsonObject
   → native-patches/cruise-map.S
   → DTO vector（+0x48/+0x50，stride 0x10）与元数据（+0x40 lightCount、+0xa8 sdType）
   → content-cruise-map.bin（version 2，LE header32 + count*16）
   → ContentCruiseMapBridge
   → Sink → ContentRuntime.acceptCruiseMapBatch
   → ContentStore.acceptCruiseMapSignals
   → ContentState → ContentUiMapper → ContentPanel / CruiseSignalBar
```

DTO 每项仍是四个 int：`{showType,crossManeuverID,lightCountdown,status}`。文件 v2 头部为 `magic/version/pid/vectorCount/timestampNs/lightCount/sdType`；native 侧使用临时文件后原子 rename，Java 侧按进程、长度、单调时间、新鲜度、generation 和生命周期校验。`ContentCruiseMapBridge` 的 Sink 直接进入 `ContentRuntime.acceptCruiseMapBatch(...)`，文件 Sink 是当前唯一可见接收入口。

历史 wrapper／HMI 链仍可用于解释高德原有行为和收集诊断：

```text
libhsl: GuideInfoExport.OnUpdateCruiseTrafficLightCountdown
   → CalculateCruiseLightCountDown → CameraLightInfoWrapper
   → CameraLightInteract.notifyCameraLightInfosImpl(CameraLightInfoWrapper)
   → CruiseTrafficLightVoice / FloatViewHelper / 其它 HMI 消费者
```

`ContentRuntime.onCruiseSignalBatch(Object)` 仍同步复制 wrapper 字段并记录诊断，但不再写入可见 `ContentStore` 灯组。历史 wrapper 的枚举、共享对象修改和 HMI 行为继续保留在下文作为历史合同，不能反向套用于地图 DTO。

### 3.1 原生生产、资源枚举与文件协议

以下地址和资源偏移只适用于当前正式输入及对应原生证据。`libGbl.so` SHA-256 为 `89c624e3bdc24ddfdede61fa6458236eb09fa25f7085d1c1ea16d830b3a26547`；其 `CruiseTrafficSignalLightDisplayInfoToJsonObject` converter 入口为 VA `0x19820c4`；原生分支在 `0x1982330` 读取 `lightCount`、在 `0x1982548` 读取 `sdType`，并在 `0x19823c4`、`0x19823cc`、`0x19823dc`、`0x19823ec` 读取每项四个 raw int。地图显示 DTO 的 vector 位于对象 `+0x48/+0x50`，元素 stride 为 `0x10`。native update 分支 `0x16dddc8..0x16de984` 过滤 `showType=2` 且非直行方向的次灯。`libLayerAsset` 的 SHA-256 为 `b96099b4a89473155e4e7f882cbee2974aa74bf107de019b16f7319c77cc874a`，巡航资源 JSON 位于文件偏移 `[0x383bc0,0x397b6d)`，abstract 为巡航 biz `5017`。这些资源和反汇编证据闭合了地图 DTO 的方向、灯态和主／次灯分支；不等于车机已经产生过一批运行数据。

| 当前地图 DTO 来源／字段 | 已确认行为 |
|---|---|
| `libGbl` 显示 DTO vector | 每项四个 int：`showType`、`crossManeuverID`、`lightCountdown`、`status`；`+0x48/+0x50` 为 vector，stride `0x10` |
| `libGbl` DTO 元数据 | `lightCount` 由 converter `0x1982330` 读取，`sdType` 由 `0x1982548` 读取；对象来源分别对应 `+0x40` 与 `+0xa8`，随 DTO 批次写入文件 v2 头部 |

### 3.2 Java字段与两种枚举差异（历史 wrapper 与当前 map DTO）

当前 map DTO 不复用 wrapper 的整数含义：`crossManeuverID=1/2/8` 分别归一为左／右／直；status `2/3` 归一为红、`4/5/6` 归一为绿、`8` 归一为黄，其它方向或 status 丢弃。`showType=3` 是主灯，`showType=2` 是次灯且仅接受直行 `8`；`lightCount=1` 时接受主／次两类，`lightCount>=2` 时仅接受主灯。主灯 status 8 不保留秒数，主灯 status 6 只有 `sdType=true` 才保留正秒；次灯 status 6/8 的正秒可保留，非正秒统一不显示。以上规则属于地图 DTO v2 的独立合同。

[CameraLightInteract](<../../source/amap-9.5.0.600013/smali/com/autonavi/amapauto/CameraLightInfo/CameraLightInteract.smali>)的精确落点为 `public static notifyCameraLightInfosImpl(Lcom/autonavi/amapauto/CameraLightInfo/CameraLightInfoWrapper;)V`。私有 `notifyCameraLightInfos(Parcel)V` 从Parcel解wrapper后进入此处，再回收Parcel。

[灯组包装](<../../source/amap-9.5.0.600013/smali/com/autonavi/amapauto/CameraLightInfo/CameraLightInfoWrapper.smali>)字段a是列表。[单灯模型](<../../source/amap-9.5.0.600013/smali/com/autonavi/amapauto/CameraLightInfo/CameraLightInfo.smali>)的 `toString()` 明确五个int：`a=waitNum`、`b=direction`、`c=status`、`d=countDown`、`e=showType`，没有距离、路口ID、坐标或时间戳。waitNum完整业务含义仍待核对，不能称排队车辆数。

- **历史 wrapper 合同：** 巡航方向1／2／3为左／直／右；0在插件中称调头，但原绘制无箭头。未知值不继承插件“其余都右转”的兜底。
- **历史 wrapper 合同：** 巡航灯态0红、1绿；原绘制数组也把2画成绿，但当前巡航native计算只输出0／1。当前 map DTO 的 status 2/3/4/5/6/8 见上方独立合同。
- 导航消费链方向1／2／4为左／右／直，状态使用1／4。**不能把导航与巡航的原始整数直接并入同一枚举。** 完整导航枚举和0方向语义仍需核对。
- 默认Parcel列表解码由[i50](<../../source/amap-9.5.0.600013/smali/i50.smali>)完成，数量0返回null，因此非null wrapper＋null list也表示空批次。

### 3.3 共享对象修改与消费者边界（历史 wrapper）

**应在原始回调处同步复制列表及全部字段，不能留共享wrapper稍后读取。** [FloatViewHelper$2](<../../source/amap-9.5.0.600013/smali/com/autonavi/floatwindow/FloatViewHelper$2.smali>)的 `run()V` 在 `showType==0` 时直接把原对象 `countDown` 改成 `-1`（第101～110行）；随后正数显示数字，0显示“通行”，负数无秒数。内容区即使取得原始数字，也应尊重showType的显示资格，不能强制显示被上游要求隐藏的秒数。

当前地图 DTO 通过原子文件传递四字段和 v2 元数据，不把 Java wrapper 暴露给内容区；Java reader 在 generation／生命周期门禁后复制 raw 与 `lightCount`、`sdType`，再交给不可变 Store 快照。文件桥的 Sink 是当前唯一可见接收入口。

[巡航语音消费者](<../../source/amap-9.5.0.600013/smali/floatapp/trafficlight/CruiseTrafficLightVoice.smali>)只是保存wrapper并每秒读取，使用自己的方向优先级、速度限制与语音去重。`getLastStatus()`依赖的更新方法没有实际调用链，不能作为内容快照API；null数据也没有完整超时／去重清空管理。

[nm](<../../source/amap-9.5.0.600013/smali/nm.smali>)的 `o(Wrapper)V` 转当前[fc](<../../source/amap-9.5.0.600013/smali/fc.smali>)样式。巡航[jm](<../../source/amap-9.5.0.600013/smali/jm.smali>)的 `i(Wrapper)V` 消费、清显示标记；导航[km](<../../source/amap-9.5.0.600013/smali/km.smali>)同方法为空。上述是显示消费者的模式／版本门槛，不是原生服务订阅开关，也不意味着内容区需要启用历史悬浮窗口。

## 4. 公开服务的能力边界

公开接口应区分路线设施信息与实时信号：

| 官方文档 | 实际公开能力／边界 |
|---|---|
| [Android导航SDK AMapNaviStep](<https://a.amap.com/lbs/static/unzip/Android_Navi_Doc/com/amap/api/navi/model/AMapNaviStep.html#getTrafficLightCount-->) | `getTrafficLightCount()`说明“获取该路段红绿灯总数”，自7.1.0；另有同义 `getTrafficLightNumber()`。这是灯数，不是灯色或秒数 |

| 官方站内索引核对 | 对[TrafficLightInfo](<https://lbs.amap.com/search?s=TrafficLightInfo>)、[AMapNaviTrafficLightInfo](<https://lbs.amap.com/search?s=AMapNaviTrafficLightInfo>)、[updateTrafficLightStatus](<https://lbs.amap.com/search?s=updateTrafficLightStatus>)均返回0条。本轮未找到这些名称对应的普通Android公开回调；索引未命中不等于高德完全没有内部／专门产品能力 |

因此不推荐仅申请普通Web Key就承诺调用与车机相同的实时信号服务，也不能断言高德所有SDK均不开放红绿灯。本项目已有两条内部输出，复用当前地图回调更直接。具体专门服务权限、费用、覆盖及服务端端点均没有本轮足够证据，不给出未经核实的限制结论。

## 5. 当前接入方案与剩余验证

1. 当前巡航可见入口是地图显示 DTO：`libGbl` converter 的 vector 与 `lightCount`／`sdType` 元数据由 `native-patches/cruise-map.S` 写入 version 2 的 `content-cruise-map.bin`；header32 使用 `magic/version/pid/vectorCount/timestampNs/lightCount/sdType`，正文为四整数项，临时文件完成后原子替换。
2. `ContentCruiseMapBridge` 在后台读取并校验文件，Sink 唯一进入 `ContentRuntime.acceptCruiseMapBatch`，再交 `ContentStore.acceptCruiseMapSignals(raw, lightCount, sdType, ...)` 和 `ContentPorts.fromMapRaw`。映射严格使用地图 DTO 合同：方向 `1/2/8` 为左／右／直，status `2/3` 红、`4/5/6` 绿、`8` 黄，未知值丢弃；`showType=3` 为主灯，`showType=2` 为仅直行次灯；`lightCount=1` 接受 2/3，`lightCount>=2` 仅接受 3。
3. 倒计时只保留原生允许的正值：主灯 status 8 无秒，主灯 status 6 仅在 `sdType=true` 时保留，次灯 status 6/8 的正秒可保留，非正秒只显示灯色。内容层沿现有 `ContentRuntime`／`ContentStore`／`ContentBinding`／Compose 链投影，不自行减秒、不读取语音缓存、不发起网络请求。
4. `CameraLightInfoWrapper` 及 `onCruiseSignalBatch` 保留为历史 HMI／语音合同和诊断复制；其旧方向 `1/2/3`、旧 status `0/1`、共享对象 `showType` 修改都不能作为当前地图 DTO 的归一化规则，也不再更新可见灯组。
5. 本地 Store／UI 定向测试、native v2 仿真、正式 APK 构建和车机批次采样由[巡航红绿灯沉浸顶栏验证记录](<../testing/巡航红绿灯沉浸顶栏验证-20261011.md>)统一维护。本研究本轮不填测试通过、APK 交付或实车三色／切灯结论；设备日志没有 batch 时，不把安装启动或静态夹具当作真实信号验证。

标准广播60073仍可作低侵入诊断或独立应用候选，但依赖协议连接／导出条件，不能替代当前地图 DTO 文件桥，也不能把广播接收成功当作上游巡航服务可用的充分条件。
