# 快捷车控与座椅主链对照审计（2026-10-09）

## 摘要

本审计依据当前高德 9.5.0.600013 正式源码、OEM 静态副本、已有宿主/Fake Binder 测试和研究记录。初次审计时车机离线；本轮按用户“车辆正在洗车，只分析代码与研究”的要求复核 Git `709eedd547c7`，没有执行 ADB、安装、车辆动作或共享 Gradle。§10 汇总本轮关闭未确认问题；本文明确区分当前代码、原厂发送协议、此前回读实测和仍待现场验证的事实。

当前主链可以概括为：

```text
Compose 控件
  -> ContentPanel 事件与可用性门禁
  -> ContentBinding 重新投影并分发
  -> ContentStore 保留 requestId/target/timeout
  -> ContentPorts.VehiclePort
  -> ContentVehicleAdapter 单 HandlerThread
  -> IVirturalCarProperty Binder sendData/getData
  -> 同一 worker 的 readback poll
  -> VehicleSnapshot / FeatureSnapshot
  -> ContentStore 只用新鲜 actual + known + predicate 确认
```

有五组结论直接解释新增快捷功能出现“发送后数秒提示状态未确认”：

1. `wiper_maintenance`、`glove_box`、`passenger_seat_adjust` 都是 `VehicleFeature.action`。UI/Store/Adapter 为前两个 action 放行并发出一次命令，但 `ContentStore.vehicleCommandConfirmedLocked()` 对 action 永远返回 `false`，按当前源码即使车辆执行也会在 6 秒后超时。维护 `671` 实际已有 RX `1/2` 研究证据，只是 Adapter 写死 `-1` 未接入；手套箱则没有可靠实体门状态。
2. 有三项确定的 TX 方向错误或协议语义错用：后雾灯当前关闭发 `542/0/1`，原厂 setter 固定发 `542/0/2`（RX 的 raw1 不能反推 TX）；儿童锁当前锁/解锁发 `1042/area/2/1`，原厂应发 `3/2`；中控亮度当前发 `[255,level]`，原厂 TX 是 `[1,level]`，`255` 只属于稳定 RX。它们属于代码／协议问题，不能归咎于车辆未及时回读。
3. 乘客车窗禁用的 `1041` 开1／关2、读回归一化和 Store 谓词与原厂一致；无线充电的 `568` 开2／关1也与原厂开关一致，但实际充电 `629` 未进入成功谓词。四窗发送1／5有研究依据，然而 `535` 四区读回与“全1／全5聚合”尚未在本车闭合；外放电 `602` 只看开关，未把 `604` 运行数组、连接和允许条件纳入谓词。
4. 车辆 adapter 的周期轮询、写命令和写后读回共用一个 `ContentVehicleReader` HandlerThread；每个 `readSnapshot()` 内又同步执行三十余个 Binder 读取，没有每事务超时。任何一个 OEM Binder 调用卡住、单轮某字段异常或回读混合，后续命令/快照都会排队或将字段改成 unknown，Store 的 6 秒命令超时仍会照常触发。这是车窗、禁窗、无线、外放电等“协议看起来正确但仍超时”的共同候选，需现场时间线才能定性。
5. 四路音量不走车辆 Store 的这句提示，而走 `AndroidSystemPort`／`ContentBinding` 的系统链，正常失败文案是“系统状态未确认”。当前 `write()` 要求写后立即读已经达到目标才返回 `accepted`；真实音频服务若异步应用，立即读旧值会让 `accepted=false`，随后250ms读回即使已达到目标也不会清除提示。现有 Fake 测试即时回写，未覆盖这个缺陷。

中控亮度的空数组、worker 阻塞、迟到读回和系统音量的即时读回属于确认时序问题；它们与上述确定的 TX 错误分开处理。

## 1. UI 到确认的实际调用链

### 1.1 座椅和新增特性

`ContentPanel` 对座椅/feature tile 先依据当前 `available`、`known`、`pending` 事实决定是否接收事件；事件进入 `ContentBinding` 后会重新用 Store 快照做一次门禁。相关入口见 [`ContentPanel.kt`](../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/ContentPanel.kt#L654-L736) 和 [`ContentBinding.kt`](../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/ContentBinding.kt#L270-L335)。

- 座椅点击进入 `cycleControlLevel()`、`setControlLevel()` 或显式 power/automatic 路径。
- 普通 feature 根据当前 actual 在 0/1 间切换；`feature.action` 则固定请求 target 1。见 [`ContentBinding.kt`](../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/ContentBinding.kt#L329-L335)。
- 座椅请求要求已有有效 actual/readback、车辆数据可用、adapter 可用、没有另一条 pending，并且目标与当前状态不同；见 [`ContentStore.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentStore.java#L972-L985)。
- feature 请求在一个全局 vehicle pending 槽中保存 feature id、target、requestId、6 秒 deadline；中心亮度也复用同一槽；见 [`ContentStore.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentStore.java#L997-L1057)。
- Adapter 的 `sendData` 返回或 `worker.post` 接受只表示传输被排队/发送，最终必须等新的 `VehicleSnapshot` 进入 Store，再由确认谓词比较 actual；接口注释也明确“transport only”和“readback confirmation remain separate”：[`ContentPorts.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentPorts.java#L446-L521)。

### 1.2 中控亮度

可见亮度竖条在 [`ContentPanel.kt`](../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/ContentPanel.kt#L524-L548) 读取 `state.brightness`。事件在 [`ContentBinding.kt`](../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/ContentBinding.kt#L347-L349) 进入 `store.setCenterBrightness()`，不是 `writeSystem(0)`。

`ContentUiMapper` 的 `state.brightness` 来自车辆 `FeatureSnapshot.centerBrightnessLevel`；它要求 level 1..10 且 known 才 available，见 [`ContentUiMapper.kt`](../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/ContentUiMapper.kt#L149-L175)。因此“屏幕亮度”与 Android Settings 亮度不能在现场排查时混称：当前可见 slider 的写入和读回都是车辆 `794` 数组。

### 1.3 系统音量

当前可见系统音量分为四类：

- `VolumeChanged`：媒体音量，kind 1、usage 1、audio group 0。
- `SystemVolumeChanged(CallVolume)`：通话，kind 2、usage 2、group 2。
- `SystemVolumeChanged(NavigationVolume)`：导航，kind 3、usage 12、group 1。
- `SystemVolumeChanged(VoiceVolume)`：语音，kind 4、当前查询 usage 11、group 3。

事件入口见 [`ContentBinding.kt`](../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/ContentBinding.kt#L347-L349)，映射和 Binder descriptor/transaction 见 [`ContentPorts.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentPorts.java#L74-L92)。代码注释同时提到 voice usage 11/16 都可能属于 group 3，但当前数组只实际查询 11；usage 16 是否需要兼容必须在目标车机确认，不能由当前注释代替现场证据。

## 3. OEM Binder 事务与原始协议

协议 owner 在 [`ContentVehicleProtocol.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentVehicleProtocol.java#L5-L100)：descriptor 是 `com.chery.canmanager.interfaces.IVirturalCarProperty`；scalar read/write 使用 `getData=7` / `sendData=5`，array read/write 使用 `getDataArray=8` / `sendDataArray=6`，float scalar 使用 `getDataFloat=13`。

### 3.3 中控亮度的空数组链

当前代码的完整链是：

```text
readSnapshot()
  -> getDataArray(0x31a, 0) [transaction 8]
  -> readIntArray()
  -> normalizeCenterBrightness(): 只有 [255,1..10] 才 known
  -> FeatureSnapshot.centerBrightnessKnown
  -> ContentStore.centerBrightnessKnown
  -> ContentUiMapper.state.brightness.available
  -> ContinuousVerticalControl.enabled = available && target == null
```

对应源码：

- 读与规范化：[`ContentVehicleAdapter.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentVehicleAdapter.java#L822-L832) 和 [`ContentVehicleProtocol.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentVehicleProtocol.java#L223-L226)。

- Store 覆盖 known：[`ContentStore.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentStore.java#L603-L630)。
- UI available 和 enabled：[`ContentUiMapper.kt`](../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/ContentUiMapper.kt#L169-L175) 与 [`QuickControls.kt`](../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/QuickControls.kt#L231-L275)。

因此，首次亮度请求可能已发出，但 1.5 秒后的下一次全量轮询若 794 暂时返回 `[]`，新 snapshot 会把滑条变成不可用；如果在 Store 的 6 秒窗口内没有 `[255,target]`，确认会超时。这是源码和已有研究现象可以共同支持的静态因果链；“目标车机必然在首次写后返回空数组”仍需现场抓 Binder 原始返回确认。

## 4. action 恒 false、超时和失联恢复

### 4.1 action 的静态确定根因

`VehicleFeature` 将维护雨刮、手套箱和副驾调节都标记为 action：[`VehicleControl.kt`](../../source/amap-9.5.0.600013/content-compose/model/com/icar03/content/model/VehicleControl.kt#L59-L78)。当前 capability 逻辑却对维护/手套箱的 target 1 直接放行，并对副驾调节直接返回 false：[`ContentVehicleAdapter.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentVehicleAdapter.java#L216-L236)。

发送包可以由 `featureWrite()` 生成（维护 `0x29f/0/2`，手套箱 `1046/0/2`），但读快照在维护处写死 `maintenance=-1`，FeatureSnapshot 又将 glove box 固定为 -1：[`ContentVehicleAdapter.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentVehicleAdapter.java#L801-L832)、[`ContentPorts.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentPorts.java#L578-L606)。

最终确认分支如下：

```java
if (feature != null) {
    if (feature.getAction() || feature == PassengerSeatAdjust) return false;
    return state.featureLevel(id) == pendingFeatureTarget;
}
```

见 [`ContentStore.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentStore.java#L1493-L1507)。所以对已被放行并实际发出的维护雨刮/手套箱请求，当前不是“可能慢”，而是“即使收到发送 ACK 也没有成功谓词”，六秒后必定进入失败结果；副驾调节则在 capability/write admission 阶段直接不可用。

### 4.2 timeout 的清理与迟到工作

Store 在创建每个 vehicle command 时设置 6 秒 timeout：[`ContentStore.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentStore.java#L1461-L1491)。timeout 调用 `finishVehicleCommandLocked(false, "车辆状态未确认，请查看车机状态")`，清除 pending/target/requestId，但不发送恢复或重试；feature/center brightness 只调用 `VehiclePort.cancelFeatureRequest()` 默认空实现，普通座椅 level 没有对应的 adapter 取消调用：[`ContentStore.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentStore.java#L1526-L1553)、[`ContentPorts.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentPorts.java#L497-L522)。当前 `ContentVehicleAdapter` 没有 generic `cancelFeatureRequest()` override。

generic `queueCommand()` 在入队时保存 binder，但 runnable 只检查 running、binder 身份和 worker 身份，不检查 request deadline 或 Store 是否仍有同一个 requestId；完成后无论发送是否被接受都触发一次读回：[`ContentVehicleAdapter.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentVehicleAdapter.java#L615-L657)。因此：

- 已经执行的同步 Binder 写无法被 Java Future 物理中断。
- 尚未执行但排在阻塞轮询后的 generic 写，可能在 Store 已超时后才执行。
- 晚到 snapshot 会更新 actual，但因为旧 pending 已清空，不会重新确认旧请求。
- 不应通过自动重发或补偿写来掩盖这种 late work；应在统一 command 层使用 requestId/deadline/binder generation 丢弃过期任务。

### 4.3 Binder 失联

`onServiceDisconnected()` 清除 binder、发布 unavailable，并重启轮询/绑定计时；`onBindingDied`/`onNullBinding` 进入 reconnect：[`ContentVehicleAdapter.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentVehicleAdapter.java#L160-L185)。Store 收到 unavailable snapshot 后立即把 pending 命令结束为“车控连接中断，命令未确认”，不会把本地 target 当 actual：[`ContentStore.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentStore.java#L631-L640)。重绑定成功后从 unavailable 开始重新读；用户需要在新鲜 known snapshot 后再次发起命令。

UI 侧 command failed 会进入反馈文本，并在 `ContentBinding.project()` 中显示 Store 的失败消息；反馈默认 3 秒后清除：[`ContentBinding.kt`](../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/ContentBinding.kt#L627-L650) 和 [`ContentBinding.kt`](../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/ContentBinding.kt#L750-L761)。pending 清除后，普通 feature 只要旧 actual 仍 known 就可再次尝试；action feature 由于 capability 被硬放行，也会再次可点，但仍会重复同一个必然超时的闭环。

## 5. 串行 worker、系统读写和恢复

### 5.1 车辆 worker

Adapter 启动一个名为 `ContentVehicleReader` 的 HandlerThread，先发一次 poll，之后每 1500ms 在同一 worker 上调 `readSnapshot()`；下一次 poll 只有在本次同步读取完成后才排队：[`ContentVehicleAdapter.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentVehicleAdapter.java#L68-L100) 和 [`ContentVehicleAdapter.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentVehicleAdapter.java#L513-L531)。

`readSnapshot()` 从 gear、温度、SOC、充电、座椅、锁、雨刮、所有新 feature 到 794/外放电数组连续执行 scalar/array Binder 读取，见 [`ContentVehicleAdapter.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentVehicleAdapter.java#L765-L875)。写命令也投递到这一个 worker，发送 finally 再触发同一 worker 的即时读回：[`ContentVehicleAdapter.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentVehicleAdapter.java#L615-L657)。源码没有单个 Binder transaction 的超时；`readInt/readFloat/readIntArray/readFloatArray` 只在返回异常后把事实变为 -1/空列表：[`ContentVehicleAdapter.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentVehicleAdapter.java#L928-L1017)。

这意味着一处卡住会造成一个共同表象：车控按钮发送后没有新的读回、中心亮度滑条在 unknown/old state 上、后续车控全部像“不响应”。静态上可以确定存在这个阻塞拓扑；卡住的是哪个 function、是否由 OEM Binder 权限或服务端队列造成，则必须看现场 Binder 日志或车机行为。

### 5.2 AndroidSystemPort 与五个系统 channel

`ContentBinding` 维护另一条 `systemWorker` 单线程执行器。每次系统轮询按固定顺序串行读取 kind 0..4，再读 screen-clean capability：[`ContentBinding.kt`](../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/ContentBinding.kt#L464-L509)。每次 system write 也在同一 worker 中执行：先读目标 kind，写入，再读完五个 kind；首轮回调清 target、评估结果，然后 250ms 后再发一轮五通道确认读：[`ContentBinding.kt`](../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/ContentBinding.kt#L511-L580)。

`AndroidSystemPort` 的 kind 0 读取/写入 Settings.System；kind 1..4 先绑定 `com.mengbo.media`，校验四个 usage→group 映射和范围，再通过 ICarAudio transaction 1/4 写读。绑定等待上限为 300ms，失败后的下一次绑定间隔为 1s，但单次 Binder `transact()` 本身没有超时：[`ContentPorts.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentPorts.java#L242-L302)、[`ContentPorts.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentPorts.java#L305-L400)。服务失联会清空 root/binder/ranges，后续读取重新绑定：[`ContentPorts.java`](../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentPorts.java#L402-L425)。

系统写确认与车辆写确认有两个差异：

- `AndroidSystemPort.write()` 自己会立即 `read(kind).matches(target)`；Binding 随后还要读五个通道和 250ms 后再次读。
- Binding 在首个读回不匹配时会暂时显示“系统状态未确认”，但不会自动 resend；延迟读回达到 target 才清除提示。request sequence、generation 和 latest kind request 防止旧任务改写新结果，但正在执行的同步 Binder 仍无法物理取消。

已有 [`ContentBindingDomainsTest.kt`](../../ui-preview/content-runtime/src/test/java/com/icar03/content/runtime/ContentBindingDomainsTest.kt#L88-L125) 证明阻塞 system read 不阻塞媒体/时钟且不在主线程；[`ContentBindingDomainsTest.kt`](../../ui-preview/content-runtime/src/test/java/com/icar03/content/runtime/ContentBindingDomainsTest.kt#L170-L187) 证明 250ms 延迟读回可消除提示；[`ContentBindingDomainsTest.kt`](../../ui-preview/content-runtime/src/test/java/com/icar03/content/runtime/ContentBindingDomainsTest.kt#L216-L250) 证明 stop/restart 能隔离迟到任务，但测试替身不会证明目标 audio Binder 的真实时延。

## 8. 未来统一主链方向

不建议继续给每个新按钮加独立的“发送后等几秒”分支。建议统一成一条可审计的 command contract，同时保留 property-specific raw codec：

1. 每个 request 统一保存 `requestId`、target、deadline、Binder generation、raw write packet、readback source/type/area、known predicate 和单一 pending owner。发送回调只表示 transport result；只有同 generation 的 fresh readback 满足 predicate 才能完成。
2. 把 `ToggleFeature`、`ActionFeature`、`CenterBrightness`、seat level 和 rear-window pulse 区分成不同 command kind。action 若没有可读 actual 或 OEM callback，就只能显示“已请求/等待车机反馈”或暂不可用，不能使用永远 false 的确认器伪装成可完成按钮。
3. 对 794 等有暂时空返回的数组保留“本轮 unknown”和“上次展示值”两个概念：空数组不能参加成功谓词，也不能被解释成 0；在同一 Binder generation 且未超过 deadline 时可以继续等待有效样本，超过 deadline 必须明确失败。
4. 车辆 polling、command write、readback 需要有取消/过期检查和 Binder generation；queued work 在真正发包前再次检查 deadline/pending owner。正在执行的 Binder 无法物理取消时，必须把晚到结果标为 late observation，禁止为旧 request 重启确认。
5. 大型全量 snapshot 不能无限阻塞命令。应至少记录每个 function 的耗时和失败类型，并在 adapter 层隔离慢属性；若采用独立线程/进程执行 Binder，应以 generation 丢弃旧读回，避免并发读把旧状态覆盖新状态。
6. 系统 channel 与车辆 channel 可以拥有不同 transport，但复用相同的 `requestId → target → readback → delayed confirmation → recovery` 语义；系统 Brightness kind0 与车辆 794 必须在模型和 UI owner 上保持单一明确来源。
7. 失联、timeout、malformed/empty、permission failure、late readback 要进入同一结构化状态，日志至少记录 requestId、generation、function/area、transaction、send timestamp、readback raw、known reason 和 deadline；禁止自动 restore write 或无条件重发。

## 9. 建议的回归矩阵

- **协议**：对每个 feature 断言 transaction、function、area、raw target 及 target 0/1；对 794 断言 transaction 6/8、`[255,1]` 到 `[255,10]`，拒绝空/坏形状。
- **正式 Adapter**：Fake Binder 实现 transaction 5/6/7/8/13；分别覆盖 scalar、array、float array、异常、空返回和 malformed 返回。
- **action**：维护雨刮/手套箱发送后若没有 callback/readback，确认必须保持 pending 到 deadline 后失败，且测试明确写出不会因为 send return 成功；有真实 callback/状态字段后再增加成功谓词。
- **亮度**：`[] -> [255,7]` 在 deadline 内最终确认；连续 `[]` 到 6 秒失败；unknown 不应转成 level0，也不应发送自动恢复值。
- **worker**：让一个 `getData` 阻塞，验证 poll、command、readback 的排队顺序；timeout 后释放 Binder，验证迟到写/快照不会确认旧 request；下一代 Binder 的快照不能被旧 generation 覆盖。
- **失联恢复**：send 前、send 中、readback 中断开 Binder，均清 actual/known 和 pending；重新绑定得到 fresh snapshot 后只允许显式重试。
- **feature 语义**：无线充电 switch 与 actual state 不一致时不得误报 operating success；外放电 switch 与七项 status 不一致时保留未确认。
- **系统音频**：验证 usage 1/2/12/11 的 group 0/2/1/3、离散范围 tolerance、250ms delayed confirmation、audio Binder disconnect/rebind；在目标设备确认 usage 16 是否同属 voice。
- **UI**：确认可见 Brightness 只走 `setCenterBrightness()`/车辆 794；系统 kind0 的 Android Settings 旁路不能悄然改变车辆 slider；action button 不因注册存在就获得假的成功动画。
