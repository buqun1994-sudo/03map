# iCAR 03 车机控制能力扩展研究（2026-10-08）

> **职责：** 记录 iCAR 03 当前车机控制目标的静态来源、普通 UID 只读回读、用户实体操作、恢复结果和未验证边界。本记录是车控适配的研究输入，不代表正式地图 APK 已接入这些能力。
>
> 本轮目标包括后雾灯、后排车窗禁用、前雨刮维护、手套箱、左右后排儿童锁、中控屏亮度、手机无线充电开关、四个侧窗透气、副驾电动座椅、蓝牙、Wi-Fi、媒体／通话／导航／语音音量、清洁屏幕和外放电。用户明确要求车窗只提供“全关／透气”二态，不提供全开。

## 1. 研究条件与证据规则

设备是 iCAR 03，车型 `S56_HQX`，Android SDK 28。研究使用普通 UID 的临时 `ControlsRead15` APK；原始设备 serial、完整 logcat 和 APK 保留在本机忽略目录，正式文档只记录车型、接口和脱敏结果。

本轮动态流程固定为：用户改变一个可逆状态 → 只读探针采集 → 用户用原车操作恢复 → 再次只读采集。车辆 setter、写事务、回调注册和探针恢复命令均为零。每次探针完成行均应为：

```text
COMPLETE writes=0 bindingsReleased=true
```

证据等级统一使用：

- **静态确认：** 原厂 CSV、反编译 OEM/SystemUI 或服务接口给出编号、区域、类型和命令映射。
- **实机确认：** 用户完成实体或车机操作，且取得状态回流或用户明确观察到实体动作；若回读不完整，会在结论中单独标出。
- **实验参考：** 只读快照或相邻字段可帮助理解，但不能独立证明目标语义。
- **待验证：** 需要正式地图 APK、订阅、失败回调、Binder 断开、超时或其它现场条件才能确认。

本轮动态原始摘要保存在 [controlsread-20261008-dynamic.md](<../../.tmp/vehicle-controls-15.9XVju4/controlsread-20261008-dynamic.md>)。只读探针源码在 [ControlsReadService.java](<../../.tmp/vehicle-controls-15.9XVju4/probe/src/com/codex/controlsreadprobe/ControlsReadService.java>)；本轮没有修改正式 `source/` 产品代码。

## 3. 原始接口与状态回流

### 3.1 Vehicle Binder

车机属性服务 descriptor 为：

```text
com.chery.canmanager.interfaces.IVirturalCarProperty
```

本轮只读探针使用：

| 用途 | Binder 事务 | 参数形态 | 说明 |
|---|---:|---|---|
| 整数属性读取 | `7` | `function, area` | `getData(II)` |
| 数组属性读取 | `8` | `function, area` | `getDataArray(II)`；亮度和外放电状态使用 |
| 浮点属性读取 | `13` | `function, area` | 作为后续浮点读候选；本轮探针未写入任何值 |

OEM `SignalManager` / `VehicleRepository` 的已定位入口包括：`getData(int,int)` vtable `12`、`getDataArray(int,int)` vtable `13`、`getDataArrayObject(int,int)` vtable `14`、`sendData(int,int,int)` vtable `31`、`sendDataArray(IILjava/util/List;)` vtable `35` 和 `sendSeatData(int,int,int)` vtable `37`。这些静态入口不等于普通 UID 已取得正式写入权限，也不等于写入后车辆接受请求。

### 3.2 车控请求不能代替成功状态

正式适配器对每个可写能力都应按下列顺序实现：

```text
新鲜读取实际状态
    ↓
确认当前没有其它 pending 请求
    ↓
发送一次目标请求
    ↓
等待自身属性的 callback 或有界 readback
    ↓
比较车辆实际状态与目标
    ↓
成功 / 拒绝 / Binder 断开 / 超时 / 数据形态错误
    ↓
释放 callback 和 worker，保留可恢复诊断
```

发送返回、按钮动画结束和本地目标状态都不能单独形成成功结论。回读为空数组、数组长度错误、属性值不在已知枚举、服务断开或回调迟到时应进入 `UNKNOWN`／失败态，并停止重复发送。

本轮具体观察到的亮度空数组尤其说明：写后马上调用 `getDataArray(794,0)` 可能得到 `[]`，稍后稳定读取才得到 `[255,7]`；系统日志同时出现 `brightness changed 7`。因此亮度适配器必须允许回读延迟和空向量，不能把空数组当作第 0 档或把本地 slider 草稿当作车辆成功。

### 3.3 状态请求与实际功能的分离

下列目标明确需要至少两个状态字段或两个事实来源：

- 无线充电：`568` 是开关请求，`629` 是实际充电状态；本轮关闭请求期间 `629` 仍为 `0`。
- 后雾灯：`542` 是后雾灯请求／状态候选；前灯光模式 `541` 和实体灯是否真正点亮必须独立确认。
- 手套箱：`1046` 是开箱请求，实体门状态没有稳定回读；`glove_lock_status` 是门禁，不是门体位置。
- 前雨刮维护：`671=2` 表示维护请求／维护态，必须通过雨刮实际回位和 `671=1` 确认恢复。
- 外放电：`602` 是允许／输出开关候选，`604` 是运行状态数组；不能用开关值代替实际负载电流或功率。
- 车窗透气：`0x217/0x550=1` 是透气命令，`0x217/0x550=5` 是全关命令；命令发送完成不证明四块玻璃已到位，`535` 分区回读仍需单独接入。

## 4. 各能力的静态来源与现场说明

### 4.1 灯光、车窗禁用和儿童锁

CSV 属性定义在 [S56_202306161348.csv](<../../.tmp/research-20260926/decode/virtualcar/assets/S56_202306161348.csv>)。后雾灯的 SystemUI 入口在 [LightModeControllerImpl.smali](<../../.tmp/icon-inventory-20260928/systemui-code/smali_classes2/com/mb/systemui/qs/lightmode/LightModeControllerImpl.smali>)，后排车窗禁用、两侧儿童锁、后雾灯等 OEM 发送映射在 [SignalManager.smali](<../../.tmp/vehicle-lights.7HB3BK/control-15-oem/dex5/com/chery/signalmodule/SignalManager.smali>)。

后雾灯现场顺序是关闭 `542/0=1`、用户打开后 `2`、用户关闭后 `1`。车机 UI 可能在点击后延时刷新，正式 UI 应只消费自身回读并处理拒绝和超时。前灯光模式使用 `0x21d/541`；`0x31a/794` 是中控显示亮度，早期把它当作前灯光模式的说法已纠正。

后排车窗禁用使用 `1041/0`，用户将其打开时读到 `1`，恢复关闭后读到 `2`。儿童锁写入使用 `1042`，回读使用 `1048` 的相同左右区域，左 `0x10` 和右 `0x40` 分别独立从 `1` 变为 `2` 再回到 `1`，所以 UI 不能用一个总开关覆盖两侧。

### 4.2 中控亮度与无线充电

亮度 SystemUI 入口使用 `0x31a/794` 的数组第二项，setter 接受 `1..10` 并发送 `[1,value]`；仪表／集群亮度是独立的 `0x23c/572` 标量，不能共用一条 UI 状态。现场从第 7 档拖到最大后读到 `[255,10]`，恢复过程先出现 `[]`，再由 `MBBrightnessManager` 记录 `brightness changed 7`，稳定回读 `[255,7]`。

无线充电 SystemUI 入口在 [WirelessChargeControllerImpl.smali](<../../.tmp/icon-inventory-20260928/systemui-code/smali_classes2/com/mb/systemui/qs/wirelesscharge/WirelessChargeControllerImpl.smali>)；实际充电状态由 [WirelessChargedManager.smali](<../../.tmp/icon-inventory-20260928/systemui-code/smali_classes2/com/mb/systemui/statusbar/policy/WirelessChargedManager.smali>)读取另一个属性。现场关闭请求时开关 raw 为 `1`，实际充电 raw 仍为 `0`；这正是请求状态和实际功能状态必须分开的运行证据。

### 4.3 前雨刮维护、手套箱和清洁屏幕

前雨刮维护的 SystemUI 代码在 [FrontWiperMaintennaceControllerImpl.smali](<../../.tmp/icon-inventory-20260928/systemui-code/smali_classes2/com/mb/systemui/qs/frontwipermaintennace/FrontWiperMaintennaceControllerImpl.smali>)。它读取 `0x29f/671`，active 使用 `2`，setter 始终发送 `2`。现场触发后 `671=2` 持续存在，雨刮臂处于维护位置；用户用正常雨刮关闭／回位后 `671=1`。因此正式能力名应是“前雨刮维护”，而不是普通可反复切换开关。

手套箱的请求入口在 [EGlovesBoxControllerImpl.smali](<../../.tmp/icon-inventory-20260928/systemui-code/smali_classes2/com/mb/systemui/qs/eglovesbox/EGlovesBoxControllerImpl.smali>)。实体操作确认车机点击后手套箱正常打开，但 `1046` 在采集时为 `0`，说明该字段不能作为稳定门体状态。按钮还会读取 `glove_lock_status`；该键属于密码／代客门禁判断，空值不能解释为“门已关闭”。产品只需要一次打开动作和失败提示，不需要把手套箱做成开／关切换。

清洁屏幕的入口在 [ScreenCleaningControllerImpl.smali](<../../.tmp/icon-inventory-20260928/systemui-code/smali_classes2/com/mb/systemui/qs/screencleaning/ScreenCleaningControllerImpl.smali>) 和 [ScreenCleaningBtn.smali](<../../.tmp/icon-inventory-20260928/systemui-code/smali_classes2/com/mb/systemui/qs/screencleaning/ScreenCleaningBtn.smali>)。静态实现用 `597/0` 的 P 挡值 `11` 控制按钮可用性；点击打开全屏覆盖层，长按 3 秒退出，控制器自身不写车辆属性。现场 `screen_clean` 在进入时为 `1`、退出后为 `0`，形成了覆盖层生命周期的实机回流。

### 4.4 四个侧窗的全关／透气二态

OEM 映射在 [SignalManager.smali](<../../.tmp/vehicle-lights.7HB3BK/control-15-oem/dex5/com/chery/signalmodule/SignalManager.smali>)：

| 用户状态 | 函数 | area | value | 对外语义 |
|---|---:|---:|---:|---|
| 透气 | `0x217` | `0x550` | `1` | 对四个侧窗各开一条缝 |
| 全关 | `0x217` | `0x550` | `5` | 二态按钮的关闭／恢复目标 |
| 50%／75% | `0x217` | `0x550` | `2/3` | 不纳入产品 |
| 全开 | `0x217` | `0x550` | `4` | 不纳入产品 |

用户现场确认“车窗透气”确实让主驾、副驾、左后、右后四个玻璃开缝，随后用“车窗全关”恢复。车机探针当时既有的 `539/0` 读取属于 `BODY_WINDOW_SUNROOF_STATE` 天窗字段，值保持 `2`，与四侧窗动作无关，已从本结论排除。CSV 中的 `WINDOW_POS=535` 提供 `0x10/0x40/0x100/0x400` 分区定义，可作为四窗实际位置回读候选；本轮已安装探针没有取得这些四区的动态数据，所以当前只把命令值和用户实体动作标为确认。

正式二态控件必须区分“目标已发送”和“四窗全部全关／透气已回流”。任一窗拒绝、断连、超时或四区状态不一致时显示未知／失败，不自动重复发送全关或透气恢复命令。

### 4.5 副驾座椅

静态 OEM 入口包括 `sendSeatData(int,int,int)`；普通只读快照中副驾位置候选字段 `590/0`、`591/0`、`592/0` 均为 `0`。用户说明车机没有副驾座椅调节页面，改用副驾实体电控按钮前移约 1 秒，再后移约 1 秒；两次探针的三个字段均为 `0`。因此当前可以确认实体按钮动作发生，但不能确认这三个字段是位置百分比、目标位置、回中值还是普通 UID 的不可见字段。

正式产品若要接入副驾座椅，应逐轴确认前后、靠背、腿托和停止命令，明确发送方向、callback、位置读回、拒绝和超时。坐垫升降不在本轮已确认范围内，不能从三个零值推导出支持。

### 4.6 音频、蓝牙和 Wi-Fi

音频根 descriptor 为 `com.mengbo.media.client.IAudio`，lookup 后返回 `com.mengbo.media.client.ICarAudio`，服务 action/package 为 `com.mengbo.media.IAudio` / `com.mengbo.media`。本轮只读事务是 group count `22`、usage 映射 `23`、max `2`、min `3`、current `4`。当前映射与快照如下：

| 业务流 | usage | group | 当前值 | 范围 | 动态结论 |
|---|---:|---:|---:|---:|---|
| 媒体 | `1` | `0` | `3` | `0..31` | 一格调高后 `3→4`，恢复 `→3` |
| 导航 | `12` | `1` | `5` | `0..10` | 未制造导航播报 |
| 通话 | `2` | `2` | `15` | `1..31` | 未制造 HFP 通话 |
| 语音 | `11`、`16` | `3` | `7` | `2..10` | 未制造语音会话 |

读取可达不等于写入和 callback 可达；正式音量适配必须按实际音频焦点和当前流确认写后回读。通话、导航和语音不能用媒体组的动态结果代替。

蓝牙 vendor service 为 `mb.bluetooth`，只读结果与 Android Adapter 结果一致地表示当前已启用且 HFP/A2DP 已连接。用户明确跳过关闭／开启，原因是会断开当前连接；因此本轮没有写入或回调证据。Wi-Fi 只使用 Android SDK 28 的公共状态读取，结果为已启用、已连接、详细状态 `CONNECTED`。不读取 SSID、MAC、扫描结果、保存网络或凭据；用户也明确跳过 Wi-Fi 切换，以免中断当前无线 ADB 采集。

### 4.7 外放电

相关静态来源是 [FragmentPowerChargeDischarge.smali](<../../.tmp/vehicle-lights.7HB3BK/control-15-oem/dex4/com/chery/carsettingmodule/ui/fragment/FragmentPowerChargeDischarge.smali>) 和 [SignalManager.smali](<../../.tmp/vehicle-lights.7HB3BK/control-15-oem/dex5/com/chery/signalmodule/SignalManager.smali>)。源码读取外放电允许开关、SOC 限值、连接状态和七元素状态数组，并根据连接态和开关状态决定页面控件是否可用；启动／停止还涉及输出允许和确认路径，不能只依赖一个按钮返回值。

本次用户具备兼容放电负载，在安全停车条件下按原车页面完成了启动和停止。启动前状态为：

```text
602/0 = 1
601/0 = 20
604/0 = [0, 0, 1, 0, 0, 0, 0]
```

启动后状态为：

```text
602/0 = 2
601/0 = 20
604/0 = [0, 1, 0, 0, 0, 0, 1]
```

用户随后按原车流程停止，确认负载断电；停止后回到：

```text
602/0 = 1
604/0 = [0, 0, 1, 0, 0, 0, 0]
```

这已经确认开关和七元素数组会随真实外放电启停变化，并形成启动／停止恢复闭环。数组的第 0、1 项被 OEM UI 用于逆变器电流／功率相关显示，但完整七项枚举、单位、第三方可见的确认状态和错误码仍未取得；正式产品必须把“允许、连接、输出中、实际功率、停止完成、异常”拆成独立状态。

## 5. 当前可落地的正式控制合同

研究结果支持以下能力进入正式适配器设计，但不支持把研究探针直接当正式实现：

1. 只读快照由车辆适配器统一拥有，向 UI 发布带时间戳、来源、属性健康和 `known/unknown` 的不可变状态。
2. 每个可写能力拥有自己的 request id、目标值、开始时间、deadline、Binder 代际和回读 predicate；同一能力只允许一个 pending。
3. 只有自身 callback 或新鲜回读匹配目标，才把 UI 标为成功；用户按钮动画、发送返回和本地草稿不构成成功。
4. Binder 断开、权限错误、拒绝值、数组为空／长度错误、超时和迟到事件都进入失败或未知态；不自动重发，不盲写恢复命令。
5. 需要恢复的动作由用户或原车流程完成：亮度恢复第 7 档、前雨刮正常回位、四侧窗全关、外放电按原车停止；适配器只观察和确认，不替用户偷偷补发。
6. 正式地图 APK 仍需在同包身份下验证服务绑定、生命周期、订阅／回调释放、进程重启和 UI 状态投影；本轮普通 UID 独立探针的成功不替代这些验证。

| 优先级 | 项目 | 当前缺口 |

| 1 | 四侧窗回读 | 将 `WINDOW_POS=535` 的四个区域接入只读探针，确认全关与透气是否能由四区共同判定；不引入全开控制 |
