## 结论与证据等级

已连接当次身份核验通过的 `S56_HQX / SDK 28`。现场确认蓝牙会话正在播放、`PlaybackState.speed=0.0`，地图实际接收了新 sequence 的同值位置和带有小幅时间偏差的位置回报。当前时钟对每个有效 AVRCP 位置立即重锚，因此连续播放时，新的绝对位置即使比上一条更大，也可能小于上一锚点在当前时刻的外推位置；逐字填充直接消费该位置，能撤回已亮字符。

证据分级：广播、位置回报及安装身份为**实机确认**；接收时间重锚和渲染消费关系为**静态确认**；日志时间差推算为**离线数值分析**，不等于逐帧车机截图测量。手机当前 App 身份未由车机数据确认；Apple Music、QQ、网易云同机同录音对照未执行，因此“Apple Music为何更频繁”仍是需要平台对照的假设，不能写成 Apple 内部实现缺陷。

诊断阶段只读取设备状态和正式源码，保留原工作树改动；没有改变播放、安装候选、下发车控或修改运行代码。

## 现场位置与短回跳

[统计脚本](<../../.tmp/bt-lyric-investigation-20261005-134805/analyze_positions.py>)解析 `ContentMediaAdapter: AVRCP accepted`，只选 `state=3` 且 position 非负的记录，按当前播放中 speed0 回退为 1x 的规则，计算：

```text
校正差 = 新位置 − (上一位置 + 两次有效位置之间的接收时间差)
```

该差小于零代表硬重锚会回拉本地时钟；原始 position 未必下降。统计不包含完整 MediaSession 回调交错，也不记录实际 draw，因此只作为机制和量级证据，不声称每次回拉都在显示器上画出了一个反向帧。

稳定首段 29.871 秒：共 146 条 accepted 事件，其中 86 条有效播放位置；28 次新 sequence 同值位置，按重锚规则回拉 6—57ms，中位 21.5ms；另有 24 次变化位置的负校正，8—145ms，中位 53ms。此首段原始 position 数值没有一次下降。完整输出见[统计结果](<../../.tmp/bt-lyric-investigation-20261005-134805/position-analysis.json>)及[位置表](<../../.tmp/bt-lyric-investigation-20261005-134805/logcat-initial-positions.csv>)。

可复核示例：

| 接收时刻 | sequence | 原始位置 | 当前 1x 重锚规则的含义 |
|---|---:|---:|---|
| 13:47:44.048 | 4290 | 106639ms | 建立位置锚点 |
| 13:47:44.069 | 4291 | 106639ms | 同值晚到约 21ms，重设锚点会回拉约 21ms |
| 13:47:44.232 | 4294 | 106726ms | 距上一锚点 163ms，本地预计 106802ms，新位置只增加 87ms，硬对齐会回拉约 76ms |

实时片段还确认一次原始位置本身的轻微反向：13:49:26.591 的 `209147ms` → 26.597 的 `209127ms` → 26.620 的 `209147ms`。因此既有“原始位置增长但外推后回拉”，也有多入口位置之间的小幅数值差异；不需要假设歌曲音频发生了真实倒播。

## 业务主链与已有门禁的空缺

1. [ContentMediaAdapter.acceptAvrcpEventLocked()](<../../source/amap-9.5.0.600013/content-src/com/autonavi/amapauto/content/ContentMediaAdapter.java#L514>)验证来源、token、录音、曲长和生命周期后，把每条可用广播的 position 写入快照，并在 566—569 行使用本地接收时间和新 sequence。相同位置也获得新的事件身份；TRACK 中的 PlaybackState 只读取 position，未将其原始发布时间作为该 AVRCP 样本的时间依据。
2. [ContentLyricsTimeline.update()](<../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/lyrics/ContentLyricsTimeline.kt#L38>)只屏蔽已经消费的 sequence；新 sequence 且接收年龄在 0—1500ms 内，就把位置交给唯一 tracker。
3. [MediaSessionTimelineTracker.update()](<../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/lyrics/MediaSessionTimelineTracker.kt#L185>)对每个有效 AVRCP 样本直接替换 `basePositionMs / capturedAtElapsedRealtime`，没有同值新事件去重或小幅相位误差处理。其 170—175 行的发布时间倒序门禁约束 MediaSession 报告位置，不能代替 AVRCP 接收样本防抖；`effectiveSpeed()` 在播放中把设备报告的 0 回退为 1x。
4. [ContentUiMapper.mapLyrics()](<../../source/amap-9.5.0.600013/content-compose/runtime/com/icar03/content/runtime/ContentUiMapper.kt#L177>)传递 canonical anchor；[WallpaperLyrics.lyricPositionAt()](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/WallpaperLyrics.kt#L511>)按同一 elapsedRealtime 外推，只有未知／起点／曲长边界，没有小回拉过滤；[LyricReveal.sample()](<../../source/amap-9.5.0.600013/content-compose/ui/com/icar03/content/ui/LyricInkRenderer.kt#L146>)允许词内 fraction 下降，反向移动填充前沿。字符未完成的上浮也随位置重算。

03歌词当前[正式 tracker](<../../../03lyrics/app/src/main/kotlin/com/ninepointnine/desktoplyrics/MediaSessionTimelineTracker.kt#L167>)同样直接接收有效 AVRCP 新锚点；其已有进度恢复、来源／录音隔离和旧 MediaSession 回报门禁不能作为“所有小回拉都已防抖”的证明。本轮只读对照了参考源码和相关测试，没有向该独立仓库迁入地图事实。

[执行输出](<../../.tmp/bt-lyric-investigation-20261005-134805/timeline-static-harness-output.txt>)确认编译退出 0，22 项诊断断言通过。这些断言刻意验证当前问题行为，不能理解为回跳已修复：

这是正式时钟源码在隔离 JVM 中的行为复现；现场屏幕每帧回退幅度、手机端平台身份及三平台差异仍未测量。

## 平台差异、备选原因与建议

音频传输和进度回报是不同链路。当前适配器把手机端媒体统一观察为蓝牙来源，不能从选中会话可靠识别 Apple Music、网易云或 QQ。平台身份不可见不意味着其回报数据、快照新鲜程度和通知节奏相同：手机播放器／系统提供的进度，经过车机蓝牙栈的查询、通知及 MediaSession 转发后，可能呈现不同的样本时间差。现场已经证实多入口及重锚放大误差；哪个手机平台产生更大的偏差需要同一手机、同一录音／版本的对照，不能猜成 Apple 独有协议、歌词 Provider 或均为整秒精度。

同歌正文／词轴升级能在媒体位置不下降时重新分配亮字，是一次正文版本变化的备选。纯滚动改变整行几何，不改变词内时间；cold→prepared 能产生一次亮度／清晰度／上浮变化，不改媒体时钟。当前上游证据足以解释连续小回跳；没有逐帧实证时，不把理论上的新 anchor 与旧 frameElapsed 短暂组合升级为额外根因。

推荐在既有唯一媒体时间线 owner 内处理：短窗口内的冗余位置不重复建立时间锚点；有可靠原始样本时间时保留它，只有接收时间时按有限精度样本准入；同录音稳定连续播放的微小相位差通过短时放缓／加快逐步校正，避免直接撤回可见进度。明确 seek、切歌、暂停／恢复及持续确认的新时间轴仍需准确响应。仅依赖 position 数值无法完美区分细小手机 seek 与噪声，具体判据、阈值及响应延迟需由回放和现场对照约束。

不要在每个字形内部无条件取历史最大 fraction：那会破坏回退拖动、重播和录音切换。最低后续验证应覆盖真实日志重复／负校正、前后 seek（含 0 与小 seek）、暂停恢复、切歌、同曲版本补齐及三平台对照；优先记录同一 now 下旧、新 anchor 的 sample 差，异常无法解释时再补实际 draw position、正文版本和 prepared/fallback 状态。
