# 车机摄像头实时画面可行性研究

## 1. 本轮结论与边界

第一阶段对当前在线 `S56_HQX / SDK 28` 做只读设备检查，并提取原厂 APK 静态分析；该阶段未安装探针、未打开摄像头或写车属性。随后用户明确同意独立测试APK安装及同步打开原厂360检查冲突，第二阶段的当前探针身份与实测结果见第7节。静态研究与实测结论分开，不把单路视频成功等同于原厂360无冲突共存。

| 能力 | 当前结论 | 证据等级 |
|---|---|---|
| 从自定义按钮拉起原厂环视 | 原厂 SystemUI 具有明确启动链；本车车型标识为23，目标是 DJI `SplashAvmActivity` | 静态确认＋实机车型确认；本轮未启动 |
| 自定义界面显示环视视频 | 普通应用UID已通过camera 0取得1280×720鸟瞰＋广角合成视频；约20fps | 实机确认，独立探针；正式地图未接入 |
| 原厂环视视角切换 | 已追踪2D/3D视角到 `sendData(0x40a,0,list)`；本应用权限与状态回流仍待核验 | 静态确认，未实写 |
| 自定义界面显示行车记录仪视频 | 找到 `NativeOpengl.play(Surface)`，原生库连接 `dvr_screen` 本地socket并渲染 | 静态确认接口＋实机socket存在；第三方读取待验证 |
| 前后左右各物理摄像头独立显示、同时显示 | 尚不能确认；Android只枚举两路逻辑设备，不等于所有物理摄像头 | 待验证 |
| 智驾原始相机画面 | 尚无接入证据；不能因存在环视视频就推断可读取智驾原始传感器 | 待验证 |

“控制摄像头”应拆为：启动原厂页面、读取视频、切换设备输出视角、录制/拍照。它们不是同一个接口；本轮不扩大到录像控制、标定或驾驶功能控制。

## 3. 实际原厂环视路线：DJI

### 3.1 为什么不是优先研究 Mengbo AVM

已有 SystemUI 样本的 `OpenAvmBtnView.openAvmApp()` 根据 `vendor.cartype.version` 分支：22/23启动 `com.dji.autoivi/com.dji.autoivi.ui.SplashAvmActivity`，其它值才启动 `com.mengbo.avm/com.mengbo.avm.views.MainActivity`。

样本锚点：`.tmp/research-20260926/decode/systemui/smali_classes2/com/mb/systemui/qs/openavm/OpenAvmBtnView.smali:39–115`。本轮读出的23与该分支对应。

本轮提取 `/system/app/MB_DJIAdas/MB_DJIAdas.apk`，解包至 `.tmp/camera-research/dji-decode/`：

- Manifest:2原厂应用使用 `android.uid.system`；:5声明CAMERA。
- Manifest:53–58 `SplashAvmActivity`明确exported，具备原厂页面启动入口。
- Manifest:59–78声明对外Auto/State/Data/Navigation服务。服务exported不等于提供视频流，也不保证所有事务无额外权限检查。

### 3.2 已追踪的视频数据面

1. `smali_classes2/com/dji/is_avm/AvmLayout.smali:1787–1861`：从 `videoRendererView` 的TextureView获取SurfaceTexture，创建Surface，保存至 `CameraProxy.e`，投递打开任务。
2. `smali_classes3/u5/a.smali:114–165`：真实AVM业务任务调用 `CameraManager.openCamera("0", callback, handler)`，不是Unity通用库中的无关Camera2实现。
3. `smali_classes2/u5/b.smali:85–107`：onOpened把设备交给任务处理。
4. `smali_classes3/o0/n.smali:554–585`：读取该Surface，建立CameraCaptureSession。
5. `smali_classes2/u5/c.smali:17–58`：收到onCaptureCompleted后更新SUCCESS并累计帧完成计数。

据此可以考虑在自定义Android界面中使用独立Camera2预览模块，并以SurfaceView/TextureView呈现；Compose仅作为承载层，不让频繁状态重组重开摄像头。尚未证明camera 0输出的是某个单镜头、原始多路拼接还是设备端合成环视，也未证明没有原厂控制命令时能得到有效帧。

### 3.3 控制面不能与视频面混同

已追踪的视角业务：`AvmVM.smali:1597–1642` 的 `u/v` 对应2D/3D切换；对应协程写 `Avm2dView/Avm3dView`，等待200ms，再写Default形成脉冲。`CheryAvmHardwareAbstraction$registerSetMethod$2/$3` 创建长度10、初始全-1的数组，仅改下标3为视角协议值，经 `smali_classes2/e6/a.smali:45–62` 调用 `VirtualCarPropertyManager.sendData(0x40a,0,list)`。

静态协议映射：2D前/后/左/右鸟瞰组合=1/2/3/4，前/后广角=5/6，前多视图=20；3D前/后/左/右=7/8/9/10，左前/右前/左后/右后=11/12/13/14，自由拖动=15，Default=0。**这是协议映射，不是enum自身value，也不是camera ID；本轮没有写入或确认实车效果。** 系统属性的普通应用授权、请求拒绝和回流仍须验证，不能直接照数值发命令。

对外接口补查：`AutoService.smali:259–268` 的onBind直接返回null；Data/State服务检查各自ACCESS权限后提供监听器注册/注销，已检查的 `smali/t4/b.smali`、`t4/d.smali`、`t4/c.smali` 没有Surface、视频帧数组、共享buffer或FD转发；State回调是两个整数。结论仅限这些接口，不能泛化为“整个系统没有视频服务”。

旧SystemUI `DualVehicleProperty` 常量不能替代本车DJI协议。旧canapp的0x40a已在DJI实际业务中找到消费者，但其余字段不能据名称盲写。

## 5. 最小验证与建议顺序

### 第一阶段：单路实时预览证据

先做独立最小Android预览探针，不改正式地图、歌词和车控源码：

1. 枚举Camera2设备、characteristics及availability；获取正常CAMERA授权，明确使用普通应用身份，不盲加system shared UID。
2. 在停车、原厂环视未显示且可接受短时视频占用变化的现场，验证camera 0短时预览。**打开相机不是只读无副作用行为**：本车有跨ID驱逐记录，验证前须确认该具体影响在用户范围内。
3. 只连接数据面，不发送未知AVM/CAN/标定指令。记录是否有首帧、真实动态帧、画面内容、尺寸、延迟、帧率、错误码；黑帧或request完成不能算可用视频。
4. 离开页面立即关闭session/device，验证原厂环视可恢复及其它相机客户端未持续异常。占用失败时显示不可用，不抢优先级、不自动停原厂服务。
5. 只有取得有效画面后，才判断原厂是否需要激活命令，以及视频是否已合成；再单独研究前/后/左/右视角。

### 第二阶段：正式嵌入

单路通过后再讨论内容区摄像头页、临时小窗或扩展画面；保留页面停止/销毁释放、权限拒绝、被占用、断连、黑帧及超时反馈。必须验证原厂倒车/环视的接管与恢复，不能把黑屏或冻结上一帧伪装成实时视频。

优先顺序：**DJI camera 0预览 → 确认画面语义与接管 → 视角控制 → DVR socket适配 → 多路并发**。不推荐用循环截图/ADB录屏代替正式实时视频链路；电脑ADB仅用于研究和验证，不是最终功能的运行依赖。

### 7.3 冲突：实机确认，不支持直接并发

用户明确反馈“手动测试完了，能显示，会跟360冲突”。随后回读 `after-user-camera.txt` 补充确定性证据：

### 7.4 下一步与流媒体后视镜边界

优先验证后广角 `RearWide`输出，而不是从当前前方画面猜后方。已有静态控制映射：`BirdAndRear`协议值2、`RearWide`协议值6；均不是Camera ID，也不是可不经生命周期/权限/状态确认随意写入的指令。本阶段未发送视角命令。

可行的显示链：真实后广角输出 → 去掉鸟瞰/车模/无关区域 → 等比宽屏裁剪及适度缩放 → 依据真实左右参照决定是否水平镜像。当前数据是已合成画面，未证明有原始四路buffer；裁剪不能恢复已丢失像素，放大会降低有效分辨率。去鱼眼仅在能取得合理标定/映射时准确进行，不能以任意拉伸代替校正。

下一批有价值的候选：camera 1画面内容与读权限；DVR本地socket视频（预计更适合前向，方向未证实）；后/左/右广角模式。不是需要重新把已通过camera 0从头验证。大疆代码中存在 `AVM_ERM_SMALL` 与 `ErmVideoGlesTextureView` 名称，仅证明该软件有相关模式类，尚未确认本车是否提供专用电子后视视频。

流媒体后视镜原型需测真实后方移动物体、端到端延迟、夜间/眩光、裁剪后的视野、镜像方向、视频冻结/掉帧及原厂360接管。当前约20fps环视合成流可以作为原型输入，但不足以宣称能替代实体后视镜或达到专用流媒体镜头画质。

### 7.5 后视广角与去畸变结论（2026-10-02）

本节记录用户确认“不适合作为流媒体后视镜”后的收束结论。它不撤销第7.2节已经确认的“camera 0可以输出真实动态画面”，而是限定该画面不适合当前产品目标。

#### 实机确认的后视继承路线

1. 用户先在原厂环视页面手动选择标准后视方向；原厂截图显示真实后方场景、后视标签、鸟瞰区域和后摄区域。
2. 关闭原厂窗口后，独立探针打开逻辑 camera 0，仍收到同一组后视合成输出；这是当前唯一确认可重复的后视来源。camera 1仍是前向画面，不能用来合成后视。
3. 探针的“仅右侧主画面”候选对应源图归一化 ROI `[1/3, 0, 2/3, 1]`，能够去掉左侧鸟瞰候选区域，但它只是裁切，不是从原始后摄 buffer取流。

#### GPU校正实验

0.5探针把普通预览改为 GLES2 外部纹理链：Camera2 → `SurfaceTexture` → `GL_TEXTURE_EXTERNAL_OES` → 右侧 ROI → 一阶径向采样 → 屏幕。校正参数只改变显示采样，不写车端属性，也不改变Camera2输出。实车日志显示 `camera 0 / 1920x1080`持续产生capture和GL帧，首帧日志同时出现 `CAPTURE count=1` 与 `GL_FRAME count=1`，之后约20fps级别持续更新；相机争用和断连边界仍与前述一致。

静态检查没有找到可直接复用的OEM镜头参数：DJI解码目录中的 `texture_oes_fragtment_shader.glsl` 只是对外部纹理直接 `texture` 采样，顶点着色器只有矩阵变换；找到的“AVM calibration”是状态/售后标定业务，未暴露后摄内参、径向系数、切向系数或网格LUT。Mengbo静态路径是QNX `SimpleClient`视频链，也没有在当前Android侧找到可用标定数据。因此探针只能提供现场候选参数，不能声称完成数学标定。

现场滑杆比较了 `k1=0` 原图、负值和正值候选，确认参数能实时改变画面，`k1=0`也能作为原图对照。但负值只能收回一部分边缘，不能修复以下问题：

- camera 0是环视合成画面，裁切前已经包含布局和可能的设备端投影；裁切不能恢复被合成流程丢弃的像素。
- 右侧画面仍有明显广角透视、边缘拉伸和视场取舍；单一径向系数不能修复投影、切向误差、相机姿态或合成几何。
- 为了只保留右侧主画面，有效区域本身已经缩窄；校正再向内取样会进一步损失边缘视野，放大后有效分辨率和可读性下降。
- 该画面的角度和质量不符合流媒体后视镜的观看习惯，尤其不能把它当作专用后视镜头的自然、稳定、低畸变画面。

实机证据保留在被忽略目录：`.tmp/camera-rear-test/after-oem-rear-probe-ready.png`、`.tmp/camera-rear-test/rear-cropped.png`、`.tmp/camera-rear-test/v05-preview-k00.png`、`.tmp/camera-rear-test/v05-preview-k12.png`以及对应 `v05-preview-k12-log.txt`。原图含车牌和现场环境，只保留本机，不作为公开fixture。

#### 收束决定

不把0.5 GPU校正方案接入正式地图，也不继续以camera 0合成流开发流媒体后视镜。若未来重新评估，前置条件应是取得独立的原始后摄流，或取得与本车匹配的OEM标定网格/内外参，并重新测视场、延迟、夜间眩光、镜像方向和原厂接管；仅继续调一个径向滑杆没有足够收益。

本轮结束清理时，`adb shell am force-stop com.icar03.cameraprobe`因 `192.168.0.203:5555`进入 offline 未获设备确认，后续重连诊断也未发现在线的 `S56_HQX / SDK 28`。因此文档只记录“停止未确认”，不把设备清理写成已完成；APK和源码仍作为本机研究产物保留。
