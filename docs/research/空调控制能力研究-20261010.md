## 1. 现有文档覆盖情况

已有记录已经包含三类相邻能力，但此前没有一张空调完整目标表：

1. [车机媒体能力研究](车机媒体能力研究.md)记录了普通第三方 APK 读取车内温度 `getDataFloat(0x110, 1)`、座椅通风、前后风挡除霜等能力。这里的车内温度是实际环境温度，不是主驾／副驾空调设定温度。
2. [车机控制能力扩展研究](车机控制能力扩展研究-20261008.md)已确认 `com.mengbo.launcher3.OPEN_AC` 可以打开 OEM 底部空调页；这证明了“打开原厂控制页”的入口，不等于第三方应用已经拿到空调属性读写闭环。
3. [快捷车控与座椅主链对照](快捷车控与座椅主链对照-20261009.md)确认当前正式地图已有统一 `VirtualCarService` 适配链，但现有正式协议和 UI 还没有空调这些字段。

当前正式地图源码只登记了座椅通风等既有车控能力；没有找到空调电源、主副驾设定温度、同步、自动、风量、风向或离子发生器的正式 `VehiclePort`／`ContentVehicleProtocol` 接入。因此下表都是研究输入，不能当作产品已实现。

## 3. 冷、暖、通风三个 OEM 按钮是什么

你要的就是 OEM 空调页右下角的三个按钮，原厂代码中的对应关系是：

- **雪花按钮**：控件名 `btFastCool`，调用 `setPapidCooling()`，发送 `0x11e / raw 2`。源码把它称为快速制冷，但它就是页面上的制冷按钮。
- **太阳按钮**：控件名 `btFastHot`，调用 `setPapidHeating()`，发送 `0x11f / raw 2`。源码把它称为快速制热，但它就是页面上的制热按钮。
- **风按钮**：控件名 `btVenMode`，调用 `setVentilationSwitched()`，发送 `0x119 / raw 2`。这是页面上的通风按钮，本轮已经完成普通 UID 的写入、回读和恢复验证。

因此，`0x11e`、`0x11f`、`0x119` 不是三个无关的内部动作，而是 OEM 页面这组三按钮背后的三个控制入口。前两个带有“一键快速”的原厂命名，所以它们可能是一次性请求而不是持久二态；但产品上仍应按“制冷、制热、通风”三个按钮来理解，并以关联状态回读或用户体感确认成功。

其他字段是辅助控制：AC 开关是 `0x102`，Auto 是 `0x104`，风量是 `0x10a`，出风方向是 `0x105`，PTC 是 `0x106`，ion 是 `0x10e`。`0x346` 出现在顶部自动风量滑条 `acMarkView` 的回读和写入中，不是右下角三个按钮。

本轮已经验证风按钮 `0x119`；雪花 `0x11e` 在普通 UID 路径返回 `sendData not handled`；太阳 `0x11f` 尚未独立发送，因此制冷和制热按钮仍不能宣称第三方控制成功。

## 4. ion 是否是空气净化

可以确认两点：

1. 原厂空调应用的函数命名是 `getGenerator()`／`setGenerator()`，界面控件是 `btPurify`。
2. 当前 S56 CSV 对同一虚拟函数的名称是 `HVAC_ION_GENERATOR_ON`，而空气质量评分另有 `HVAC_AIR_QUALITY_RATING_INNER`，AQS 模式又是单独的 `HVAC_AQS_MODE_ON`。

所以 `ion` 最稳妥的中文说明是**离子发生器／净化相关**。可以在产品层显示“离子净化”或“空气净化（离子）”候选，但在普通 APK 实测确认它的物理效果前，不把它写成完整的空气质量控制或滤芯净化能力。

另外存在一个需要保留的静态冲突：SystemUI 的 [HvacManager](../../.tmp/research-20260926/decode/systemui/smali_classes2/com/mb/systemui/statusbar/HvacManager.smali) 把虚拟函数 `0x10d` 的状态存进 `isGeneratorOn`；而原厂空调应用的明确 `getGenerator()`／`setGenerator()` 使用的是 `0x10e`，CSV 又把 `0x10d` 命名为 `HVAC_AQS_MODE_ON`、把 `0x10e` 命名为 `HVAC_ION_GENERATOR_ON`。在这个冲突消除前，正式适配只采用空调应用和 CSV 同时支持的 `0x10e`，不采用 `0x10d` 作为 ion 命令。

## 5. 能否由 03地图或第三方应用控制

### 已有可复用条件

普通第三方 APK 已经在当前车机通过以下链路实际读取并控制过其它车控目标：

```text
普通 APK
  → com.chery.virtualcarservice/.virtualcar.VirtualCarService
  → com.chery.canmanager.interfaces.IVirturalCarProperty
  → getData / getDataFloat / sendData
  → VirtualCar / Vehicle HAL
```

这条链路在[车机媒体能力研究第17节](车机媒体能力研究.md#17-普通第三方apk车辆读取与主驾座椅控制实机研究2026-09-28)中已有普通 UID 的温度读取、座椅通风／加热写入、回读和恢复证据。OEM 空调应用则通过 `MBCanManager` 包装的 `VirtualCarPropertyManager` 调用同一类虚拟车控服务。它们说明空调值得沿现有车控适配器路线验证，但不替代空调字段本身的运行级证据。

### 普通 UID 实车验证结果

本轮使用普通 UID `10293` 的临时 APK，通过 `com.chery.virtualcarservice/.virtualcar.VirtualCarService` 和 `IVirturalCarProperty` 直接调用 Binder，在当前在线 `S56_HQX` 上完成了真实读写。测试前基线为：`power=2、ac=1、auto=2、direction=1、ptc=1、dual=2、left=27.5、right=27.5、fan=1、ion=1、autoVent=2、ventilation=1`。通风独立 round-trip 的专用日志为 [`controls-hvac-ventilation-20261010.txt`](../../.tmp/vehicle-controls-15.9XVju4/controls-hvac-ventilation-20261010.txt)。

| 字段 | 运行级结果 | 证据含义 |
|---|---|---|
| 主驾／副驾温度 | `27.5→27.0→27.5`，两个区域均目标值回读且恢复成功 | 普通 UID 可写入两侧 float 设定值，两个区域没有串写 |
| 风量 | `1→2→1`，目标值和恢复值均回读 | 普通 UID 可写入相邻风量档位 |
| 双区同步 | `2→1→2`，目标值和恢复值均回读 | 普通 UID 可切换该状态字段 |
| ion | `1→2` 目标值回读；延迟恢复后最终为 `1` | `0x10e` 字段可控；不等于已证明离子发生器的物理净化效果 |
| AC | `1→2` 目标值回读；最终为 `1` | 普通 UID 可触发并读回 AC 字段变化 |
| Auto | 从 `1` 发送 raw `2` 后即时和 4 秒后均为 `2` | raw `2` 是可用的开启请求；温度／风量手动写入会退出 Auto，恢复时必须最后处理 |
| 通风按钮 `0x119` | 写 raw `2` 后回读 raw `2`；写 raw `1` 后短延时仍为 raw `2`，最终等待后回到 raw `1` | OEM 风按钮对应的通风控制已完成普通 UID 验证，但 UI 必须等待新鲜回流 |
| 雪花制冷按钮 `0x11e` | 请求返回 `RemoteException: sendData not handled` | 当前第三方 Binder 路径未证明支持制冷按钮 |
| 太阳制热按钮 `0x11f` | 独立请求同样返回 `RemoteException: sendData not handled`；请求前左右为 `28.5°C`，未接受写入 | 当前第三方 Binder 路径未证明支持制热按钮，且本次未发送恢复写入 |
| 自动风量附加档位 `0x346` | 本轮未单独验证 | 它是顶部自动风量滑条字段，不是雪花／太阳／风按钮 |
| PTC | 发送 raw `2` 后仍回读 `1` | 当前条件下未证明普通 UID 可开启 PTC |

最终恢复通过 OEM 空调页和普通 UID 只读／回读交叉核对，日志为 `power=2、ac=1、auto=2、left=27.5、right=27.5、fan=1、direction=1、dual=2、ion=1、ventilation=1`；探针退出时绑定已释放。日志只证明 Binder 字段和车机状态回读，不证明用户在车内感受到实际降温、升温或离子净化效果，也没有把页面视觉状态当作第三方控制成功条件。

### 当前还没有证明的部分

- `0x11e/0x11f` 快速制冷／制热动作的可用路径、完成回报、失败状态和与 PTC／AC／风量的联动仍未证明。
- PTC raw `2` 在当前车辆条件下没有改变回读，需先确认原车条件或原厂 UI 前置状态，再决定是否继续验证。
- 没有验证正式 `com.autonavi.amapautolite` 在当前身份下的持续订阅、Binder 断连、超时和状态投影。
- 不能把 `com.mengbo.launcher3.OPEN_AC` 打开原厂页当成地图已经接入每个空调字段的证据。

## 6. 下一轮最小验证顺序

普通 UID 的温度、风量、双区同步、AC、Auto、ion 和风按钮读写恢复已经完成，后续只沿剩余风险验证：

1. 如果产品需要雪花或太阳按钮，再单独排查 `0x11e/0x11f` 被拒绝是否是当前 Binder 路径或函数支持范围限制；当前两者都不能宣称可控。
2. 确认 PTC `0x106` 的原车前置条件；若仍回读 raw1，保留为当前条件不可控。
3. 在正式地图接入前，补做 `com.autonavi.amapautolite` 的持续订阅、Binder 断连、超时和状态投影验证。

完成剩余普通第三方 APK 证据后，才把字段迁入正式地图 `VehiclePort`／`ContentVehicleAdapter`；地图 UI 的成功态必须来自新鲜回读或明确动作回报，Binder 事务返回本身不算空调执行成功。

## 7. 当前结论

当前已经确认：**普通第三方 APK 可以通过当前车机的 VirtualCar Binder 路径读取并实际改变主副驾设定温度、风量、双区同步、AC、Auto、ion，以及 OEM 风按钮对应的通风字段，并完成写后回读与恢复。** OEM 雪花制冷按钮对应 `0x11e`，太阳制热按钮对应 `0x11f`；两者在当前普通 UID Binder 路径都返回 `sendData not handled`，因此不能宣称可控。`0x346` 是顶部自动风量附加档位，不是这三个按钮。正式地图仍不能宣称已经接入冷、暖、通风按钮。

对用户提出的 `ion`，当前最有根据的解释仍是“离子发生器，属于净化相关功能”；本轮已证明 `0x10e` 的状态字段可由普通 UID 改变并恢复，但没有证明离子物理净化效果。冷、暖的产品成功态还必须分别等待可接受的动作回报和车内体感确认。
