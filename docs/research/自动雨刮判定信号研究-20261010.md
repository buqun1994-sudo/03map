# 自动雨刮判定信号研究（2026-10-10）

## 目标

目标不是读取“雨刮器模式”或雨量传感器名称本身，而是确认原厂自动雨刮逻辑已经判断需要刮水时，普通第三方应用能否收到可用事件。

## 当前结论

截至本轮静态研究和普通 UID 只读订阅实验：

- 已确认普通应用可以绑定当前车机 `com.chery.virtualcarservice/com.chery.virtualcarservice.virtualcar.VirtualCarService`，接口描述符为 `com.chery.canmanager.interfaces.IVirturalCarProperty`。
- 已确认接口支持按虚拟函数注册 `ICanFuncLister` 回调；只读探针成功对 `608`、`561`、`1296`、`1563` 注册并解除订阅。
- 已确认 `561 / 0x231 / HAL 0x2140099b` 是自动雨刮灵敏度配置状态，不是雨量值。原厂设置代码读取该字段并投影灵敏度档位。
- 已确认 `1296 / 0x510 / HAL 0x2140162e` 是洗车流程使用的自动雨刮抑制／恢复状态，不是雨量或电机运行状态。
- 已确认 `608 / 0x260 / HAL 0x21400997` 是前雨刮模式状态：本车回读 `0` 为关闭、`1` 为自动、`2..5` 为手动1..4。它只能说明当前处于自动档，不能说明自动逻辑此刻是否请求刮水。
- 已确认 `1563 / 0x61b / HAL 0x21411355` 是五项复合数组，普通应用能读到并订阅其数组回调。保存的 Launcher OEM 样本中的 `WiperTrigger` 在第四项为 `2` 时弹出雨刮场景；这证明它是原厂雨刮场景显示触发输入，但尚未证明第四项是雨量判定、自动刮水请求或实际电机状态。
- 本轮只读动态采样持续约197秒，共保存100次 `dumpsys car_service` 快照。采样开始时前雨刮为自动档 `608=1`，期间 `608=1`、`561=1`、`1296=1`、`1563=[0,2,2,2,2]` 均保持不变；HAL `0x21400997` 的事件计数保持 `1`，`0x21411355` 的事件计数保持 `2`，应用侧没有新的候选回调。由于本轮没有得到“实体雨刮确实因洒水自动刮动”的人工确认，这只能作为自动档静态基线，不能作为雨感触发否定证据。
- 当前系统 Android 传感器列表只有加速度、陀螺仪、环境温度，没有 Android 标准雨量传感器。
- 共享 SDK 常量中存在 `MT_RAIN_SENSOR_RAINFALL=0x21400be8`、`MT_WIPER_*` 等字段，但在当前 S56 车型 CSV、当前 HAL 属性清单和原厂消费者中未找到映射或实际读取证据，不能作为本车可用接口。

因此，现阶段还不能宣称“原厂判断该雨刮时有稳定可用通知”。最有希望的候选是 `1563` 第四项，但第三次按明确指令即时操作的对照中它和其它候选均未出现边沿；它不能接入地图作为正式事件。若继续实现“原厂觉得该雨刮了”的功能，应转向当前车型更底层的 CAN/HAL 生产者、雨感 ECU 专用接口或原厂车控服务内部；继续读取 `561`、`608`、`1296`、`1563` 只会得到配置／模式／洗车抑制／场景基线，无法可靠区分自动雨感触发。
